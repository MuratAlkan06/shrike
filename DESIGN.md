# Design decisions

Each entry states the decision, the strongest alternative that was rejected, and why, in plain language. They are written to be quotable in an interview, so nothing here hides behind jargon.

## Module graph: shrike-core <- shrike-clients <- shrike-admin

**Decision.** Three Maven modules in one reactor. `shrike-core` holds the broker engine and depends on the JDK alone. `shrike-clients` depends on core for its protocol and codec types. `shrike-admin` depends on clients and is the only module allowed to use a framework. Nothing points back up the chain.

**Alternative rejected.** A single module with packages as the only boundary.

**Why.** A package boundary is a convention; a module boundary is compiled and checked. The maven-enforcer bannedDependencies rule on core turns "core stays JDK-only" into a build failure rather than a code-review opinion, and it keeps the engine testable without a framework on the classpath.

## Spring enters through an imported BOM, not a parent POM

**Decision.** `shrike-admin` imports `spring-boot-dependencies` as a `pom`-typed dependency with `import` scope in its own dependencyManagement, and pins `spring-boot-maven-plugin` itself.

**Alternative rejected.** Inheriting from `spring-boot-starter-parent`.

**Why.** The reactor needs its own parent for the toolchain, enforcer, and version pinning that apply to every module, and a POM has only one parent. Importing the BOM keeps Spring's version alignment where it is wanted — inside the admin module — while core and clients carry no Spring coordinate at all. The cost is that the BOM brings no plugin management, so the plugin version is pinned by hand.

## Toolchains plugin, because local Maven runs on a Java 25 JVM

**Decision.** `maven.compiler.release=21` plus `maven-toolchains-plugin` requiring vendor `temurin` version `21`, and a test that asserts `Runtime.version().feature() == 21`.

**Alternative rejected.** Relying on `release=21` alone.

**Why.** `release=21` fixes the language level and the API surface, but the build still compiles and runs tests on whatever JVM launched Maven — here a Java 25 JVM. The toolchain forces javac and the surefire fork onto a real JDK 21, so what CI tests is what a JDK 21 user runs. CI adds a class-file check for major version 65, and the build fails outright when no matching toolchain is declared, which is the loud failure the alternative lacks.

## The clock is an injected TimeSource in its own package

**Decision.** `io.shrike.core.time.TimeSource` is a single-method interface returning epoch milliseconds; `SystemTimeSource` is the only code in the broker that calls `System.currentTimeMillis()`. Components take a `TimeSource` through their constructor.

**Alternative rejected.** Calling `System.currentTimeMillis()` where the timestamp is needed, and letting tests assert a range around "now".

**Why.** A record's timestamp is data that ends up on disk, so tests should assert its exact value, not that it fell inside a window. Injection makes that possible without a single sleep, and it keeps the wall clock — the one thing a test cannot control — behind a seam that is one line long. The interface lives in `io.shrike.core.time` rather than in `io.shrike.core.log` because retention, delivery timeouts, and the network layer will all need the same clock, and none of them should have to depend on the log package to get it.

## The record frame, byte by byte

**Decision.** Every record is stored as one frame, big-endian, with a fixed-width header:

```
length:int32 | crc32c:uint32 | magic:uint8 | attributes:uint8 | offset:int64 | timestamp:int64 | keyLen:int32 | key | valueLen:int32 | value
```

- `length` counts every byte after itself, so a frame occupies `4 + length` bytes on disk.
- `crc32c` is `java.util.zip.CRC32C` over the bytes from `magic` through the last byte of `value`. The `length` field is deliberately outside that cover.
- `magic` is 0 and identifies this layout. `attributes` is 0 and reserved; a reader steps over its bits so a later slice can spend them without invalidating today's files.
- `offset` is written into the frame rather than inferred from the file.
- `keyLen` is -1 for a record appended with no key and 0 for a key of zero bytes, so the two stay distinguishable after a round trip. `valueLen` is never negative: a null value would be a tombstone, tombstones only mean something under compaction, and compaction is a non-goal, so `append` refuses one.

**Alternative rejected.** Covering the whole frame with the checksum, including the length, and skipping the explicit `offset` field because a reader could count records from the start of the file.

**Why.** A reader meets the length field first and must decide how many bytes to allocate for the rest of the frame *before* it has anything to verify: a checksum over the length is a checksum it cannot use yet. So the length is range-checked against `max.record.bytes` instead — the same bound the append side enforces — and a corrupt or hostile length is refused rather than believed and turned into a 2 GiB allocation. Everything after the length is covered, so a flipped bit anywhere in the header or payload fails the read.

Writing the offset into the frame costs eight bytes and buys self-description: a frame carries its own identity, so a reader can assert that the record at a position is the record it asked for, and a later recovery scan can rebuild offsets from the file alone instead of trusting a count. `RecordFrameGoldenBytesTest` freezes the whole layout, checksum included, against bytes derived from this description rather than from the implementation.

## `offset` counts records, `position` counts bytes — and the names never blur

**Refined in Slice 2.** The in-memory `positionsByOffset` list is gone; a segment's sparse index is what maps an offset to a position now, and the mapping is rebuilt from the log rather than held for the life of the process. The law itself is unchanged, and the last sentence of this entry is why the swap cost nothing.

**Decision.** `offset` is always a logical record number and `position` (always spelled `positionBytes` on a variable) is always a byte location in a file. `Log.append` returns an offset; the in-memory `positionsByOffset` maps one to the other; `RecordLocation` carries both plus topic, partition, and file, and every storage error quotes it.

**Alternative rejected.** Letting a reader address records by byte position, which is what the file actually needs.

**Why.** The two numbers are both `long`, so the compiler cannot tell them apart and only names can. Keeping the offset as the public currency also keeps the door open for segments and an index: when a record moves into a different file at a different position, its offset does not change. The mapping is the part that is allowed to be rebuilt.

## A read outside the readable range throws, and reads return a `StoredRecord`

**Decision.** `Log.read(long offset)` returns a `StoredRecord` — a record of `offset`, `timestampMillis`, `key`, and `value` — or throws. A negative offset and an offset at or past the high-water mark (`nextOffset()`) both raise `OffsetOutOfRangeException`, which carries the requested offset and the readable range `[firstOffset, nextOffset)`. An empty log has the empty range `[0, 0)` and refuses every read.

**Alternative rejected.** Returning `Optional<StoredRecord>` or `null` for a read past the end, and clamping a negative offset to 0.

**Why.** Reading past the end and reading before the start are two different mistakes, and a caller that gets `Optional.empty()` cannot tell them apart or learn what the valid range was — it would have to ask a second question to write a useful error. Clamping is worse: it silently answers a question the caller did not ask. A consumer that wants "wait until there is more data" is asking about the network layer's fetch semantics, not about a byte range in a file, so that behavior belongs in a later slice rather than smuggled into this return type. `StoredRecord` returns the stored offset and timestamp alongside the payload so a caller can verify what it got rather than assume.

## The log refuses to reopen a file it did not create

**Superseded by Slice 2.** Recovery arrived, so reopening no longer refuses: see "Reopening a log recovers it, because Slice 2 can read a file it did not write". The entry is kept because the reasoning it records is why recovery had to exist before reopening was allowed.

**Decision.** `SingleFileLog.open` creates the log file with `CREATE_NEW`. An existing file fails the open with a `ShrikeIOException` that says a recovery scan is a later slice. The offset-to-position map is held in memory only.

**Alternative rejected.** Opening an existing file and appending to the end of it.

**Why.** Appending to a file this class has not read means trusting that its last record is intact and that the next offset is whatever the file implies. Deciding that safely is exactly what recovery does — scan for the last valid frame, truncate a torn tail, and say so — and recovery is not in this slice. Refusing loudly beats a broker that quietly appends after a half-written record. It also makes the in-memory map honest: nothing is lost by not persisting it, because there is no path that needs it after a restart yet. Its size is bounded by `Integer.MAX_VALUE` records, which is another reason it is temporary.

## Durability in this slice: appends reach the operating system, `close` forces the file

**Refined in Slice 3.** The broker now acknowledges produce requests, and it acknowledges them on exactly this promise and no stronger one — see "What a produce promises, said plainly, and where the flush mode went". A commit of a group offset is the one thing this build forces before it answers.

**Refined in Slice 2.** Sealing a segment forces it, so a log now has two force points rather than one: the roll that seals a segment, and `close()` for the segment still taking records. What an `append` promises has not changed — see "Segments roll on size, and a segment is sealed only after it is forced".

**Decision.** `append` writes the frame through `writeFully` and returns once the operating system has the bytes. Nothing is forced to the device until `close()`, which calls `force(true)` before closing the channel. The README claims ordering and integrity, not survival of a power cut.

**Alternative rejected.** Forcing on every append, which would let the log claim durability today.

**Why.** An fsync per record is a policy decision with a large cost, and the policy — per record, per interval, or never — is a configured flush mode in a later slice. Choosing one now would either pick the slow default for everyone or leave the claim vague. Forcing at `close()` is the one point where the cost is paid once and the promise is exact, so it is the only durability sentence this slice makes.

## Segments roll on size, and a segment is sealed only after it is forced

**Decision.** A partition is a sequence of segment files named after the offset of their first record: `00000000000000000000.log` beside `00000000000000000000.index`, then whatever base offset comes next. Appending to a **non-empty** active segment rolls it when the record would push it *past* `segment.bytes`; a record that fills the segment to the byte does not roll it, and the record that would have overflowed becomes the first record of a new segment whose base offset is that record's own offset. An empty active segment accepts any record `max.record.bytes` allows, even a frame larger than `segment.bytes`, because a record no segment would take could never be stored at all. Rolling seals the segment it leaves behind, in this order: force the log file, force the index file, and only then treat the pair as immutable.

**Alternative rejected.** Rolling when a segment *reaches* `segment.bytes` and marking segments sealed without forcing them, leaving the fsync to the operating system's own schedule.

**Why.** The order of those three steps is the whole point, and it buys the recovery algorithm. Because a sealed segment was on the device before the writer moved on, a crash can only tear the segment that was being written, so startup reads one file frame by frame instead of all of them — a partition with a thousand segments costs the same to recover as a partition with one. Sealing without forcing would make that reasoning false: any segment could then hold a half-written frame, and honest recovery would have to walk every byte the broker had ever stored. Rolling on "would exceed" rather than "would reach" keeps `segment.bytes` a bound the files respect rather than one they cross by a frame, and the empty-segment exception is what keeps the bound from turning into a record the log refuses to store.

## The offset index is derived data, so nothing trusts it

**Decision.** Each segment carries a sparse index of fixed 8-byte big-endian entries, `relativeOffset:int32 | position:int32`, holding one entry per `index.interval.bytes` of appended records. Offsets are stored relative to the segment's base offset and positions as int32, which the 1 GiB cap on `segment.bytes` and `max.record.bytes` keeps safe. A lookup finds the segment whose base offset is the greatest one at or below the target, binary-searches that segment's entries for the greatest relative offset at or below it, and walks frames from there comparing each frame's stored offset with the one asked for — a walk bounded by the index interval. An index that is missing, whose size is not a whole number of entries, or whose entries do not climb or point inside the log is emptied and rebuilt by scanning the log. The rule that decides which record earns an entry is one method, `indexIfDue`, called both by `append` and by the scan that rebuilds, so it reads nothing but the bytes of the log.

**Alternative rejected.** A dense index — one entry per record, which is what Slice 1's in-memory `positionsByOffset` list was — and treating a damaged index as a reason to fail startup.

**Why.** A dense index costs 8 bytes of memory or disk per record forever and buys a lookup that is already cheap: with a 4 KiB interval, the walk after a binary search reads at most a few kilobytes. More importantly, an index restates what the log already says, so making it authoritative would create a second copy of the truth that can disagree with the first. Deriving it means a corrupt index is an inconvenience rather than data loss, and it means the code has one honest answer to "what if the index is wrong": delete it and read the log. Because the entry rule lives in exactly one method, an index grown record by record and an index rebuilt in one pass are the same file, which is what lets recovery rewrite an index without changing anything a reader can see. An index with no entries at all still yields correct reads — a lookup that finds no entry starts at the first byte of the segment — which is the strongest way to say the index is not load-bearing.

## Recovery walks the tail segment, cuts off what is torn, and logs where

**Decision.** Opening a partition directory sorts its segments by base offset. Every segment but the last is sealed, so it gets a cheap check of its index only — the file exists, its size is a whole number of entries, no entry points past the end of the log — and is rebuilt only when that fails; its log file is not read. The last segment is walked frame by frame from its first byte, applying the checks a read applies: the length field must be in range, the CRC32C must match, the magic must be this build's, and the frame's own offset must be the one the walk expects. The first frame that fails, or that the file ends inside, ends the log: the channel is truncated to the byte after the last whole frame, the tail's index is rebuilt from the same walk, a WARN names the topic, partition, byte position, and file, and the next offset becomes the base offset plus the number of frames that survived. A zero-byte tail segment is a valid empty segment; fewer than four trailing bytes cannot even hold a length field, so they are cut off; a run of trailing zeros fails the length range check and is cut off too. Damage inside a sealed segment is not repaired: startup does not look, the damaged record fails with a `CorruptRecordException` when it is read, and the records before and after it still read.

**Alternative rejected.** Walking every segment at startup, and refusing to start when the tail is torn so that a human decides what to do.

**Why.** Walking every segment would make startup cost grow with everything ever stored, and it would be redundant work: the sealing order already proves the earlier segments are whole. Refusing to start is the option that sounds safe and is not — a broker that will not come up after a power cut is down, and the torn tail is by definition made of records no producer was ever told about, so cutting them off loses nothing that was acknowledged. The WARN with the byte position is what keeps that honest: the truncation is a fact in the log file, not a silent repair. Recovery is idempotent because the walk depends only on the bytes on disk: a second restart with no writes in between truncates nothing, writes the same index entries, and leaves every file the size it already was, which is asserted rather than assumed. Leaving sealed damage in place is the same honesty in the other direction: the broker reports the record it cannot vouch for instead of quietly deleting the healthy records that follow it.

## Reopening a log recovers it, because Slice 2 can read a file it did not write

**Decision.** `SegmentedLog.open` creates a partition directory and its first segment when there is nothing there, and recovers what is there when there is. This replaces Slice 1's refusal to reopen an existing log file. The in-memory offset-to-position map is gone: a reopened log finds its records through the segment index instead.

**Alternative rejected.** Keeping the refusal for existing files and adding a separate explicit "recover this directory" entry point that a caller has to remember to call first.

**Why.** Slice 1 refused because appending after a record it had never checked would have meant trusting a file it had not read, and it said so in the exception. That reason is now satisfied rather than argued with: opening reads the tail and proves its last frame before it appends a byte after it. A separate recovery step would leave two ways to open a log, one of them wrong, and the wrong one would be the shorter one to type. Recovery is not an operation on a log — it is what opening one means. Dropping the in-memory map is what makes the size of a partition a disk question rather than a heap question, which is the same reason the index exists.

## The log's sizes live in one record next to the log

**Refined in Slice 5.** Half of the last sentence below is now history: `LogConfig` holds two retention settings, `retention.ms` and `retention.bytes`, because retention exists. The rule that sentence stated has not moved — a knob arrives with the code behind it — and the flush half of it still stands, because there is still no flush mode. The record grew rather than a second configuration type appearing beside it, for the same reason it was one record in the first place: these are the numbers one partition's log is opened with, and a retention bound is one of those. Both new settings default to −1, which is off, so a log opened the way every log was opened before this slice deletes exactly what it deleted before: nothing. That default is deliberate and is the subject of its own entry below.

**Refined in Slice 3.** `RecordFrame` is public now. A fetch response carries a byte range of a partition's log verbatim, so the consumer that reads those records back parses the same frames the log writes, and one parser for one layout beats two that are free to disagree — `WireRecordsTest` reads the very bytes `RecordFrameGoldenBytesTest` freezes. What this entry says about where validation belongs is unchanged: `max.record.bytes` is still checked in the log package, and what became public is the parse and the three constants a parser needs. The same move settles the boundary PRINCIPLES §9 asks to have written down: `StoredRecord` and `ProducedRecord` are part of the codec surface `shrike-clients` may depend on, because they are value types with no behavior, and nothing else in `io.shrike.core.log` is on that side of the line.

**Decision.** `LogConfig` is a record of `maxRecordBytes`, `segmentBytes`, and `indexIntervalBytes`, validated in its compact constructor, with a `defaults()` factory holding 1 MiB, 128 MiB, and 4 KiB. `segmentBytes` and `maxRecordBytes` are both capped at 1 GiB. It lives in `io.shrike.core.log` beside the log it configures, and it holds no flush or retention setting, because neither behavior exists yet.

**Alternative rejected.** Putting it in `io.shrike.core.config` as the start of a broker-wide configuration type, and keeping `open(...)` overloads that take one `int` per setting.

**Why.** Three `int` parameters in an `open` call are three chances to swap two numbers that the compiler cannot tell apart; a record names them at the call site and validates them once, so a log that holds a config holds one that already makes sense. Validation belongs there rather than in `open` because the smallest legal `maxRecordBytes` is a fact about the frame layout, and keeping the check in the log package is what lets `RecordFrame` stay package-private instead of publishing frame constants to satisfy a config type in another package. The 1 GiB cap is not a taste preference: an index entry stores a byte position in an int32, and the cap is what makes that field safe by construction rather than by hope. Settings for behavior that does not exist are left out, because a knob with no code behind it is a promise the README cannot make.

## The request envelope names an api and its version; the response echoes a correlation id

**Decision.** A request is `length:int32 | apiKey:int16 | apiVersion:int16 | correlationId:int32 | body` and a response is `length:int32 | correlationId:int32 | errorCode:int16 | body`, big-endian throughout, with `length` counting every byte after itself in both. The api key names the operation — 0 produce, 1 fetch, 2 commit offset, 3 create topic, with 4 and 5 reserved and unimplemented — and the version belongs to the key rather than to the connection: `ApiKeys.isSupportedVersion(apiKey, apiVersion)` is the one method that decides whether this build understands a pair, and today it says yes only to version 0. The correlation id is the client's own number, echoed back untouched, and the response repeats neither the api key nor the version.

**Alternative rejected.** One protocol version agreed when the connection opens, and matching each response to its request by the order the two travel in.

**Why.** Order as identity works right up to the first time a client wants two requests in flight, or the broker wants to answer a fetch that is still waiting for records after a produce that arrived later — which is what a fetch held open for `maxWaitMs` will do. A four-byte number the broker never interprets buys that for the price of one field, and it turns a client's bookkeeping into a lookup by key rather than a queue whose invariant nobody can see. A single protocol version is worse than it looks: the day fetch grows a field, produce's version number moves with it, and every client has to be told that its unchanged produce path now speaks version 1. Versioning per key keeps a change local to the api that changed. The response drops the api key because the correlation id already says which question is being answered, and a field the broker restates is a field that can be found disagreeing with the request it answers.

## One error code in the envelope, and an error answer carries no body

**Refined in Slice 3.** `FRAME_TOO_LARGE` has a producer now. The broker weighs every record of a produce request against `max.record.bytes` before it appends any of them, and a request carrying one record too large earns that code and stores none of its records — not even the ones that would have fitted. So the sentence below about it being the one code nothing can produce is history rather than a description: eight of the nine codes were reachable when they were frozen and the ninth is reachable now. What makes it reachable at all is that the two bounds are different numbers — a request may be 4 MiB and a record 1 MiB by default — so an oversized record arrives at the broker instead of being cut off by the frame guard, which is the only reason the broker gets to have an opinion about it.

**Decision.** Every response carries one int16: 0 none, 1 unknown topic or partition, 2 offset out of range, 3 corrupt record, 4 frame too large, 5 invalid request, 6 unsupported version, 7 topic already exists, 99 internal. `NONE` means the body that follows is the answer; every other code means the body is empty and the code is the whole answer. The codec refuses only what the bytes themselves can be wrong about — a negative string length, a record count over its cap, a name outside the character set a path component may use, an api key or version this build does not implement — and leaves what the broker holds to the broker. An unknown topic, an offset outside a partition's range, and a topic that already exists are answers rather than malformed requests, which is why `FetchRequest` does not judge its own offset and `ProduceRequest` does not judge its partition number. Reserved api keys 4 and 5 earn `INVALID_REQUEST`, the same as an api key of 999. `FRAME_TOO_LARGE` is the one code nothing in this slice can produce: it is held for a produce request whose record exceeds `max.record.bytes`, which is a check the broker makes once this protocol reaches it.

**Alternative rejected.** A per-api error body — a message, or a map of per-partition codes — and a distinct code for an api key that is reserved rather than unknown.

**Why.** An error body is a place to leak from. What the parser can say about the field it choked on is useful to whoever runs the broker and useful in a different way to whoever is probing it, so that sentence lives in `RequestDecoding.Refused` for the broker's own log and is never encoded. What is left is the code, and one code in the envelope means the same six bytes answer every api, which is what lets a client read a failure without knowing which request failed. A separate code for a reserved key would tell a caller which numbers are worth waiting for, and it would be a promise this build cannot keep: 4 and 999 are equally "not a request I implement" today, and that is the whole truth about both. Naming `FRAME_TOO_LARGE` with nothing behind it yet is the honest half of freezing numbers — a wire number can be added but never renumbered, so all nine are spelled out now and this entry says which one has no code behind it.

## A length this reader cannot believe closes the connection and is owed no answer

**Decision.** `RequestReader` reads exactly four bytes, and the length they carry must land in `[8, maxRequestBytes]`: 8 because that is the smallest length that can hold an envelope, and `maxRequestBytes` because a broker decides how much memory one connection may make it hold — 4 MiB by default, passed in rather than compiled into the reader. A length outside that range ends the connection with no reply and with nothing allocated for a body, and so does a stream that ends inside the length field or inside the frame. Only a length that passes gets a buffer allocated and filled. Inside the body every count and every declared length is checked against the bytes actually in hand, and against its own cap, before anything is sized to it: a string length against what remains, a produce record count against both its cap of 10 000 and the fewest bytes that many records could occupy, a key or value length against what remains. A body that breaks a rule is a refusal carrying the correlation id and `INVALID_REQUEST`, and the connection lives through it. Those three outcomes are one sealed type, `RequestDecoding` — `Accepted`, `Refused`, `BrokenFrame` — so a connection loop that forgets one does not compile.

**Alternative rejected.** Answering a bad length with `FRAME_TOO_LARGE` and then skipping that many bytes to find where the next frame starts.

**Why.** The correlation id lives after the length. If the length is nonsense then the bytes claiming to be a correlation id are nonsense too, so the reply would be addressed to nobody, and it would tell a stranger that something is listening and how it parses. Skipping ahead is worse than useless: it resynchronizes the stream by trusting the same number that just proved it cannot be trusted. Closing costs a well-behaved client nothing, because a well-behaved client never sends such a length, and it costs a hostile one the connection it was using. The allocation rule is the other half of the same argument: four bytes can ask for 2 GiB, and a reader that allocates first and validates second can be brought down by four bytes, repeatedly, from one socket. So the guard allocates a fixed four bytes, decides, and only then sizes anything to what it was told — and the test that proves it drives the reader with a channel that fails the run if anything reads past the length field, because a body that was never read is a body that was never allocated for.

## A fetch checks and waits under the same lock an append signals on

**Decision.** Every partition owns one `ReentrantLock` and one `Condition`. Every append and every read of that partition's log happens under the lock, because `SegmentedLog` says plainly that nothing in it is safe to call from two threads at once. A fetch that finds fewer than `minBytes` of records available checks what it has and registers as a waiter **without releasing the lock in between**; a produce appends every record of its request, then signals, under that same lock. The wait is bounded by an absolute deadline computed once from the injected `TimeSource`: each `await` is for whatever is left of it, and the predicate — at least `minBytes` readable from `fetchOffset`, or the deadline has passed, or the broker is stopping — is re-checked on every wakeup. `maxWaitMs` of 0 or `minBytes` of 0 answer on the first pass without waiting at all. A wait that expires answers with whatever there is, usually nothing, with error code `NONE` and the current high-water mark, because "there is nothing new yet" is an answer rather than a failure. The high-water mark is the log's own `nextOffset` read under that lock; no copy of it is kept.

**Alternative rejected.** Checking availability, releasing the lock, and then registering the waiter — the arrangement that reads naturally and is written most often. The other alternative was handing waiting fetches to a scheduled executor that re-checks them every few milliseconds.

**Why.** The gap between "I looked and there was not enough" and "I am now waiting" is exactly where a lost wakeup lives. An append that lands in that gap signals a condition nobody is waiting on yet, and the fetch then sleeps for the whole of its `maxWaitMs` while the records it asked for sit on disk. Doing both under one lock closes the gap by construction rather than by luck: the appending thread cannot reach the signal until the waiting thread is inside `await` and has released the lock. That is not a claim a reader has to take on trust — `BrokerFetchWaitTest` lands an append inside the window on purpose, through a seam that fires under the lock at the moment a waiter registers, and the test fails within seconds when the signal is removed.

A poller closes the same gap and pays for it forever: every partition would cost timer work whether or not anything is happening, and every answer would arrive up to one poll interval late for no reason a user could see. The absolute deadline is the other half of the rule. A wait that starts counting `maxWaitMs` again after each spurious wakeup is a wait with no bound at all, which is the same defect wearing different clothes.

The cost is honest and worth naming: a fetch reading bytes off disk holds the partition lock, so it serializes with appends to that partition. That is what the storage layer's own single-writer contract asks for, and the waiting itself does not hold the lock — `await` releases it — so a long poll blocks nobody.

## One acceptor, one platform thread per connection, and a hard cap

**Refined by the network-layer review.** Three things about handing a socket to a thread were wrong in a way only failure could show, and all three are fixed here. First, an accept that failed used to count towards a limit of sixteen, after which the acceptor returned and the broker took no more connections for as long as it ran — but the failure that limit was written for, running out of file descriptors, is exactly the one that clears on its own as connections close, so the cure outlived the disease. An accept that fails while the broker is running now logs a WARN and waits up to a hundred milliseconds *on the stop signal* before accepting again. That is a bounded wait whose predicate is "this broker is stopping", not a sleep for coordination: a shutdown during a backoff ends the acceptor at once, and the only way out of the loop is stopping. Second, the connection is put into the open-connection map *before* `Thread.start()` and the stopping flag is re-read *after* that put: `close()` sets the flag before it walks the map, so a `close()` that walked the map without seeing this entry cannot have set the flag after this read — which means one of the two closes the connection, and neither can leave a served connection that nobody will ever close. Third, a `Thread.start()` that throws — `OutOfMemoryError: unable to create native thread`, under exactly the pressure where a leaked slot matters most — now gives back the map entry and the place under the cap and closes the socket, rather than leaving all three to a thread body that will never run.

**Refined again by the security re-review.** That third fix was right about what to give back and wrong about what to do next: it rethrew, and the throwable ended the acceptor thread while `stopping` was still unset and the listening socket was still bound. What that leaves is a broker that keeps its port and its ready file, answers the connections it already had, and never accepts another one — the exact opposite of the sentence above that the only way out of the loop is stopping. It was also narrower than the hazard it was written for: `new Connection`, `new Thread`, and the map registration all run before `Thread.start()` and can each fail with an `OutOfMemoryError` under the same pressure, and a throw from any of them leaked the place under the cap — shrinking the effective cap by one for the life of the process — together with the socket. So the whole handoff is covered by one unwind now, from the moment `reserveConnection()` succeeds to `Thread.start()` returning: whatever is thrown, the acceptor logs a WARN naming the connection, then the map entry, the place under the cap, and the socket go back, and it accepts the next socket. **No throwable from a handoff ends the accept loop.** A failure that is about this process rather than about that one socket — out of memory, out of native threads — also earns the same bounded `stopSignal` wait an accept failure earns, because meeting the same wall at the speed of a loop is its own outage. The ordering guarantee of the paragraph above survives the restructuring unchanged: the map registration still happens before the stopping re-check, `close()` still sets the flag before it walks the map, and the unwind only ever removes an entry it put there itself. `BrokerConnectionHandoffTest` proves the whole of it through a package-private seam that fails a handoff at its earliest point, on a broker whose cap is one connection: the socket is closed, the acceptor is still accepting, and the place under the cap is back, which is what serving the next client requires. What is left of that handoff — the WARN is logged before the unwind runs rather than after it — is tracked in #10.

**Decision.** A thread named `shrike-acceptor` does nothing but accept. Every accepted connection gets its own platform thread named `shrike-conn-<n>`, where `n` only ever climbs so that two connections an hour apart cannot share a name. Connections are capped — 64 by default — and at the cap the next socket is accepted and immediately closed, never queued and never left for the acceptor to hold. The count is an `AtomicInteger` moved only through a compare-and-set that refuses to cross the cap, so the cap is exact even between two instructions. Stopping closes the listening socket, wakes every waiting fetch, closes the open connections so their threads come out of their blocking reads, joins those threads under one bounded deadline, and closes every log. Nothing is deleted.

**Alternative rejected.** Virtual threads, one per connection, with no cap because they are cheap. The second alternative was a single non-blocking selector loop.

**Why.** A virtual thread's advantage is that it releases its carrier while it waits, and this broker's waiting is mostly file I/O, which the JDK does not perform asynchronously: a virtual thread blocked in a `FileChannel` read occupies a carrier thread anyway. On Java 21 there is a second, smaller cut — a virtual thread pinned inside a `synchronized` block cannot yield at all, and that was not fixed until Java 24, which is not the platform this codebase targets. What is left of the advantage is thread footprint, which a hard connection cap already bounds, and against it stands something worth more here: a thread dump of this broker reads like documentation, with one named thread per connection and a stack that says what that connection is doing. A selector loop gives up even that, and it turns the fetch long poll from a thread that waits on a condition into a state machine that has to be right about the same thing without ever saying so.

The cap is a resource bound, not a queue-length knob, and closing is the point of it: a client that opens a thousand sockets should cost a thousand closes rather than a thousand threads, and it should cost the acceptor nothing that it can be made to wait for. Sixty-four is a default for a broker on one machine serving a handful of clients — at the default request bound it puts a number on the worst case, 64 threads and at most 256 MiB of request buffers — and it is a constructor argument, so a deployment that knows better says so.

## The ready file holds a port and a pid, and that shape is frozen

**Decision.** Once the logs are recovered, the socket is bound, and the acceptor is running, the broker writes a file with exactly two lines: `port=<the port it bound>` and `pid=<the process it is in>`. It is `java.util.Properties`-parseable, it is written through the same temporary-file-then-atomic-move sequence as everything else here, and stopping does not delete it.

**Alternative rejected.** Printing the port on standard output for a harness to scrape, and writing the file straight to its final name.

**Why.** A broker started on port 0 knows its port and nothing outside it does, so something has to carry that number across a process boundary; a later slice's test harness will start this broker with `ProcessBuilder` and needs both the port to connect to and the pid to destroy. Standard output is the wrong pipe for it: it is interleaved with logging, it has no atomicity, and a harness reading it has to parse prose. A file appearing in one atomic move gives a reader a rule it can rely on — the file is either absent or complete — so waiting for the broker to be ready is a file existence check rather than a guess. Writing in place would break that rule for the sake of one fewer syscall. Leaving the file behind on shutdown means a stopped broker and a crashed one look the same from outside, which is the truth; whoever starts a broker chooses the path and points it somewhere it does not mind overwriting. How the temporary file itself is opened — `<target>.tmp`, without `CREATE_NEW` or `NOFOLLOW_LINKS`, which matters most for a ready file whose directory something else can write to — is tracked in #12.

## A committed offset is the next offset to read, and the client hears about it only after fsync

**Decision.** Committed offsets live in one text file per group, `groups/<groupId>.offsets` under the data directory, keyed by group, topic, and partition from the first commit. **The number stored is the next offset that group should read, not the last one it read.** A commit rewrites that group's whole file through one shared sequence: write a temporary file in the same directory, force it, move it onto the target with `ATOMIC_MOVE`, and force the directory so the rename itself is on the device. The broker answers the client only after all four steps have happened. Committing the high-water mark is legal — it is how a group says it has read everything there is — a negative offset is `INVALID_REQUEST`, and an offset past the high-water mark is `OFFSET_OUT_OF_RANGE`.

**Alternative rejected.** Storing the last offset read, and appending each commit to a log that is replayed at startup rather than rewriting a small file.

**Why.** "Last read" and "next to read" differ by one, and the difference is the empty case: a group that has read nothing has no last offset, so the convention needs a sentinel, and every consumer then has to remember which sentinel and add one in the right place. "Next to read" needs no sentinel — a group that has committed nothing has no entry — and the number a consumer commits is the number it will ask for, which removes an off-by-one from the one place where an off-by-one silently redelivers or silently skips. So the convention is stated in the javadoc, here, and in the field's own name.

Rewriting the whole file is right while a group's offsets are a handful of lines: it costs one fsync per commit against a log's one append plus periodic compaction, and it has no recovery story to get wrong, because the file is either the old one or the new one. An append-only commit log wins when the file is large enough that rewriting hurts, and nothing here is close to that.

The durability is deliberately stronger than what a produce promises, and the asymmetry is the point: a lost produce is a record the producer was never told about, while a lost commit is redelivery of records somebody already handled. The sequence lives in one place, `DurableFile`, which the topic registry and the ready file use too — it sits in the log package because that package already owns this codebase's answer to "when is this durable", from `writeFully` to `ShrikeIOException`. Its steps report themselves as they complete, which is a seam and nothing else: an fsync leaves no trace a JVM can observe, so the only way to prove a caller is told about a write after the write was made durable is to have the sequence say what it did while it did it. Forcing a directory means opening it for reading, which POSIX allows and Windows does not; this build is developed and tested on POSIX systems, and on a platform that refuses, a commit fails loudly rather than quietly promising less than it delivers.

## What a produce promises, said plainly, and where the flush mode went

**Decision.** The broker answers a produce request once the records' bytes have been handed to the operating system through `writeFully`. Nothing is forced. That is the same promise `SegmentedLog.append` has made since Slice 1, and the broker adds nothing to it: ordering and integrity, plus whatever the sealing of a segment already guarantees, and not the survival of a power cut. There is no flush-mode setting in `BrokerConfig`, because there is no flush mode.

**Alternative rejected.** Adding `flush.mode` to the broker configuration now, with `none` as the default, so that the knob exists before anything needs it.

**Why.** A knob with no code behind it is a promise the documentation cannot make. The interesting version of this setting — per record, per interval, or never — is a cost that has to be measured to be chosen, and the slice that measures it is the one that should introduce it, together with the numbers that justify its default. Stating the current promise in one sentence is worth more than a setting whose only value today would be the one it already behaves as. What this entry buys is that nobody has to read the code to find out when a produce is durable: it is durable when the operating system writes it out, and the broker does not know when that is.

## A fetch response carries the log's own bytes, not a re-encoding of its records

**Refined in Slice 5.** The last sentence of the "Why" below made a prediction — that a range of a file, identified without being decoded, is a `transferTo` waiting to happen — and this is the slice that cashed it. `readRange` gained a twin, `Log.openRange`, which locates the same range and opens the file over it instead of copying it out; the walk that decides where the range starts and stops lives once, in `LogSegment`, so the two cannot come to different conclusions about which frames a consumer was promised. What the entry did not anticipate is the other half of the shape. A range that leaves the log has to carry a channel with it, and *who owns that channel* turned out to be the whole of the safety argument, because retention had meanwhile learned to delete the file underneath it. That is settled in "A transfer reads through a channel of its own, so retention can delete under it".

**Decision.** `Log` grew one method, `readRange(fetchOffset, limitOffset, maxBytes)`, which returns whole record frames copied verbatim out of the segment file. The broker puts those bytes into the fetch response without looking inside them. The range starts at `fetchOffset` and stops at the first of: the high-water mark, `maxBytes`, or the end of the segment `fetchOffset` falls in. `maxBytes` yields to the whole-frame rule twice: a frame that would cross the cap is left for the next fetch, and a first frame larger than the cap all by itself is returned anyway.

**Alternative rejected.** Reading `StoredRecord`s through the existing `read(offset)` and encoding them into the response, which needs no new method on the log at all.

**Why.** Re-encoding creates a second path that produces record frames, and two paths that produce the same layout are two paths that can disagree about it — at which point the bytes a consumer checksums are not the bytes the log checksummed. Copying the range keeps one layout, one parser, and one checksum, and it is what makes `WireRecords` able to parse a fetch response with `RecordFrame`, the very code the disk format is frozen against. It is also the shape a later zero-copy slice needs: a range of a file, identified without being decoded, is a `transferTo` waiting to happen, while a list of decoded records is not.

Stopping at a segment boundary is a short answer rather than an error because the alternative is stitching two files together in a buffer to save a client one round trip it can make itself. The first-frame exception is the one place `maxBytes` is deliberately violated: a consumer that asked for fewer bytes than the next record occupies would otherwise be stuck on that record forever, unable to make progress and unable to learn why. Serving it whole bounds the overrun at `max.record.bytes`, which is a number the broker already enforces, and lets the consumer move. The broker also caps what any fetch may be answered with at `max.request.bytes` — the same number that bounds a request — because that is the one setting that says how much memory one connection may make this broker hold, and a fetch asking for two gibibytes is a request for memory like any other.

## The topic registry is one text file, written before the directories it describes

**Refined in Slice 5.** The last sentence of this entry made a prediction and it turned out to be wrong, so it is corrected here rather than quietly left standing. Retention arrived, it does want partitions without wanting sockets, and `Partition` and `TopicRegistry` did **not** move. What retention needed was one method — "delete the segments you no longer keep, as of this millisecond" — and that is a one-method interface, `io.shrike.core.retention.SegmentDeletion`, which `TopicRegistry` implements and which names no partition, no socket, and no segment file. Moving two types into a package of their own to satisfy a dependency that a single interface satisfies would have been a larger change bought for nothing, and it would still have cost the fetch seam its package privacy. The prediction was right that something had to give; it was wrong about which direction it would give in, and a seam this narrow is the cheaper answer.

**Decision.** Which topics exist and how many partitions each has is one file, `topics`, directly under the data directory: a version header line and then one `name partitionCount` line per topic, written through the same `DurableFile` sequence as a group's committed offsets. A create writes that file **before** it opens a single partition log. Partition directories keep the layout the log package already used, `<dataDirectory>/<topic>-<partition>/`. A partition count is fixed when a topic is created, so a repeat create is `TOPIC_ALREADY_EXISTS` whatever count it asks for, the same count included. The registry and the live partitions behind it live in `io.shrike.core.net` beside the broker that owns them.

**Alternative rejected.** Deriving the topic list from the directories on disk, so that there is no registry file to keep in step with them. Opening the logs first and recording the topic afterwards. A separate `io.shrike.core.topic` package.

**Why.** Directories cannot answer the question. A topic with four partitions that has never been produced to looks exactly like a topic with one, because the empty directories are indistinguishable from missing ones — and a partition count that can be inferred wrongly is a partition count that changes under a producer, which is the one thing it must never do. So the count is written down, in the smallest durable form that holds it.

The order matters for the same reason the sealing order mattered in Slice 2. A crash between writing the file and opening the logs leaves a topic listed whose directories do not exist yet, and the next start creates them as it opens them — the file is the truth and the directories follow it. The other order leaves directories that nothing lists: storage no restart accounts for, and a name that a later create would silently adopt along with whatever was in it.

Keeping the registry in `io.shrike.core.net` rather than in a package of its own is a judgement about what these types are. A `Partition` here is not storage — the log package is storage — it is the lock, the condition, and the wait that the fetch api is defined in terms of, and it exists only because connections ask it things. Splitting it out would have bought one package boundary between two types that are never used apart, and it would have cost the fetch seam its package privacy: the test that lands an append inside a waiter's window has to reach that partition, and a public method for it would be a wider surface than the boundary was worth. When retention arrives and wants partitions without wanting sockets, that is the change that should move them.

## `shrike-clients` may name four types from the broker, and this entry is the list

**Refined by the network-layer review.** `SafeName` moved from `io.shrike.core.protocol` to `io.shrike.core.log` — see "One name rule, and it lives where names become paths" — so the list below reads one type shorter on the protocol side and one longer on the log side. Nothing in the client's main code names it either way; what the boundary allows has not changed.

**Decision.** The client library compiles against `io.shrike.core.protocol` — the request and response records, `RequestFrame`, `ResponseFrame`, `WireRecords`, `ApiKeys`, `ErrorCode`, `SafeName`, and `RequestReader`'s default request bound — plus exactly three types out of `io.shrike.core.log`: `ProducedRecord`, `StoredRecord`, and `MalformedFrameException`. Nothing else in the broker is on the client's side of the line: not `io.shrike.core.net`, not `io.shrike.core.group`, not the log itself, not `ByteChannels`. The module's *test* code is allowed the broker, because a test whose subject is a real broker needs a real broker; its *main* code is not.

**Alternative rejected.** A fourth module, `shrike-protocol`, that both the broker and the clients depend on, so that the boundary is compiled rather than described. And, in the other direction, letting the client call `ByteChannels.writeFully`, so that this repository keeps exactly one write loop.

**Why.** The three log types are on the client's side because the codec's own signatures name them: a produce request is built out of `ProducedRecord`s, and `WireRecords.decode` returns `StoredRecord`s and throws `MalformedFrameException` when a block turns out not to be records. A boundary that excluded them would force a client to convert between two identical record types, and the second copy would be free to disagree with the first about what a null key means — which is the same argument that keeps one record layout on disk.

A separate protocol module is the tidy answer and it is not free. `RecordFrame` owns the disk format and lives beside the log that writes it; splitting the protocol out would either move it away from that log or duplicate it. The line is worth drawing now and worth compiling later — when a third thing speaks this protocol, that is the change that should pay for the module.

`ByteChannels.writeFully` is the one place this boundary and PRINCIPLES §5 pull against each other, and the client resolves it by not needing the loop. §5 exists because a NIO `channel.write` may write fewer bytes than the buffer holds and leave half a frame on the wire; `OutputStream.write` cannot do that — its contract is that every byte is written or an exception is thrown. So the client has no short-write loop rather than a second, more forgiving copy of one, and the surface stays four types wide.

## The client reads an answer the way the broker reads a request, and numbers its own questions

**Decision.** `BrokerConnection` owns one socket and carries one call at a time. It assigns correlation ids from 1 upwards, and reads every answer through the guard `RequestReader` uses pointed the other way: read exactly four bytes, believe the length only inside `[ResponseFrame.MINIMUM_LENGTH_BYTES, maxResponseBytes]`, and allocate nothing until it does. `maxResponseBytes` defaults to the broker's own `max.request.bytes` — 4 MiB, the cap the broker serves a fetch under — plus a kibibyte of envelope headroom, and it is a configuration field, so a client pointed at a broker with a larger bound says so rather than meeting it as a broken frame. An answer whose correlation id is not the one that was sent, a body that does not parse, and an error code carrying a body are all the same verdict: this connection cannot be believed, so it is closed. A broker error code is not — it is an answer, and the connection stays usable after one. The socket is a `java.net.Socket` with a connect timeout and `SO_TIMEOUT`, and a fetch's `SO_TIMEOUT` is its own `maxWaitMs` plus the configured margin rather than a fixed number.

**Alternative rejected.** Trusting a length because the broker is what wrote it, and matching answers to requests by the order they arrive in. A `SocketChannel`, which is what the broker's own side of this wire uses, with one blocking read after another. One read timeout covering every api, fetch included.

**Why.** A client is not a privileged reader. The thing on the other end of the socket is whatever answered on that port, and four bytes from it can ask for two gibibytes just as easily as four bytes from a client can ask the broker for them. The guard is the same shape on both sides because the hazard is the same on both sides, and the cap is stated as a number a deployment can change rather than derived from a constant the broker might not share.

Order as identity would work today, because this connection has one call in flight. It would stop working the first time it did not, and it would stop working silently: the answer to the previous question would be read as the answer to this one. The correlation id costs four bytes and turns that into a check, and a check that fails is not a request that failed — it is a client that has lost its place in the stream, which is why it closes the connection instead of raising an error the caller could retry.

A `SocketChannel` is what the broker uses and it is the wrong tool here: a blocking channel read cannot be bounded, because `SO_TIMEOUT` applies to a socket's streams and not to a channel's reads. A client that must be able to say "the broker did not answer" needs that bound. The margin is the other half of it. One flat timeout means that raising a fetch's `maxWaitMs` above it turns a long poll the broker is serving correctly into a client-side timeout, and the caller who raised it has to know to raise a second, unrelated number. Adding the wait to the margin makes the client's bound follow the request's own wait, and the margin keeps its plain meaning: how long the broker gets to answer once it has stopped waiting. A read that does time out closes the connection, because the answer it gave up on may still be on its way, and a reused connection would read it as the reply to the next request.

## Creating a topic is a client of its own

**Decision.** `ShrikeTopics.create(name, partitionCount)` in `shrike-clients`, an `AutoCloseable` of its own over its own connection.

**Alternative rejected.** A `createTopic` method on `ShrikeProducer`, which is where the caller that needs it already is. A single `ShrikeAdmin` type collecting everything that is neither produce nor fetch.

**Why.** A producer exists for as long as there is something to send; a topic is created once, usually by whoever sets a deployment up and often from a different program entirely. Putting the two behind one type would mean every producer carries a method it must never call twice, and it would make the first thing a reader learns about producing be a sentence about topics. Splitting them costs one small class and buys each of them one reason to change.

`ShrikeAdmin` would be a name for "the rest", and the rest is one method. The types this repository bans — `Manager`, `Helper`, the grab-bag `Processor` — are banned because they are named after their own vagueness, and a type named after what it is not would be the same mistake with a better-looking word. When describing topics and describing groups arrive, they arrive next to `create` in a class already named after the thing they are about.

## The flagship test is five processes, a ready file, and a killed process tree

**Decision.** `ClientProcessIT` starts a broker, two producers, and two consumers as separate operating-system processes with `ProcessBuilder`, using the `java` of the JVM running the test and the classpath it was given. It learns the broker's port by waiting for the ready file under one deadline with a short poll interval, speaks to the broker through the client library, reads every process's exit code with a bounded `waitFor`, and parses `field=value` lines out of each process's redirected output. An `@AfterEach` destroys every process it started — descendants first, then the process itself, forcibly, under a bound — on every outcome, including an assertion failure and a wait that gave up. `maven-failsafe-plugin` runs it, pinned to the version surefire is pinned to, so that the `*IT` name keeps it out of the fast unit loop and `verify` is what fails on it. The resume half of the flow reads the committed offsets out of the broker's own `groups/<groupId>.offsets` file and starts the replacement consumer process from them.

**Alternative rejected.** Threads in the test JVM, which is what every broker test in `shrike-core` already uses and what is cheapest to write. Scraping the port from the broker's standard output. Handing the replacement consumer the offsets the first consumer said it committed. Cleaning up in a `finally` inside the test method.

**Why.** Threads share a heap, and a heap is the one thing a client and a broker must not share. A client that reached past the protocol — held a reference to a partition, read a field it should have asked for — would still pass a test that ran both in one JVM, and would fail the first real deployment. Here the only things that cross a boundary are a TCP socket, a file, an exit code, and lines of text, so what the test proves is that the protocol carries the meaning.

The ready file is the port's only way out of a broker started on port 0, and it appears in one atomic move, so a reader either sees the whole file or no file. Standard output has neither property: it is interleaved with log lines and it arrives a character at a time. Waiting for the file is the one place this repository polls, because there is no lock to hold and no condition to signal across a process boundary — so the poll lives in one helper, with an absolute deadline, a short interval, and a failure that quotes the broker's own output, and it gives up early if the broker process has already died.

Reading the committed offsets out of the broker's file rather than trusting what the first consumer printed is what makes the resume worth testing. The numbers the replacement starts from are then the numbers the broker stored, so a commit the broker acknowledged and lost fails this test; if the consumer's own output were passed along, the second half would prove only that a consumer can be told where to start. There is no api that reads a committed offset back in this build, and that is the honest reason a file is read at all — the *test* knows a format that DESIGN.md fixes, while the client library still knows only the protocol.

Destroying the tree is not tidiness. A leaked broker holds a port and a data directory, and the next run of the same test would meet it; a leaked child of a child is a process nothing has a handle on at all. `descendants()` before `destroyForcibly()` covers the second, and running the destruction from `@AfterEach` rather than a `finally` inside the test covers the first for every path — including the ones nobody remembered to wrap, which are exactly the paths a failing test takes.

## A topic name and a group id are case-insensitive, because the paths they name are

**Refined by the security re-review.** The fold decided the name a group's file is *written* under and said nothing about a file already sitting in that directory under another casing, which turned a routine restart into a permanent, loud failure. A data directory holding `Readers.offsets` — from an unreleased build of this branch, or from something else that wrote into it — opens, and then the first ordinary commit writes `readers.offsets` beside it on a case-sensitive filesystem; from that moment every start refuses with "names one group twice", and nothing in the tree can repair it. So opening the store now renames a file whose name is not folded onto the folded one, durably and through the same machinery a commit uses: one `ATOMIC_MOVE` and then the directory forced, which is `DurableFile.rename` — the last two steps of `DurableFile.replace` and none of the others, because the bytes are already on the device. After the rename, memory and disk agree everywhere, and a WARN names the file that was renamed and why. The genuinely ambiguous case — both casings present at once — still fails the start, and its message now spells out the repair a human has to make: keep whichever of the two holds the offsets that group should resume from, name it `<folded id>.offsets`, and remove the other.

**Alternative rejected.** Refusing that single unfolded file too, and demanding the same manual repair for it. It is the tidier rule, and it charges the wrong person. One file under one casing is not ambiguous: there is exactly one set of committed offsets and exactly one name this build stores them under, so the only thing a human would add is the typing. Refusing would also turn a fold introduced to prevent silent data loss into a broker that will not start over a directory it can read perfectly — the same failure mode the recovery entry above rejected for a torn tail, arriving for a file that is not even damaged. Ambiguity is where a refusal belongs, and the colliding pair is the only ambiguity there is.

**Decision.** A topic is held under `SafeName.fold(name)` — the name lowercased with `Locale.ROOT`, which for the ASCII the name rule allows is exactly a case fold — and so is a consumer group. `orders` and `Orders` are one topic: a create whose name folds onto a topic that is already here is `TOPIC_ALREADY_EXISTS`, and a produce, a fetch, or a commit naming any casing reaches the one topic that exists. The topic keeps the spelling it was created with, because that is what the registry file lists and what its directories are named. A group's *file* takes the folded id, `groups/<folded group id>.offsets`, since a group has no registry and its file name is its identity; the topic inside a group's offsets is folded too, so a commit and the fetch that follows it cannot key the same partition two ways. A registry file listing two names that fold together, or a groups directory holding two files that do, fails the start with a message naming both.

**Alternative rejected.** Case-sensitive names, plus a documented requirement that this broker runs on a case-sensitive filesystem. The other alternative was folding only the create-time guard and leaving lookups exact.

**Why.** A partition's identity on disk is `<dataDirectory>/<topic>-<partition>/`, and on APFS and on Windows that directory name does not tell two casings apart. So `create("orders")` followed by `create("Orders")` used to give two `Topic` objects with two locks, two `SegmentedLog`s, and two open channels over the same segment file — two writers that hand out the same base offsets and overwrite each other's acknowledged records. The rule that closes it is one sentence: a name's identity must be at most as fine-grained as the identity of the path it becomes. Since the coarsest filesystem this could run on folds case, the fold is where identity is decided, on every filesystem, so the behaviour a test proves on Linux is the behaviour macOS gets.

Requiring a case-sensitive filesystem is the alternative that costs nothing to write and everything to rely on: it is a condition no code checks, that a developer on macOS breaks by existing, and whose failure mode is silent data loss rather than a refusal. Folding the guard but not the lookup is worse than either: the broker would answer "that topic already exists" to a create and "no such topic" to a produce naming the same string, which is two different truths about one name.

The cost is stated plainly: two topics that a case-sensitive filesystem could have kept apart can no longer both exist, and a name is echoed back in the spelling it was created with rather than the spelling a caller used. That is the same trade every case-insensitive namespace makes, and it is a refusal at create time rather than a surprise at read time.

What the fold settles is APFS-style case-insensitivity, and that is the whole of the claim. Windows is named above for the shape of its path identity rather than as a platform this build runs on: Win32 folds more than case — `nul`, `con`, `aux`, and `com1` are reserved device names, and `SafeName` admits all four — so a Windows port would need a rule about those as well. It is out of reach today in any case, because forcing a directory means opening it for reading and Windows refuses that, which the committed-offsets entry above already states as a loud failure rather than a quiet one.

## A fetch's wait and its `minBytes` are clamped to what this broker can serve

**Decision.** `BrokerConfig` grew `maxFetchWaitMs`, 30 seconds by default, and a fetch's wait is `min(maxWaitMs, maxFetchWaitMs)`. Its `minBytes` is clamped too, to `min(maxBytes, max.request.bytes)` — the most bytes that fetch could ever be answered with. Both clamps are pure functions on `Partition` with tests of their own. While waiting, a wakeup that finds the high-water mark exactly where the last read left it waits again without re-reading the log.

**Alternative rejected.** Refusing an out-of-range `maxWaitMs` or `minBytes` as `INVALID_REQUEST`, and leaving the read on every wakeup because it is simple and obviously correct.

**Why.** Both numbers are int32 fields a client fills in, and the codec only refuses them for being negative — as it should, since neither is a statement the bytes can be wrong about. Taken at face value, `maxWaitMs` of `Integer.MAX_VALUE` parks a connection thread and its slot under the connection cap for about twenty-five days, so 64 of them are the whole broker. A `minBytes` above what can be served is worse than long: it is a predicate no append can satisfy, so the fetch sleeps out its entire deadline while the records it asked for sit readable on disk. Clamping turns both into what they always were — a caller's preference, met as far as the broker is willing — and it keeps a well-behaved client's request untouched, which refusing would not. Refusing would also break a client that raised `maxWaitMs` for a reason, at the moment it needed the answer, and it would put a number the operator can change into the protocol's error surface where it does not belong.

The skipped re-read is the other half of the fix and it is small: bytes readable from a fixed offset can only change when the high-water mark moves, and nothing in this build removes records. Without it, one tiny produce woke every waiter on the partition into a full `readRange` of up to `max.request.bytes` — 63 waiters re-reading 4 MiB each to discover they still could not be filled. What is *not* fixed, and is worth naming: the waiters that do read still read one after another under the partition lock, because that lock is what makes the log a single writer. Cutting that cost means serving many fetches from one read, which is a change to how a fetch is answered rather than to when it wakes up.

## The partitions a broker will open are budgeted

**Decision.** `BrokerConfig` grew `maxTotalPartitions`, 1024 by default. A create that would push the number of open partitions past it is refused with `INVALID_REQUEST`, counted across every topic and enforced under the same lock that makes a create atomic. A registry that already lists more than the budget still opens every partition it lists, and says so in a WARN; the budget stops the next create instead.

**Alternative rejected.** Leaving the per-request cap of 1024 partitions as the only bound. Refusing to start when the stored partition count is past the budget.

**Why.** The per-request cap bounds one request and nothing else: a thousand creates of a thousand partitions each is a million directories, two open file handles apiece, and the process meets `EMFILE` long before that. What arrives then is not a bad answer to a create — it is `accept()` failing on the acceptor thread, connections that cannot be served, and a broker that is up and useless. A budget makes the same limit arrive as a refusal that names the number it crossed, at the request that asked for it, while the broker is still healthy. Both numbers earn their keep: one create still cannot ask for more than the whole budget, and the budget is what makes many creates add up to something bounded.

Refusing to start over a stored count past the budget was the tempting symmetry, and it is the wrong call. Those partitions were created under whatever budget was configured at the time, their records are acknowledged records, and lowering a number in a config file should not turn a broker's data directory into one it will not open. Opening what exists and refusing what is new keeps the budget a bound on growth rather than a retroactive verdict, and the WARN is what keeps that from being silent.

What is *not* budgeted is the number of consumer groups: partitions, connections, request bytes, and fetch waits all have a number, while every distinct group id creates a `groups/<id>.offsets` file and an in-memory entry that outlive the connection that committed and survive a restart. Tracked in #11.

## One name rule, and it lives where names become paths

**Decision.** `SafeName` moved from `io.shrike.core.protocol` to `io.shrike.core.log`, and `SegmentedLog`'s own `[a-zA-Z0-9._-]{1,249}` pattern is gone: opening a log calls `SafeName.require(topic, "topic")`. One rule, one place, applied by the protocol as a request is decoded and by the log as a path is built.

**Alternative rejected.** Leaving the copy in `SegmentedLog` alone, since it was stricter than the filesystem and nothing had gone wrong. Making `SegmentedLog` import `io.shrike.core.protocol.SafeName` where it stood. A package of its own for one class.

**Why.** The two rules had already drifted: 249 characters in the log against 200 in the protocol, which is a name the log would accept and the broker would refuse, and a difference nobody would notice until a name landed between the two numbers. That is what a second copy of a rule is for — being more generous than the first — and the fix is to have one rather than to keep them in step by hand.

Where it lives is decided by which import would be a cycle. `io.shrike.core.protocol` already depends on `io.shrike.core.log`, because `WireRecords` parses the very frames `RecordFrame` writes, so a log that imported the protocol would close a loop between two packages. Pointing the dependency the other way costs nothing and reads better than the accident it replaces: the log package is where a name becomes a path — `<dataDirectory>/<topic>-<partition>/` is built there — and it is already where `DurableFile` and `ByteChannels` live for the same reason. A package holding one final class with two static methods would be a boundary drawn for tidiness, and this repository already decided that question when `DurableFile` went into the log package rather than into one of its own.

## Loopback only, no authentication, and no read timeout yet

**Decision.** The listener binds `InetAddress.getLoopbackAddress()`. There is no authentication, no authorization, and no transport security, and the bind address is not configurable. There is also no server-side read or idle timeout: a connection that opens and then says nothing holds its slot under the connection cap until it is closed or the broker stops. This entry, the README, and the `ShrikeBroker` class javadoc all say so.

**Alternative rejected.** A configurable bind address now, defaulting to loopback. A read timeout implemented with `SO_TIMEOUT`.

**Why.** A bind address is one line of code and a promise this build cannot keep: the moment it is configurable, somebody sets it to `0.0.0.0`, and what is on the other side of that port is a broker that will append whatever it is sent by whoever can reach it. The knob belongs to the slice that makes exposure defensible — authentication first — and until then the loopback bind is the access control. What the review asked for, and what this entry is, is that the fact lives somewhere a reader finds it before deployment rather than only in a class javadoc.

The idle connection is an accepted, deferred exposure and is named as one. `SO_TIMEOUT` is not the tool: it bounds reads on a socket's *streams*, and the broker reads through a `SocketChannel`, whose blocking reads it does not bound at all — which is the same asymmetry the client entry describes from the other side. A real fix is a reaper thread that closes connections idle past a configured bound, with the bookkeeping to know what "idle" means for a fetch that is legitimately waiting 30 seconds. That is a slice's worth of work, and today the controls are the two this build does have: the loopback bind, so only a local process can hold a slot, and the connection cap, so the number of slots that can be held is a number rather than a hope. Both deferrals — the configurable bind address and the read or idle timeout — are tracked in #9.

## A key picks its partition on the client, and CRC32C is what picks it

**Decision.** Routing lives in `shrike-clients`. `PartitionRouter.partitionOfKey(key, partitionCount)` is `Math.floorMod((int) crc32c(key), partitionCount)`, and a record with no key takes each partition in turn starting at 0. A caller that names a partition is obeyed whatever its key would have hashed to: `ShrikeProducer.send(topic, partition, key, value)` is that path and it is unchanged. The broker does not route — a produce request has always carried an explicit partition and still does, so nothing about this decision is on the wire. The mapping is pinned by a table of literal vectors in `PartitionRouterTest`, for two partition counts, one a power of two and one not.

**Alternative rejected.** Routing on the broker, so a client could send a key and let the side that knows the partition count decide. A murmur-style hash, which is what a partitioner usually reaches for. A test that hashes the keys itself and checks the modulo it computes.

**Why.** Routing on the broker would be a protocol change — a produce that names no partition — and it would move a decision that belongs to whoever chose the key onto the one component that has to stay simple: the broker's produce path is a single writer per partition and knows nothing about keys, groups, or members, and every entry in this file that keeps it that way is worth more than the convenience. It would also make the partition a record landed on depend on the broker's build rather than on the sender's, which is the failure this decision is trying to avoid, only harder to see.

CRC32C is not the best-mixing hash available, and it is the right one here. It is already a dependency of the record frame — every stored record carries a CRC32C, `java.util.zip.CRC32C` ships with the JDK, and the hardware runs it — so choosing it adds no code to write, no code to test, and no second thing to freeze. A murmur-style hash would have to be implemented and then defended byte for byte forever, in a repository whose core depends on the JDK alone. What a partitioner needs is a spread across a handful of buckets, not resistance to somebody choosing keys to collide; `PartitionRouterTest` asserts that 400 keys reach all four partitions, and that is the property being bought. `Math.floorMod` rather than `%` because a CRC32C read as an `int` is negative for about half of all keys, and `%` would answer those with a negative partition.

The vectors are literals because a test that hashes the keys the same way the code does agrees with every rule, including a rule that changed between two releases. A changed mapping is not a loud failure: the records already stored stay where they are, the new ones go somewhere else, and one key's history is quietly split across two partitions with its order gone. Freezing eight keys, four raw byte arrays, and two partition counts costs twelve lines and turns that into a failing build.

## A member's partitions are arithmetic, and nothing rebalances them

**Decision.** A consumer group member is configured with three numbers — `GroupAssignment(groupId, memberIndex, memberCount)` — and owns the partitions where `partition % memberCount == memberIndex`. That is the whole assignment. The broker stores committed offsets keyed by group, topic, and partition, and nothing else: no members, no sessions, no heartbeats, no generations. A `memberCount` below 1, or a `memberIndex` outside `[0, memberCount)`, is refused where it is configured with a message naming both numbers. A group with more members than the topic has partitions is allowed, and the members past the last partition own nothing. A member that dies is replaced by a process started with the same index and count, which resumes from the last offset that index committed.

**Alternative rejected.** A coordinator on the broker: members register, heartbeat, are given partitions, and are declared gone by a session timeout. Letting a member discover the partition count from the broker rather than being told it.

**Why.** Dynamic rebalancing is a stated non-goal of this build, and this is what that non-goal costs and buys. A coordinator is not one feature: it is registration, heartbeats, a session timeout, a generation number, and a fencing rule for the member that was declared dead and comes back mid-batch anyway — and every one of those is a way for records to be delivered twice or not at all, on the broker, where this repository has been keeping the number of moving parts down on purpose. Arithmetic needs no state on either side, survives every process being restarted, and can be checked by reading two numbers off a command line.

What it costs is said plainly rather than hidden. The partitions of a member that is not running are read by nobody until an operator starts one with that index again — there is no other member that picks them up. Changing the size of a group means restarting its members with a new `memberCount`, and while that is happening the group is briefly inconsistent about who owns what. And two live processes configured with the same index is a mistake nothing here can detect, because nothing here talks to the other process: they read the same partitions and both commit, so records are processed more than once. That is the failure direction this design chooses — extra redelivery, which at-least-once delivery already allows, rather than a record nobody read. Fencing the second process would need exactly the broker-side membership this entry is refusing.

The partition count is a number the caller passes rather than one the client asks for, because this build has no api that describes a topic. A member is told the same three or four numbers a producer is told, and when a describe api arrives it can fill them in without changing what an assignment means.

## Records are processed before the offset that covers them is committed

**Decision.** `ShrikeConsumer.processThenCommit` hands records to a `RecordHandler` and commits the offset to read next — one past the last record handed over — only after that handler has returned. A handler that throws is not caught: the exception reaches the caller and nothing is committed, so the same records are read again. An empty list commits nothing at all. How many records go into one call is the caller's choice, so a commit can cover part of what one fetch answered with, and the records that were not handed over are simply read again next time.

**Alternative rejected.** Committing as soon as the records are handed over, or as soon as a fetch answers. Catching the handler's failure and committing anyway so the group keeps moving. Committing on a timer in a thread of the library's own.

**Why.** Every ordering here is a choice between doing work twice and never doing it at all, and this build has said which one it takes since its first README line. Committing first turns a process that dies mid-batch into records that nobody processed, that no consumer will ever be handed again, and that nothing in the system will report — silent loss, which is the one outcome a log-structured broker exists to prevent. Committing after means a process that dies between the work and the commit does that work again when it is replaced: duplicates are possible, and no record is lost. The cost is real and it is the caller's to handle — the offsets a handler is given are what an effect can be keyed on to make repeating it harmless.

Swallowing the handler's exception is the same trade wearing a disguise: the group moves on, the records are gone, and the only sign is a log line. A timer is worse than either, because it decouples the commit from the work entirely — the offset moves while a slow handler is still in the middle of the batch, and what is lost depends on the clock.

## The redelivery test kills a member that is holding work it never committed

**Decision.** `ConsumerGroupRedeliveryIT` runs five operating-system processes: a broker, a producer that lets a `PartitionRouter` place 40 keyed records over 4 partitions, the member that is killed, the member started in its place with the same index, and the group's other member. Each member writes one line per record into a journal of its own and forces that line to the device *before* the record counts as processed, and hands records over four at a time, which is what commits them. The member that is going to die is told to pause at one partition and offset: it journals that record and then waits on a latch nobody counts down. The test tails its journal for that exact line under a bounded await and only then calls `destroyForcibly()`. The replacement is started from the offsets read out of the broker's own `groups/<groupId>.offsets` file. The assertions are over the multiset union of the journals: every record produced appears at least once, every record the killed member journaled past its last committed offset appears twice, the replacement's journal for each owned partition is exactly the offsets from the stored commit to the high-water mark, and no partition appears in two members' journals. Two of the assertions exist only to stop the test passing on an empty run: the produced set is non-empty, and so is the set of records that came twice.

**Alternative rejected.** Killing the member after a delay, or after counting N records go by, and hoping the kill lands inside a batch. Asserting on what the member printed to standard output rather than on what it forced to a device. Starting the replacement from the offsets the killed member said it had committed.

**Why.** A kill that is timed is flaky in both directions and the bad direction is silent: land it a moment late and the member has committed everything it journaled, the redelivered set is empty, and every "appears at least once" assertion still passes over a test that proved nothing. The pause turns the kill point into a place in the data — when that journal line exists, the member has, provably, journaled two records past a commit the broker acknowledged, and it can no longer commit them because it is parked. From then on the test can take as long as it likes.

The journal is fsynced per line because SIGKILL runs no shutdown hook and flushes no buffer: what is on the device is the whole of what that process can be said to have done. Standard output would be a claim about intent — a `println` that never reached the file proves nothing about work that was done, and one that did proves nothing about work that was durable.

Reading the broker's group file rather than the dead member's own output is the same argument `ClientProcessIT` makes: the numbers the replacement starts from are the numbers the broker stored, not the numbers a dying process claimed. It does not follow that this test would catch a commit the broker acknowledged and then lost — the expectations here are derived from the same file the replacement is handed, so a lost commit moves the expectation and the observation together and the assertions still hold. `ClientProcessIT` is the test that catches that, because it pins the committed offsets it expects as literals. There is still no api that reads a committed offset back in this build, which is why a test reads a file whose format this document fixes.

## Retention deletes whole sealed segments, aged by the timestamps inside them

**Decision.** `LogConfig` grew `retention.ms` and `retention.bytes`, both `long`, both defaulting to −1, which means "no bound" and deletes nothing. `retention.ms` deletes a sealed segment once **the largest record timestamp that segment holds** is at least that many milliseconds behind the moment retention is evaluated at. `retention.bytes` then deletes the oldest sealed segments, one at a time, until the log files of that partition add up to no more than the bound. Only whole sealed segments are ever deleted, and the segment still taking appends is never one of them — a partition of one segment deletes nothing, whatever its age or size — so a partition can legitimately sit above `retention.bytes` by the size of that one segment, and this is stated in the README rather than rounded off.

The largest timestamp is tracked as the segment fills, and it is fixed when the segment is sealed. A segment reopened as sealed at startup has nothing to remember it from, because nothing writes it down: it reads the timestamp back out of the log file, and out of the **last frame** of it. That read costs a lookup in the sparse index for the position of the last indexed record and then a walk of at most `index.interval.bytes` of frames, so it is bounded by the index interval rather than by the size of the segment. A segment whose last frame cannot be believed reports no timestamp at all, and a segment with no timestamp is one time-based retention keeps.

**Alternative rejected.** Aging a segment by the file's modification time, which the operating system already keeps and which needs no read at all. And, for the age itself: the *first* record's timestamp, so a segment expires once its oldest record is old enough. Also considered: writing the largest timestamp into a small per-segment metadata file so a restart could read it in one syscall.

**Why.** A modification time is a fact about this copy of these bytes, not about the records in them. Restoring a partition from a backup, copying a data directory onto a new machine, or a filesystem that updates the time for a reason of its own would all reset every segment's apparent age to now — so a broker that trusted mtime would keep a week of data forever after a restore, and, worse, the same trust points the other way: a tool that preserved mtimes across a copy could make a freshly restored partition look ancient and have retention delete all of it on the first sweep. The timestamps are already in every frame, written from the injected `TimeSource`, and they say when the record was produced, which is the thing `retention.ms` is actually about. `SegmentedLogRetentionTest#datesAReopenedSegmentFromItsLastRecordRatherThanFromTheFilesOnDisk` sets every file's modification time to the instant the test runs and then proves the segments are still deleted, which is a test that fails the moment anybody reaches for `Files.getLastModifiedTime`.

Judging a segment by its oldest record would delete records inside their retention window: the segment holding offsets 0 and 1 goes as soon as offset 0 is old enough, taking offset 1 with it. The bound has to hold for every record in the unit being deleted, and the newest record is the only one that speaks for all of them.

Reading the last frame rather than remembering the number in a metadata file keeps the log the single source of truth, the same rule the offset index already follows: a number stored beside the data is a second copy that can disagree with it, and after a torn tail or a truncation it would disagree exactly when it mattered. The cost is one bounded walk per sealed segment at startup, which is the same order of work the index check beside it already does.

Defaulting both bounds to off is the last piece and it is not timidity. Retention is the only thing in this broker that deletes acknowledged records, so it deletes none of them until somebody has said, in a configuration file, how many and for how long. A default that kept a week or a gigabyte would be this document choosing what a user's data is worth. `LogConfigTest#keepsEveryRecordUntilRetentionIsAskedForByName` is the proof that a log opened without naming retention behaves exactly as it did before this slice existed.

## Deleting a segment: the start offset first, then the list, then the files

**Decision.** One deletion is three steps and the order is the whole of it. First `logStartOffset` — a volatile field on `SegmentedLog`, not a walk of the segment list — advances to the base offset of the segment that follows. Then that segment comes out of the in-memory list. Only then are its two files unlinked. A read below `logStartOffset` is refused with `OffsetOutOfRangeException` carrying that offset, and it is refused whether or not the file is still on disk.

**Alternative rejected.** Deleting the files first and letting the list and the start offset catch up, which is the order most naturally written. And, for readers already inside a file: copying each segment away, or reference-counting open readers and deferring the unlink until the last one is done.

**Why.** The two failure shapes are different sizes. Take the files away first and a reader that is part way through the segment list can find a segment that names a file which is no longer there, and the answer it gets is an I/O error about a missing path — a broker failing on its own housekeeping. Advance the offset first and the worst a reader can meet is the refusal it was always going to meet, one moment early, carrying the number it needs to carry on. The field is volatile for exactly that reason: the ordering is only worth anything if a thread that sees the shortened list cannot also see the stale offset beside it.

Reference counting is the part that is not needed, and POSIX is why. `unlink` removes a name from a directory; the inode and its blocks survive until the last open file descriptor on them is closed. A fetch already inside a segment therefore reads on to the end of what it asked for, from the file it opened, and gets whole frames that still checksum — the space comes back when it closes. That is not a claim taken on trust here: `SegmentedLogRetentionTest#readsASegmentWholeThroughAChannelOpenedBeforeRetentionDeletedIt` opens a channel, reads one frame through it, deletes the segment under it, reads the next frame through the same channel, and asserts the bytes match what was on disk before the deletion and still decode to the records they were. Copying a segment aside before deleting it would double the disk cost of retention to buy the property the filesystem already provides.

## Retention is one named thread, and it takes the partition's own lock

**Decision.** A thread named `shrike-retention` — one, for the whole broker — asks the topic registry to delete what it no longer keeps, once every minute. Between sweeps it waits on its own stop signal, a latch the broker counts down as it shuts down, rather than sleeping: the predicate is "this sweep is stopping", so a shutdown ends the wait at once instead of after the rest of an interval, and stopping the broker waits for a sweep in flight before any log is closed. The sweep itself is `RetentionSweep.runOnce()`: one synchronous method that reads the injected `TimeSource` once and does the whole decision on the calling thread. Deletion enters a partition through `Partition.deleteRetiredSegments`, under the same `ReentrantLock` that every produce and every fetch of that partition takes. A sweep that throws is a WARN and the thread lives; a partition that cannot be trimmed is a WARN and the sweep moves on to the next one.

**Alternative rejected.** A retention thread per partition. A `ScheduledExecutorService`. Doing the work on the appending thread, after the append that rolled a segment. And, for the lock: a second lock owned by retention, or a lock-free hand-off in which retention only marks segments and the next reader removes them.

**Why.** `SegmentedLog` says plainly that nothing in it is safe to call from two threads at once, and the segment list retention shortens is the same list a fetch walks. A second lock would be a second answer to who may touch that list, which is the shape of every concurrency defect that survives review. Taking the partition's own lock means retention is not a new concurrency story at all — it is one more caller taking its turn, and what it holds the lock for is a couple of file closes and an unlink rather than a read of the log, so a sweep is not a pause a connection can feel. Marking and deferring would move the deletion onto a connection thread, which is the one thread whose latency this broker is trying to protect.

One thread rather than one per partition, and rather than an executor, because the work is a walk of a handful of partitions once a minute: a thread per partition would be a thread per partition asleep, and an executor would be a pool and a queue in a place where the queue can only ever hold one thing. One named thread is also the only one of the three that a thread dump explains — PRINCIPLES §4 reserves the name, and `RetentionSweepTest#sweepsOnItsOwnNamedThreadUntilItIsClosed` proves the sweeping thread carries it and that closing ends it.

Splitting the decision out as `runOnce()` is what keeps the tests honest. Every retention test in this repository advances an injected clock and calls the sweep by hand; not one of them waits for a minute to pass, because how often production asks is not what retention means. The interval is a constant rather than a setting for the same reason a knob with no code behind it was refused earlier: nothing yet needs to tune it, and a partition that sits over its bound for up to a minute is what a bound on storage costs.

## Offset out of range is the one error that carries a body

**Decision.** An error response is still a code and an empty body, for eight of the nine codes. `OFFSET_OUT_OF_RANGE` — code 2 — now carries an eight-byte int64 body: the offset that partition can still be read from. The encoder and the decoder are symmetric about it and both are exact. `ResponseFrame.encodeError` refuses code 2 outright and points the caller at `encodeOffsetOutOfRange`, so a code 2 with no body cannot be written; the decoder refuses bytes behind any other code, refuses a code 2 whose body is not exactly eight bytes, and hands the number back as an `OptionalLong` that is present when and only when the code is 2. It reaches a caller of the client library as `BrokerErrorException.logStartOffset()`. No api key was added and no operation was added: keys 4 and 5 stay reserved and unimplemented.

**Alternative rejected.** Leaving the code as the whole answer and letting a consumer that has fallen behind retention guess — start again from 0, or skip to the end. A new api key that asks a partition for its offset range. Putting the number in the fetch *response* body instead, so that no error carries anything.

**Why.** Retention is what made the old rule insufficient. Before this slice a fetch was only ever out of range past the high-water mark, and a consumer that got there knew what to do: it had just been told the mark. Below the range was unreachable, because nothing deleted anything. Now a consumer whose committed offset was deleted while it was down gets code 2 and, without a number, has two choices that are both wrong — re-read everything that survived, or skip records that are still there. Neither is a decision it can make; both are decisions it would be guessing at. Eight bytes turn it into a decision its author makes with the number in hand.

The reasoning that kept error bodies empty still holds everywhere else, and this exception does not weaken it. What that rule protects against is a broker describing its own internals to whoever is probing it: which field a parser choked on, which of its files was unreadable. A log start offset is not that. It is the oldest offset the broker will serve to anybody who asks for it, so a caller learns nothing from the error that a legal fetch would not have told it a moment later.

A new api key would be the tidier-looking option and it costs a round trip on every occurrence of the case it exists for — and the case is a consumer that is already behind. It would also leave the same client able to receive a bare code 2 from a broker that had not been asked, which is the ambiguity this change removes. Putting the number in the fetch response was rejected because there is no fetch response: the request was refused, and inventing a success-shaped answer for a refusal would mean a client had to inspect a body to find out whether it had been served. The decoder's exactness is what keeps the wire honest either way — a frame that breaks either half of the rule is refused rather than half-read, which `ResponseFrameTest#refusesAnOffsetOutOfRangeResponseWithoutItsLogStartOffset` and `ResponseFrameTest#refusesAnErrorResponseThatCarriesABody` prove from both sides.

## A fetch's records go from the segment file to the socket, and one setting takes that back

**Decision.** `BrokerConfig` grew `fetch.zero.copy`, on by default. With it on, a fetch reaches the wire in two writes rather than one: `ResponseFrame.encodeFetchHeader` lays out the length field, the correlation id, the code, the high-water mark, and the size of the records block — the length already counting every record byte to come — that header goes out through the same `writeFully` every other frame uses, and then `FileChannel.transferTo` sends the record frames themselves out of the segment file, looping until the byte count the header promised has gone. With it off, the range is read into a buffer and written as one frame, which is what this broker did before the setting existed. Both paths ask `LogSegment` for the same range, located by one walk in one place, and `Partition.readable` is the only method the setting reaches.

**Alternative rejected.** Two settings, one for the fallback and one for the benchmark. Making the transfer unconditional and keeping no way back to the buffered path. And, for the shape of it: passing the choice down through `Partition` and `Connection` as a boolean argument.

**Why.** One setting does both jobs because both jobs want the same thing: the older path, unchanged, one restart away. A fallback that shares its new code with the thing it is falling back from is not a fallback, so `fetch.zero.copy=false` selects the path that was already there rather than a variant of the path that replaced it — the buffered read still goes through the segment's own channel and still allocates the array it always did. The A/B of the benchmark sub-slice is the same switch for the same reason: measuring a difference means running one broker twice with one thing changed, and that one thing has to be the whole of the difference. This is not the knob-with-no-code-behind-it that the flush entry refused, either; both paths ship with the setting, and each is proven by the same tests as the other.

The boolean never becomes an argument, because PRINCIPLES §2 bans that and because the alternative is better anyway: instead of a flag travelling with the data, the data got a shape. `Partition.fetch` answers with a `FetchedRecords` that is either `Copied` or `Pinned`; `Answer` gained a `Streamed` beside `Served`; and `Connection`'s switch over `Answer` will not compile if a shape is forgotten. Two small sealed variants buy a connection loop that cannot mistake a range that owns a file for an ordinary body.

What must not vary is the bytes, so the envelope is written in one place — `putEnvelope` — by both the whole-frame encoder and the header-only one, and `BrokerZeroCopyFetchTest#servesByteForByteTheSameResponseWithZeroCopyOnAndOff` compares raw socket bytes from the two settings over **one** data directory: the same files, the same correlation ids, six fetches covering a whole log, a fetch from the middle, one frame, a `maxBytes` landing inside a frame, an empty answer at the high-water mark, and the first-frame exception. Two directories would have compared two encodings — different timestamps, different checksums — and proved something else. Nothing here claims the transfer is quicker. Whether it is, and by how much, is a measurement, and the sub-slice that measures it is the one entitled to say.

## Sending bytes the operating system has not written out is safe, and the high-water mark is what bounds it

**Decision.** A transfer may cover records that have been appended and not forced, which today means very nearly all of them. Nothing waits for a flush before a fetch is served, and the range is bounded by the high-water mark exactly as the buffered read is.

**Alternative rejected.** Forcing the segment before sending a range over it. Serving only the bytes below the last position that was forced, and making a consumer wait for the rest.

**Why.** There is nothing to wait for. The transfer reads the same file the append wrote, through the same page cache, so a record acknowledged a moment ago is readable at its position whether or not the device has seen it — the kernel does not have two ideas about the contents of one file. Forcing per fetch would turn every read into a write barrier and would quietly make the fetch path decide the durability policy, which belongs to the flush sub-slice and to nothing else.

The bound that matters here is visibility rather than durability, and it is already in place: a range is located against the high-water mark, so no byte of a record the broker has not finished acknowledging can be in one. What a produce promises is unchanged by this slice and is stated where it was — a produce is acknowledged when its bytes are with the operating system, and that sentence is still the whole durability claim.

## A transfer reads through a channel of its own, so retention can delete under it

**Decision.** The rule, in one sentence: **a range that leaves the partition lock carries a descriptor nobody else can close.** `LogSegment.openRange` opens a second, read-only `FileChannel` on the segment's log file, under the partition lock; the `RecordRange` that carries it is what closes it, on the connection thread, once the response is complete. Retention's three steps are unchanged from earlier in this slice — start offset, list, then close the segment's own channel and unlink its two names — and it never touches a descriptor a fetch is using. Nothing is reference-counted and no unlink is deferred.

**Alternative rejected.** Lending the connection the segment's own channel. Leaving the segment's channel open after the unlink until the log is closed. Reference-counting readers and deferring the unlink until the last one is done. Pausing retention while any fetch is in flight.

**Why.** Lending the segment's channel is the option that looks free and is not. Closing a `FileChannel` while another thread is blocked in an I/O operation on it raises `AsynchronousCloseException` in that thread — and that thread has already written a response header promising a byte count. What the client gets is a frame that stops in the middle and a stream it can never resynchronize, which is the one failure this protocol has no answer for. That is not an argument from the manual: the deletion-race test was first run against a build that lent the segment's channel, and it failed with the connection closed part way through the length the broker had promised. `BrokerZeroCopyDeletionRaceTest#finishesAFetchAlreadyOnTheWireWhenRetentionDeletesTheSegmentItIsBeingSentFrom` is what stands where that build failed: it takes a few bytes of a response of nearly four mebibytes off a socket with a sixteen-kibibyte receive buffer — so the broker is provably still sending — sweeps retention by hand, and then reads the rest of the promised length and checks it against the deleted segment's own bytes.

Leaving the segment's channel open past the unlink would leak a descriptor per deleted segment for as long as the broker runs, which is the opposite of what retention is for. Reference counting was refused earlier in this document and the reason has not changed: POSIX already gives this property to anybody holding a descriptor, so the cheapest way to hold one is to open one. The cost is a single `open` per served fetch, on an inode the kernel has open already, set against a copy of the whole range that the transfer no longer makes.

The lock is what makes it two cases instead of three. The channel is opened under the same partition lock the deletion takes, so either the range exists before the unlink — and then the inode and its blocks stay alive until the range is closed, however many names are left pointing at them — or it is located after the segment left the list, and then the offset is refused with the start offset that deletion has already published. There is no window between them for a fetch to fall into.

The last piece is what happens when something does go wrong. Once the header has gone, the response is finished or the connection is: `RecordRange.transferTo` raises an `IOException` rather than an unchecked exception, and `Connection` writes its `INTERNAL` frame only from the path where not a byte has been written yet, so a broker never puts a second frame on top of half of one. `RecordRange.close` logs rather than throws for the same reason — by the time it runs the bytes are already with the client, and a descriptor that would not close must not turn into an answer to a request that was already answered.
