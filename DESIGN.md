# Design decisions

Each entry states the decision, the strongest alternative that was rejected, and why, in plain language. They are written to be quotable in an interview, so nothing here hides behind jargon.

## Module graph: shrike-core <- shrike-clients <- shrike-admin

**Decision.** Three Maven modules in one reactor. `shrike-core` holds the broker engine and depends on the JDK alone. `shrike-clients` depends on core for its protocol and codec types. `shrike-admin` depends on clients and is the only module allowed to use a framework. Nothing points back up the chain.

**Alternative rejected.** A single module with packages as the only boundary.

**Why.** A package boundary is a convention; a module boundary is compiled and checked. The maven-enforcer bannedDependencies rule on core turns "core stays JDK-only" into a build failure rather than a code-review opinion, and it keeps the engine testable without a framework on the classpath.

## Spring enters through an imported BOM, not a parent POM

**Decision.** `shrike-admin` imports `spring-boot-dependencies` as a `pom`-typed dependency with `import` scope in its own dependencyManagement, and pins `spring-boot-maven-plugin` itself.

**Alternative rejected.** Inheriting from `spring-boot-starter-parent`.

**Why.** The reactor needs its own parent for the toolchain, enforcer, and version pinning that apply to every module, and a POM has only one parent. Importing the BOM keeps Spring's version alignment where it is wanted — inside the admin module — while core and clients carry no Spring coordinate at all. The cost is that the BOM brings no plugin management, so the plugin version is pinned by hand.

## Toolchains plugin, because local Maven runs on a Java 25 JVM

**Decision.** `maven.compiler.release=21` plus `maven-toolchains-plugin` requiring vendor `temurin` version `21`, and a test that asserts `Runtime.version().feature() == 21`.

**Alternative rejected.** Relying on `release=21` alone.

**Why.** `release=21` fixes the language level and the API surface, but the build still compiles and runs tests on whatever JVM launched Maven — here a Java 25 JVM. The toolchain forces javac and the surefire fork onto a real JDK 21, so what CI tests is what a JDK 21 user runs. CI adds a class-file check for major version 65, and the build fails outright when no matching toolchain is declared, which is the loud failure the alternative lacks.

## The clock is an injected TimeSource in its own package

**Decision.** `io.shrike.core.time.TimeSource` is a single-method interface returning epoch milliseconds; `SystemTimeSource` is the only code in the broker that calls `System.currentTimeMillis()`. Components take a `TimeSource` through their constructor.

**Alternative rejected.** Calling `System.currentTimeMillis()` where the timestamp is needed, and letting tests assert a range around "now".

**Why.** A record's timestamp is data that ends up on disk, so tests should assert its exact value, not that it fell inside a window. Injection makes that possible without a single sleep, and it keeps the wall clock — the one thing a test cannot control — behind a seam that is one line long. The interface lives in `io.shrike.core.time` rather than in `io.shrike.core.log` because retention, delivery timeouts, and the network layer will all need the same clock, and none of them should have to depend on the log package to get it.

## The record frame, byte by byte

**Decision.** Every record is stored as one frame, big-endian, with a fixed-width header:

```
length:int32 | crc32c:uint32 | magic:uint8 | attributes:uint8 | offset:int64 | timestamp:int64 | keyLen:int32 | key | valueLen:int32 | value
```

- `length` counts every byte after itself, so a frame occupies `4 + length` bytes on disk.
- `crc32c` is `java.util.zip.CRC32C` over the bytes from `magic` through the last byte of `value`. The `length` field is deliberately outside that cover.
- `magic` is 0 and identifies this layout. `attributes` is 0 and reserved; a reader steps over its bits so a later slice can spend them without invalidating today's files.
- `offset` is written into the frame rather than inferred from the file.
- `keyLen` is -1 for a record appended with no key and 0 for a key of zero bytes, so the two stay distinguishable after a round trip. `valueLen` is never negative: a null value would be a tombstone, tombstones only mean something under compaction, and compaction is a non-goal, so `append` refuses one.

**Alternative rejected.** Covering the whole frame with the checksum, including the length, and skipping the explicit `offset` field because a reader could count records from the start of the file.

**Why.** A reader meets the length field first and must decide how many bytes to allocate for the rest of the frame *before* it has anything to verify: a checksum over the length is a checksum it cannot use yet. So the length is range-checked against `max.record.bytes` instead — the same bound the append side enforces — and a corrupt or hostile length is refused rather than believed and turned into a 2 GiB allocation. Everything after the length is covered, so a flipped bit anywhere in the header or payload fails the read.

Writing the offset into the frame costs eight bytes and buys self-description: a frame carries its own identity, so a reader can assert that the record at a position is the record it asked for, and a later recovery scan can rebuild offsets from the file alone instead of trusting a count. `RecordFrameGoldenBytesTest` freezes the whole layout, checksum included, against bytes derived from this description rather than from the implementation.

## `offset` counts records, `position` counts bytes — and the names never blur

**Refined in Slice 2.** The in-memory `positionsByOffset` list is gone; a segment's sparse index is what maps an offset to a position now, and the mapping is rebuilt from the log rather than held for the life of the process. The law itself is unchanged, and the last sentence of this entry is why the swap cost nothing.

**Decision.** `offset` is always a logical record number and `position` (always spelled `positionBytes` on a variable) is always a byte location in a file. `Log.append` returns an offset; the in-memory `positionsByOffset` maps one to the other; `RecordLocation` carries both plus topic, partition, and file, and every storage error quotes it.

**Alternative rejected.** Letting a reader address records by byte position, which is what the file actually needs.

**Why.** The two numbers are both `long`, so the compiler cannot tell them apart and only names can. Keeping the offset as the public currency also keeps the door open for segments and an index: when a record moves into a different file at a different position, its offset does not change. The mapping is the part that is allowed to be rebuilt.

## A read outside the readable range throws, and reads return a `StoredRecord`

**Decision.** `Log.read(long offset)` returns a `StoredRecord` — a record of `offset`, `timestampMillis`, `key`, and `value` — or throws. A negative offset and an offset at or past the high-water mark (`nextOffset()`) both raise `OffsetOutOfRangeException`, which carries the requested offset and the readable range `[firstOffset, nextOffset)`. An empty log has the empty range `[0, 0)` and refuses every read.

**Alternative rejected.** Returning `Optional<StoredRecord>` or `null` for a read past the end, and clamping a negative offset to 0.

**Why.** Reading past the end and reading before the start are two different mistakes, and a caller that gets `Optional.empty()` cannot tell them apart or learn what the valid range was — it would have to ask a second question to write a useful error. Clamping is worse: it silently answers a question the caller did not ask. A consumer that wants "wait until there is more data" is asking about the network layer's fetch semantics, not about a byte range in a file, so that behavior belongs in a later slice rather than smuggled into this return type. `StoredRecord` returns the stored offset and timestamp alongside the payload so a caller can verify what it got rather than assume.

## The log refuses to reopen a file it did not create

**Superseded by Slice 2.** Recovery arrived, so reopening no longer refuses: see "Reopening a log recovers it, because Slice 2 can read a file it did not write". The entry is kept because the reasoning it records is why recovery had to exist before reopening was allowed.

**Decision.** `SingleFileLog.open` creates the log file with `CREATE_NEW`. An existing file fails the open with a `ShrikeIOException` that says a recovery scan is a later slice. The offset-to-position map is held in memory only.

**Alternative rejected.** Opening an existing file and appending to the end of it.

**Why.** Appending to a file this class has not read means trusting that its last record is intact and that the next offset is whatever the file implies. Deciding that safely is exactly what recovery does — scan for the last valid frame, truncate a torn tail, and say so — and recovery is not in this slice. Refusing loudly beats a broker that quietly appends after a half-written record. It also makes the in-memory map honest: nothing is lost by not persisting it, because there is no path that needs it after a restart yet. Its size is bounded by `Integer.MAX_VALUE` records, which is another reason it is temporary.

## Durability in this slice: appends reach the operating system, `close` forces the file

**Refined in Slice 5.** The last paragraph below made a prediction — that the policy, per record or per interval, is a configured flush mode in a later slice — and this is the slice that cashed it. `flush.mode` exists, it defaults to `interval`, and what an append promises is now one sentence per mode rather than the single one this entry states: see "Two flush modes, and whichever bound comes first is the one that forces". The two force points this entry and the Slice 2 note beside it describe are unchanged; what changed is that they are no longer the only two.

**Refined in Slice 3.** The broker now acknowledges produce requests, and it acknowledges them on exactly this promise and no stronger one — see "What a produce promises, said plainly, and where the flush mode went". A commit of a group offset is the one thing this build forces before it answers.

**Refined in Slice 2.** Sealing a segment forces it, so a log now has two force points rather than one: the roll that seals a segment, and `close()` for the segment still taking records. What an `append` promises has not changed — see "Segments roll on size, and a segment is sealed only after it is forced".

**Decision.** `append` writes the frame through `writeFully` and returns once the operating system has the bytes. Nothing is forced to the device until `close()`, which calls `force(true)` before closing the channel. The README claims ordering and integrity, not survival of a power cut.

**Alternative rejected.** Forcing on every append, which would let the log claim durability today.

**Why.** An fsync per record is a policy decision with a large cost, and the policy — per record, per interval, or never — is a configured flush mode in a later slice. Choosing one now would either pick the slow default for everyone or leave the claim vague. Forcing at `close()` is the one point where the cost is paid once and the promise is exact, so it is the only durability sentence this slice makes.

## Segments roll on size, and a segment is sealed only after it is forced

**Decision.** A partition is a sequence of segment files named after the offset of their first record: `00000000000000000000.log` beside `00000000000000000000.index`, then whatever base offset comes next. Appending to a **non-empty** active segment rolls it when the record would push it *past* `segment.bytes`; a record that fills the segment to the byte does not roll it, and the record that would have overflowed becomes the first record of a new segment whose base offset is that record's own offset. An empty active segment accepts any record `max.record.bytes` allows, even a frame larger than `segment.bytes`, because a record no segment would take could never be stored at all. Rolling seals the segment it leaves behind, in this order: force the log file, force the index file, and only then treat the pair as immutable.

**Alternative rejected.** Rolling when a segment *reaches* `segment.bytes` and marking segments sealed without forcing them, leaving the fsync to the operating system's own schedule.

**Why.** The order of those three steps is the whole point, and it buys the recovery algorithm. Because a sealed segment was on the device before the writer moved on, a crash can only tear the segment that was being written, so startup reads one file frame by frame instead of all of them — a partition with a thousand segments costs the same to recover as a partition with one. Sealing without forcing would make that reasoning false: any segment could then hold a half-written frame, and honest recovery would have to walk every byte the broker had ever stored. Rolling on "would exceed" rather than "would reach" keeps `segment.bytes` a bound the files respect rather than one they cross by a frame, and the empty-segment exception is what keeps the bound from turning into a record the log refuses to store.

## The offset index is derived data, so nothing trusts it

**Decision.** Each segment carries a sparse index of fixed 8-byte big-endian entries, `relativeOffset:int32 | position:int32`, holding one entry per `index.interval.bytes` of appended records. Offsets are stored relative to the segment's base offset and positions as int32, which the 1 GiB cap on `segment.bytes` and `max.record.bytes` keeps safe. A lookup finds the segment whose base offset is the greatest one at or below the target, binary-searches that segment's entries for the greatest relative offset at or below it, and walks frames from there comparing each frame's stored offset with the one asked for — a walk bounded by the index interval. An index that is missing, whose size is not a whole number of entries, or whose entries do not climb or point inside the log is emptied and rebuilt by scanning the log. The rule that decides which record earns an entry is one method, `indexIfDue`, called both by `append` and by the scan that rebuilds, so it reads nothing but the bytes of the log.

**Alternative rejected.** A dense index — one entry per record, which is what Slice 1's in-memory `positionsByOffset` list was — and treating a damaged index as a reason to fail startup.

**Why.** A dense index costs 8 bytes of memory or disk per record forever and buys a lookup that is already cheap: with a 4 KiB interval, the walk after a binary search reads at most a few kilobytes. More importantly, an index restates what the log already says, so making it authoritative would create a second copy of the truth that can disagree with the first. Deriving it means a corrupt index is an inconvenience rather than data loss, and it means the code has one honest answer to "what if the index is wrong": delete it and read the log. Because the entry rule lives in exactly one method, an index grown record by record and an index rebuilt in one pass are the same file, which is what lets recovery rewrite an index without changing anything a reader can see. An index with no entries at all still yields correct reads — a lookup that finds no entry starts at the first byte of the segment — which is the strongest way to say the index is not load-bearing.

## Recovery walks the tail segment, cuts off what is torn, and logs where

**Decision.** Opening a partition directory sorts its segments by base offset. Every segment but the last is sealed, so it gets a cheap check of its index only — the file exists, its size is a whole number of entries, no entry points past the end of the log — and is rebuilt only when that fails; its log file is not read. The last segment is walked frame by frame from its first byte, applying the checks a read applies: the length field must be in range, the CRC32C must match, the magic must be this build's, and the frame's own offset must be the one the walk expects. The first frame that fails, or that the file ends inside, ends the log: the channel is truncated to the byte after the last whole frame, the tail's index is rebuilt from the same walk, a WARN names the topic, partition, byte position, and file, and the next offset becomes the base offset plus the number of frames that survived. A zero-byte tail segment is a valid empty segment; fewer than four trailing bytes cannot even hold a length field, so they are cut off; a run of trailing zeros fails the length range check and is cut off too. Damage inside a sealed segment is not repaired: startup does not look, the damaged record fails with a `CorruptRecordException` when it is read, and the records before and after it still read.

**Alternative rejected.** Walking every segment at startup, and refusing to start when the tail is torn so that a human decides what to do.

**Why.** Walking every segment would make startup cost grow with everything ever stored, and it would be redundant work: the sealing order already proves the earlier segments are whole. Refusing to start is the option that sounds safe and is not — a broker that will not come up after a power cut is down, and the torn tail is by definition made of records no producer was ever told about, so cutting them off loses nothing that was acknowledged. The WARN with the byte position is what keeps that honest: the truncation is a fact in the log file, not a silent repair. Recovery is idempotent because the walk depends only on the bytes on disk: a second restart with no writes in between truncates nothing, writes the same index entries, and leaves every file the size it already was, which is asserted rather than assumed. Leaving sealed damage in place is the same honesty in the other direction: the broker reports the record it cannot vouch for instead of quietly deleting the healthy records that follow it.

## Reopening a log recovers it, because Slice 2 can read a file it did not write

**Decision.** `SegmentedLog.open` creates a partition directory and its first segment when there is nothing there, and recovers what is there when there is. This replaces Slice 1's refusal to reopen an existing log file. The in-memory offset-to-position map is gone: a reopened log finds its records through the segment index instead.

**Alternative rejected.** Keeping the refusal for existing files and adding a separate explicit "recover this directory" entry point that a caller has to remember to call first.

**Why.** Slice 1 refused because appending after a record it had never checked would have meant trusting a file it had not read, and it said so in the exception. That reason is now satisfied rather than argued with: opening reads the tail and proves its last frame before it appends a byte after it. A separate recovery step would leave two ways to open a log, one of them wrong, and the wrong one would be the shorter one to type. Recovery is not an operation on a log — it is what opening one means. Dropping the in-memory map is what makes the size of a partition a disk question rather than a heap question, which is the same reason the index exists.

## The log's sizes live in one record next to the log

**Refined in Slice 5.** The last sentence below is now history in both of its halves. `LogConfig` holds two retention settings, `retention.ms` and `retention.bytes`, because retention exists; and it holds three flush settings, `flush.mode`, `flush.interval.ms`, and `flush.interval.bytes`, because a flush policy exists. The rule that sentence stated has not moved — a knob arrives with the code behind it, and both of these arrived with theirs. The record grew rather than a second configuration type appearing beside it, for the same reason it was one record in the first place: these are the numbers one partition's log is opened with, and a retention bound and a flush bound are both among them. Both retention settings default to −1, which is off, so a log opened the way every log was opened before this slice deletes exactly what it deleted before: nothing. That default is deliberate and is the subject of its own entry below, as is the flush default. `flush.mode` is an enum rather than a string, because a setting whose wrong value is a broker that starts and quietly promises something else is not a setting this repository is willing to spell out in characters.

**Refined in Slice 3.** `RecordFrame` is public now. A fetch response carries a byte range of a partition's log verbatim, so the consumer that reads those records back parses the same frames the log writes, and one parser for one layout beats two that are free to disagree — `WireRecordsTest` reads the very bytes `RecordFrameGoldenBytesTest` freezes. What this entry says about where validation belongs is unchanged: `max.record.bytes` is still checked in the log package, and what became public is the parse and the three constants a parser needs. The same move settles the boundary PRINCIPLES §9 asks to have written down: `StoredRecord` and `ProducedRecord` are part of the codec surface `shrike-clients` may depend on, because they are value types with no behavior, and nothing else in `io.shrike.core.log` is on that side of the line.

**Decision.** `LogConfig` is a record of `maxRecordBytes`, `segmentBytes`, and `indexIntervalBytes`, validated in its compact constructor, with a `defaults()` factory holding 1 MiB, 128 MiB, and 4 KiB. `segmentBytes` and `maxRecordBytes` are both capped at 1 GiB. It lives in `io.shrike.core.log` beside the log it configures, and it holds no flush or retention setting, because neither behavior exists yet.

**Alternative rejected.** Putting it in `io.shrike.core.config` as the start of a broker-wide configuration type, and keeping `open(...)` overloads that take one `int` per setting.

**Why.** Three `int` parameters in an `open` call are three chances to swap two numbers that the compiler cannot tell apart; a record names them at the call site and validates them once, so a log that holds a config holds one that already makes sense. Validation belongs there rather than in `open` because the smallest legal `maxRecordBytes` is a fact about the frame layout, and keeping the check in the log package is what lets `RecordFrame` stay package-private instead of publishing frame constants to satisfy a config type in another package. The 1 GiB cap is not a taste preference: an index entry stores a byte position in an int32, and the cap is what makes that field safe by construction rather than by hope. Settings for behavior that does not exist are left out, because a knob with no code behind it is a promise the README cannot make.

## The request envelope names an api and its version; the response echoes a correlation id

**Decision.** A request is `length:int32 | apiKey:int16 | apiVersion:int16 | correlationId:int32 | body` and a response is `length:int32 | correlationId:int32 | errorCode:int16 | body`, big-endian throughout, with `length` counting every byte after itself in both. The api key names the operation — 0 produce, 1 fetch, 2 commit offset, 3 create topic, with 4 and 5 reserved and unimplemented — and the version belongs to the key rather than to the connection: `ApiKeys.isSupportedVersion(apiKey, apiVersion)` is the one method that decides whether this build understands a pair, and today it says yes only to version 0. The correlation id is the client's own number, echoed back untouched, and the response repeats neither the api key nor the version.

**Alternative rejected.** One protocol version agreed when the connection opens, and matching each response to its request by the order the two travel in.

**Why.** Order as identity works right up to the first time a client wants two requests in flight, or the broker wants to answer a fetch that is still waiting for records after a produce that arrived later — which is what a fetch held open for `maxWaitMs` will do. A four-byte number the broker never interprets buys that for the price of one field, and it turns a client's bookkeeping into a lookup by key rather than a queue whose invariant nobody can see. A single protocol version is worse than it looks: the day fetch grows a field, produce's version number moves with it, and every client has to be told that its unchanged produce path now speaks version 1. Versioning per key keeps a change local to the api that changed. The response drops the api key because the correlation id already says which question is being answered, and a field the broker restates is a field that can be found disagreeing with the request it answers.

## One error code in the envelope, and an error answer carries no body

**Refined in Slice 3.** `FRAME_TOO_LARGE` has a producer now. The broker weighs every record of a produce request against `max.record.bytes` before it appends any of them, and a request carrying one record too large earns that code and stores none of its records — not even the ones that would have fitted. So the sentence below about it being the one code nothing can produce is history rather than a description: eight of the nine codes were reachable when they were frozen and the ninth is reachable now. What makes it reachable at all is that the two bounds are different numbers — a request may be 4 MiB and a record 1 MiB by default — so an oversized record arrives at the broker instead of being cut off by the frame guard, which is the only reason the broker gets to have an opinion about it.

**Decision.** Every response carries one int16: 0 none, 1 unknown topic or partition, 2 offset out of range, 3 corrupt record, 4 frame too large, 5 invalid request, 6 unsupported version, 7 topic already exists, 99 internal. `NONE` means the body that follows is the answer; every other code means the body is empty and the code is the whole answer. The codec refuses only what the bytes themselves can be wrong about — a negative string length, a record count over its cap, a name outside the character set a path component may use, an api key or version this build does not implement — and leaves what the broker holds to the broker. An unknown topic, an offset outside a partition's range, and a topic that already exists are answers rather than malformed requests, which is why `FetchRequest` does not judge its own offset and `ProduceRequest` does not judge its partition number. Reserved api keys 4 and 5 earn `INVALID_REQUEST`, the same as an api key of 999. `FRAME_TOO_LARGE` is the one code nothing in this slice can produce: it is held for a produce request whose record exceeds `max.record.bytes`, which is a check the broker makes once this protocol reaches it.

**Alternative rejected.** A per-api error body — a message, or a map of per-partition codes — and a distinct code for an api key that is reserved rather than unknown.

**Why.** An error body is a place to leak from. What the parser can say about the field it choked on is useful to whoever runs the broker and useful in a different way to whoever is probing it, so that sentence lives in `RequestDecoding.Refused` for the broker's own log and is never encoded. What is left is the code, and one code in the envelope means the same six bytes answer every api, which is what lets a client read a failure without knowing which request failed. A separate code for a reserved key would tell a caller which numbers are worth waiting for, and it would be a promise this build cannot keep: 4 and 999 are equally "not a request I implement" today, and that is the whole truth about both. Naming `FRAME_TOO_LARGE` with nothing behind it yet is the honest half of freezing numbers — a wire number can be added but never renumbered, so all nine are spelled out now and this entry says which one has no code behind it.

## A length this reader cannot believe closes the connection and is owed no answer

**Decision.** `RequestReader` reads exactly four bytes, and the length they carry must land in `[8, maxRequestBytes]`: 8 because that is the smallest length that can hold an envelope, and `maxRequestBytes` because a broker decides how much memory one connection may make it hold — 4 MiB by default, passed in rather than compiled into the reader. A length outside that range ends the connection with no reply and with nothing allocated for a body, and so does a stream that ends inside the length field or inside the frame. Only a length that passes gets a buffer allocated and filled. Inside the body every count and every declared length is checked against the bytes actually in hand, and against its own cap, before anything is sized to it: a string length against what remains, a produce record count against both its cap of 10 000 and the fewest bytes that many records could occupy, a key or value length against what remains. A body that breaks a rule is a refusal carrying the correlation id and `INVALID_REQUEST`, and the connection lives through it. Those three outcomes are one sealed type, `RequestDecoding` — `Accepted`, `Refused`, `BrokenFrame` — so a connection loop that forgets one does not compile.

**Alternative rejected.** Answering a bad length with `FRAME_TOO_LARGE` and then skipping that many bytes to find where the next frame starts.

**Why.** The correlation id lives after the length. If the length is nonsense then the bytes claiming to be a correlation id are nonsense too, so the reply would be addressed to nobody, and it would tell a stranger that something is listening and how it parses. Skipping ahead is worse than useless: it resynchronizes the stream by trusting the same number that just proved it cannot be trusted. Closing costs a well-behaved client nothing, because a well-behaved client never sends such a length, and it costs a hostile one the connection it was using. The allocation rule is the other half of the same argument: four bytes can ask for 2 GiB, and a reader that allocates first and validates second can be brought down by four bytes, repeatedly, from one socket. So the guard allocates a fixed four bytes, decides, and only then sizes anything to what it was told — and the test that proves it drives the reader with a channel that fails the run if anything reads past the length field, because a body that was never read is a body that was never allocated for.

## A fetch checks and waits under the same lock an append signals on

**Decision.** Every partition owns one `ReentrantLock` and one `Condition`. Every append and every read of that partition's log happens under the lock, because `SegmentedLog` says plainly that nothing in it is safe to call from two threads at once. A fetch that finds fewer than `minBytes` of records available checks what it has and registers as a waiter **without releasing the lock in between**; a produce appends every record of its request, then signals, under that same lock. The wait is bounded by an absolute deadline computed once from the injected `TimeSource`: each `await` is for whatever is left of it, and the predicate — at least `minBytes` readable from `fetchOffset`, or the deadline has passed, or the broker is stopping — is re-checked on every wakeup. `maxWaitMs` of 0 or `minBytes` of 0 answer on the first pass without waiting at all. A wait that expires answers with whatever there is, usually nothing, with error code `NONE` and the current high-water mark, because "there is nothing new yet" is an answer rather than a failure. The high-water mark is the log's own `nextOffset` read under that lock; no copy of it is kept.

**Alternative rejected.** Checking availability, releasing the lock, and then registering the waiter — the arrangement that reads naturally and is written most often. The other alternative was handing waiting fetches to a scheduled executor that re-checks them every few milliseconds.

**Why.** The gap between "I looked and there was not enough" and "I am now waiting" is exactly where a lost wakeup lives. An append that lands in that gap signals a condition nobody is waiting on yet, and the fetch then sleeps for the whole of its `maxWaitMs` while the records it asked for sit on disk. Doing both under one lock closes the gap by construction rather than by luck: the appending thread cannot reach the signal until the waiting thread is inside `await` and has released the lock. That is not a claim a reader has to take on trust — `BrokerFetchWaitTest` lands an append inside the window on purpose, through a seam that fires under the lock at the moment a waiter registers, and the test fails within seconds when the signal is removed.

A poller closes the same gap and pays for it forever: every partition would cost timer work whether or not anything is happening, and every answer would arrive up to one poll interval late for no reason a user could see. The absolute deadline is the other half of the rule. A wait that starts counting `maxWaitMs` again after each spurious wakeup is a wait with no bound at all, which is the same defect wearing different clothes.

The cost is honest and worth naming: a fetch reading bytes off disk holds the partition lock, so it serializes with appends to that partition. That is what the storage layer's own single-writer contract asks for, and the waiting itself does not hold the lock — `await` releases it — so a long poll blocks nobody.

## One acceptor, one platform thread per connection, and a hard cap

**Refined by the network-layer review.** Three things about handing a socket to a thread were wrong in a way only failure could show, and all three are fixed here. First, an accept that failed used to count towards a limit of sixteen, after which the acceptor returned and the broker took no more connections for as long as it ran — but the failure that limit was written for, running out of file descriptors, is exactly the one that clears on its own as connections close, so the cure outlived the disease. An accept that fails while the broker is running now logs a WARN and waits up to a hundred milliseconds *on the stop signal* before accepting again. That is a bounded wait whose predicate is "this broker is stopping", not a sleep for coordination: a shutdown during a backoff ends the acceptor at once, and the only way out of the loop is stopping. Second, the connection is put into the open-connection map *before* `Thread.start()` and the stopping flag is re-read *after* that put: `close()` sets the flag before it walks the map, so a `close()` that walked the map without seeing this entry cannot have set the flag after this read — which means one of the two closes the connection, and neither can leave a served connection that nobody will ever close. Third, a `Thread.start()` that throws — `OutOfMemoryError: unable to create native thread`, under exactly the pressure where a leaked slot matters most — now gives back the map entry and the place under the cap and closes the socket, rather than leaving all three to a thread body that will never run.

**Refined again by the security re-review.** That third fix was right about what to give back and wrong about what to do next: it rethrew, and the throwable ended the acceptor thread while `stopping` was still unset and the listening socket was still bound. What that leaves is a broker that keeps its port and its ready file, answers the connections it already had, and never accepts another one — the exact opposite of the sentence above that the only way out of the loop is stopping. It was also narrower than the hazard it was written for: `new Connection`, `new Thread`, and the map registration all run before `Thread.start()` and can each fail with an `OutOfMemoryError` under the same pressure, and a throw from any of them leaked the place under the cap — shrinking the effective cap by one for the life of the process — together with the socket. So the whole handoff is covered by one unwind now, from the moment `reserveConnection()` succeeds to `Thread.start()` returning: whatever is thrown, the acceptor logs a WARN naming the connection, then the map entry, the place under the cap, and the socket go back, and it accepts the next socket. **No throwable from a handoff ends the accept loop.** A failure that is about this process rather than about that one socket — out of memory, out of native threads — also earns the same bounded `stopSignal` wait an accept failure earns, because meeting the same wall at the speed of a loop is its own outage. The ordering guarantee of the paragraph above survives the restructuring unchanged: the map registration still happens before the stopping re-check, `close()` still sets the flag before it walks the map, and the unwind only ever removes an entry it put there itself. `BrokerConnectionHandoffTest` proves the whole of it through a package-private seam that fails a handoff at its earliest point, on a broker whose cap is one connection: the socket is closed, the acceptor is still accepting, and the place under the cap is back, which is what serving the next client requires. What is left of that handoff — the WARN is logged before the unwind runs rather than after it — was tracked in #10 and is settled in the paragraph below.

**Refined again in v1.2, which is that last residual.** The unwind now runs **before** the WARN, in both handoff-failure handlers, and the WARN is written somewhere a throwable from writing it cannot reach the accept loop. The order is the whole of the fix, and the reason it matters is that the failure this guard exists for is terminal memory pressure — the one condition under which formatting a message and appending a line are themselves able to throw. Logging first therefore lost all three of the things the unwind exists to give back, and lost them to the line that was meant to report the loss: the place under the cap stayed taken, the socket stayed open, and the `OutOfMemoryError` from `System.Logger` came out of the catch block and ended the acceptor. Unwinding first means everything that handoff took is already back before a byte of the message is formatted. What stays **outside** the guarded region is what was outside it before: `accept()` itself, which is the loop's own call and whose failures the backoff above already answers, and the connection's name, which is allocated before the place under the cap is taken precisely so that failing to allocate it costs nothing that has to be returned. Writing the line then happens inside a `catch` that drops what it catches — one of six, listed together in "The read bound covers idling and mid-frame reading, and never covers serving" below — and that is the exception to PRINCIPLES §3, documented here as §3 requires: the thing that just failed *is* the logger, so there is nowhere to report the failure of reporting, and a broker that stopped accepting because it could not write one line about one socket would be a far larger outage than the missing line. `BrokerConnectionHandoffTest#givesTheSlotBackAndKeepsAcceptingWhenTheWarnAboutAFailedHandoffThrowsToo` fails a handoff and then fails the WARN about it, through a second package-private seam that stands where that line is written, and asserts the socket closed, the place under the cap back, and the next client served on a broker whose cap is one connection. Against the old order it fails in both halves.

**Refined by the security review, which found the bolded sentence above was still a promise rather than a structure.** "No throwable from a handoff ends the accept loop" was true of everything the guard covered and not true of the guard itself: the unwind ran *inside* the `catch`, so a throwable out of the unwind — and removing a map entry and closing a socket are both allocations under the terminal memory pressure this whole guard exists for — travelled straight out of `serveOrClose` and ended the acceptor, with the port still bound and the ready file still where it was. It cost the place under the cap on the way past, too, because the throw happened before the count came down. Two changes make the sentence structural instead. The count is decremented in a `finally`, so a place under the cap goes back however the unwind ends; and what the unwind throws is caught and dropped, which is the same exception to PRINCIPLES §3 that the paragraph above documents for the WARN, and for the same reason — this *is* the path that gives things back, so there is nothing left to report a failure of giving back to, and the WARN that follows names the connection that was not served. What a throwing close costs is the socket, which stays open until the process ends: the cheaper half of a trade whose other half is an accept loop that is gone. The second change is smaller and is about counting rather than throwing: the stopping branch unwinds a connection the `catch` below could still see, so a throw from *that* unwind would have unwound the same connection twice and given its place back twice, raising the effective cap by one for the life of the process. The connection is forgotten before that unwind rather than after it, so at most one unwind per connection is a fact about the code rather than a fact about which of two paths ran first. `BrokerConnectionHandoffTest#givesTheSlotBackOnceAndKeepsAcceptingWhenTheUnwindOfAFailedHandoffThrows` fails a handoff and then fails the unwind of it, through a fourth package-private seam standing where the unwind gives things back, and asserts both halves: the next connection is served — which takes an acceptor that is alive and a place that came back — and the one after it is closed, which is how a place given back twice would show under a cap of one.

**Decision.** A thread named `shrike-acceptor` does nothing but accept. Every accepted connection gets its own platform thread named `shrike-conn-<n>`, where `n` only ever climbs so that two connections an hour apart cannot share a name. Connections are capped — 64 by default — and at the cap the next socket is accepted and immediately closed, never queued and never left for the acceptor to hold. The count is an `AtomicInteger` moved only through a compare-and-set that refuses to cross the cap, so the cap is exact even between two instructions. Stopping closes the listening socket, wakes every waiting fetch, closes the open connections so their threads come out of their blocking reads, joins those threads under one bounded deadline, and closes every log. Nothing is deleted.

**Alternative rejected.** Virtual threads, one per connection, with no cap because they are cheap. The second alternative was a single non-blocking selector loop.

**Why.** A virtual thread's advantage is that it releases its carrier while it waits, and this broker's waiting is mostly file I/O, which the JDK does not perform asynchronously: a virtual thread blocked in a `FileChannel` read occupies a carrier thread anyway. On Java 21 there is a second, smaller cut — a virtual thread pinned inside a `synchronized` block cannot yield at all, and that was not fixed until Java 24, which is not the platform this codebase targets. What is left of the advantage is thread footprint, which a hard connection cap already bounds, and against it stands something worth more here: a thread dump of this broker reads like documentation, with one named thread per connection and a stack that says what that connection is doing. A selector loop gives up even that, and it turns the fetch long poll from a thread that waits on a condition into a state machine that has to be right about the same thing without ever saying so.

The cap is a resource bound, not a queue-length knob, and closing is the point of it: a client that opens a thousand sockets should cost a thousand closes rather than a thousand threads, and it should cost the acceptor nothing that it can be made to wait for. Sixty-four is a default for a broker on one machine serving a handful of clients — at the default request bound it puts a number on the worst case, 64 threads and at most 256 MiB of request buffers — and it is a constructor argument, so a deployment that knows better says so. Both halves of that arithmetic have ceilings of their own now, so the worst case is a number at the maxima too and not only at the defaults: see "The settings a caller can spend have ceilings" at the end of this file.

## The ready file holds a port and a pid, and that shape is frozen

**Decision.** Once the logs are recovered, the socket is bound, and the acceptor is running, the broker writes a file with exactly two lines: `port=<the port it bound>` and `pid=<the process it is in>`. It is `java.util.Properties`-parseable, it is written through the same temporary-file-then-atomic-move sequence as everything else here, and stopping does not delete it.

**Alternative rejected.** Printing the port on standard output for a harness to scrape, and writing the file straight to its final name.

**Why.** A broker started on port 0 knows its port and nothing outside it does, so something has to carry that number across a process boundary; a later slice's test harness will start this broker with `ProcessBuilder` and needs both the port to connect to and the pid to destroy. Standard output is the wrong pipe for it: it is interleaved with logging, it has no atomicity, and a harness reading it has to parse prose. A file appearing in one atomic move gives a reader a rule it can rely on — the file is either absent or complete — so waiting for the broker to be ready is a file existence check rather than a guess. Writing in place would break that rule for the sake of one fewer syscall. Leaving the file behind on shutdown means a stopped broker and a crashed one look the same from outside, which is the truth; whoever starts a broker chooses the path and points it somewhere it does not mind overwriting. How the temporary file itself is opened — `<target>.tmp`, without `CREATE_NEW` or `NOFOLLOW_LINKS`, which matters most for a ready file whose directory something else can write to — is tracked in #12.

## A committed offset is the next offset to read, and the client hears about it only after fsync

**Decision.** Committed offsets live in one text file per group, `groups/<groupId>.offsets` under the data directory, keyed by group, topic, and partition from the first commit. **The number stored is the next offset that group should read, not the last one it read.** A commit rewrites that group's whole file through one shared sequence: write a temporary file in the same directory, force it, move it onto the target with `ATOMIC_MOVE`, and force the directory so the rename itself is on the device. The broker answers the client only after all four steps have happened. Committing the high-water mark is legal — it is how a group says it has read everything there is — a negative offset is `INVALID_REQUEST`, and an offset past the high-water mark is `OFFSET_OUT_OF_RANGE`.

**Alternative rejected.** Storing the last offset read, and appending each commit to a log that is replayed at startup rather than rewriting a small file.

**Why.** "Last read" and "next to read" differ by one, and the difference is the empty case: a group that has read nothing has no last offset, so the convention needs a sentinel, and every consumer then has to remember which sentinel and add one in the right place. "Next to read" needs no sentinel — a group that has committed nothing has no entry — and the number a consumer commits is the number it will ask for, which removes an off-by-one from the one place where an off-by-one silently redelivers or silently skips. So the convention is stated in the javadoc, here, and in the field's own name.

Rewriting the whole file is right while a group's offsets are a handful of lines: it costs one fsync per commit against a log's one append plus periodic compaction, and it has no recovery story to get wrong, because the file is either the old one or the new one. An append-only commit log wins when the file is large enough that rewriting hurts, and nothing here is close to that.

The durability is deliberately stronger than what a produce promises, and the asymmetry is the point: a lost produce is a record the producer was never told about, while a lost commit is redelivery of records somebody already handled. The sequence lives in one place, `DurableFile`, which the topic registry and the ready file use too — it sits in the log package because that package already owns this codebase's answer to "when is this durable", from `writeFully` to `ShrikeIOException`. Its steps report themselves as they complete, which is a seam and nothing else: an fsync leaves no trace a JVM can observe, so the only way to prove a caller is told about a write after the write was made durable is to have the sequence say what it did while it did it. Forcing a directory means opening it for reading, which POSIX allows and Windows does not; this build is developed and tested on POSIX systems, and on a platform that refuses, a commit fails loudly rather than quietly promising less than it delivers.

## What a produce promises, said plainly, and where the flush mode went

**Refined in Slice 5.** Where the flush mode went is: here. `flush.mode` is in `LogConfig` beside the log it configures rather than in `BrokerConfig`, because what it decides is when a segment file reaches the device, and that is a fact about one partition's log rather than about the broker's sockets. So the last sentence of the decision below — that there is no flush-mode setting because there is no flush mode — is history, and what a produce promises is two sentences now, one per mode, stated in "Two flush modes, and whichever bound comes first is the one that forces". The rest of this entry is unchanged and is what makes those sentences the broker's own: the force happens inside `SegmentedLog.append`, the answer is written after `Partition.produce` returns, and the broker still adds nothing to what the log promised. The reasoning that kept the knob out until now is why it arrived with the code behind it rather than a slice ahead of it.

**Decision.** The broker answers a produce request once the records' bytes have been handed to the operating system through `writeFully`. Nothing is forced. That is the same promise `SegmentedLog.append` has made since Slice 1, and the broker adds nothing to it: ordering and integrity, plus whatever the sealing of a segment already guarantees, and not the survival of a power cut. There is no flush-mode setting in `BrokerConfig`, because there is no flush mode.

**Alternative rejected.** Adding `flush.mode` to the broker configuration now, with `none` as the default, so that the knob exists before anything needs it.

**Why.** A knob with no code behind it is a promise the documentation cannot make. The interesting version of this setting — per record, per interval, or never — is a cost that has to be measured to be chosen, and the slice that measures it is the one that should introduce it, together with the numbers that justify its default. Stating the current promise in one sentence is worth more than a setting whose only value today would be the one it already behaves as. What this entry buys is that nobody has to read the code to find out when a produce is durable: it is durable when the operating system writes it out, and the broker does not know when that is.

## A fetch response carries the log's own bytes, not a re-encoding of its records

**Refined in Slice 5.** The last sentence of the "Why" below made a prediction — that a range of a file, identified without being decoded, is a `transferTo` waiting to happen — and this is the slice that cashed it. `readRange` gained a twin, `Log.openRange`, which locates the same range and opens the file over it instead of copying it out; the walk that decides where the range starts and stops lives once, in `LogSegment`, so the two cannot come to different conclusions about which frames a consumer was promised. What the entry did not anticipate is the other half of the shape. A range that leaves the log has to carry a channel with it, and *who owns that channel* turned out to be the whole of the safety argument, because retention had meanwhile learned to delete the file underneath it. That is settled in "A transfer reads through a channel of its own, so retention can delete under it".

**Decision.** `Log` grew one method, `readRange(fetchOffset, limitOffset, maxBytes)`, which returns whole record frames copied verbatim out of the segment file. The broker puts those bytes into the fetch response without looking inside them. The range starts at `fetchOffset` and stops at the first of: the high-water mark, `maxBytes`, or the end of the segment `fetchOffset` falls in. `maxBytes` yields to the whole-frame rule twice: a frame that would cross the cap is left for the next fetch, and a first frame larger than the cap all by itself is returned anyway.

**Alternative rejected.** Reading `StoredRecord`s through the existing `read(offset)` and encoding them into the response, which needs no new method on the log at all.

**Why.** Re-encoding creates a second path that produces record frames, and two paths that produce the same layout are two paths that can disagree about it — at which point the bytes a consumer checksums are not the bytes the log checksummed. Copying the range keeps one layout, one parser, and one checksum, and it is what makes `WireRecords` able to parse a fetch response with `RecordFrame`, the very code the disk format is frozen against. It is also the shape a later zero-copy slice needs: a range of a file, identified without being decoded, is a `transferTo` waiting to happen, while a list of decoded records is not.

Stopping at a segment boundary is a short answer rather than an error because the alternative is stitching two files together in a buffer to save a client one round trip it can make itself. The first-frame exception is the one place `maxBytes` is deliberately violated: a consumer that asked for fewer bytes than the next record occupies would otherwise be stuck on that record forever, unable to make progress and unable to learn why. Serving it whole bounds the overrun at `max.record.bytes`, which is a number the broker already enforces, and lets the consumer move. The broker also caps what any fetch may be answered with at `max.request.bytes` — the same number that bounds a request — because that is the one setting that says how much memory one connection may make this broker hold, and a fetch asking for two gibibytes is a request for memory like any other.

## The topic registry is one text file, written before the directories it describes

**Refined in Slice 5.** The last sentence of this entry made a prediction and it turned out to be wrong, so it is corrected here rather than quietly left standing. Retention arrived, it does want partitions without wanting sockets, and `Partition` and `TopicRegistry` did **not** move. What retention needed was one method — "delete the segments you no longer keep, as of this millisecond" — and that is a one-method interface, `io.shrike.core.retention.SegmentDeletion`, which `TopicRegistry` implements and which names no partition, no socket, and no segment file. Moving two types into a package of their own to satisfy a dependency that a single interface satisfies would have been a larger change bought for nothing, and it would still have cost the fetch seam its package privacy. The prediction was right that something had to give; it was wrong about which direction it would give in, and a seam this narrow is the cheaper answer.

**Decision.** Which topics exist and how many partitions each has is one file, `topics`, directly under the data directory: a version header line and then one `name partitionCount` line per topic, written through the same `DurableFile` sequence as a group's committed offsets. A create writes that file **before** it opens a single partition log. Partition directories keep the layout the log package already used, `<dataDirectory>/<topic>-<partition>/`. A partition count is fixed when a topic is created, so a repeat create is `TOPIC_ALREADY_EXISTS` whatever count it asks for, the same count included. The registry and the live partitions behind it live in `io.shrike.core.net` beside the broker that owns them.

**Alternative rejected.** Deriving the topic list from the directories on disk, so that there is no registry file to keep in step with them. Opening the logs first and recording the topic afterwards. A separate `io.shrike.core.topic` package.

**Why.** Directories cannot answer the question. A topic with four partitions that has never been produced to looks exactly like a topic with one, because the empty directories are indistinguishable from missing ones — and a partition count that can be inferred wrongly is a partition count that changes under a producer, which is the one thing it must never do. So the count is written down, in the smallest durable form that holds it.

The order matters for the same reason the sealing order mattered in Slice 2. A crash between writing the file and opening the logs leaves a topic listed whose directories do not exist yet, and the next start creates them as it opens them — the file is the truth and the directories follow it. The other order leaves directories that nothing lists: storage no restart accounts for, and a name that a later create would silently adopt along with whatever was in it.

Keeping the registry in `io.shrike.core.net` rather than in a package of its own is a judgement about what these types are. A `Partition` here is not storage — the log package is storage — it is the lock, the condition, and the wait that the fetch api is defined in terms of, and it exists only because connections ask it things. Splitting it out would have bought one package boundary between two types that are never used apart, and it would have cost the fetch seam its package privacy: the test that lands an append inside a waiter's window has to reach that partition, and a public method for it would be a wider surface than the boundary was worth. When retention arrives and wants partitions without wanting sockets, that is the change that should move them.

## `shrike-clients` may name four types from the broker, and this entry is the list

**Refined by the network-layer review.** `SafeName` moved from `io.shrike.core.protocol` to `io.shrike.core.log` — see "One name rule, and it lives where names become paths" — so the list below reads one type shorter on the protocol side and one longer on the log side. Nothing in the client's main code names it either way; what the boundary allows has not changed.

**Decision.** The client library compiles against `io.shrike.core.protocol` — the request and response records, `RequestFrame`, `ResponseFrame`, `WireRecords`, `ApiKeys`, `ErrorCode`, `SafeName`, and `RequestReader`'s default request bound — plus exactly three types out of `io.shrike.core.log`: `ProducedRecord`, `StoredRecord`, and `MalformedFrameException`. Nothing else in the broker is on the client's side of the line: not `io.shrike.core.net`, not `io.shrike.core.group`, not the log itself, not `ByteChannels`. The module's *test* code is allowed the broker, because a test whose subject is a real broker needs a real broker; its *main* code is not.

**Alternative rejected.** A fourth module, `shrike-protocol`, that both the broker and the clients depend on, so that the boundary is compiled rather than described. And, in the other direction, letting the client call `ByteChannels.writeFully`, so that this repository keeps exactly one write loop.

**Why.** The three log types are on the client's side because the codec's own signatures name them: a produce request is built out of `ProducedRecord`s, and `WireRecords.decode` returns `StoredRecord`s and throws `MalformedFrameException` when a block turns out not to be records. A boundary that excluded them would force a client to convert between two identical record types, and the second copy would be free to disagree with the first about what a null key means — which is the same argument that keeps one record layout on disk.

A separate protocol module is the tidy answer and it is not free. `RecordFrame` owns the disk format and lives beside the log that writes it; splitting the protocol out would either move it away from that log or duplicate it. The line is worth drawing now and worth compiling later — when a third thing speaks this protocol, that is the change that should pay for the module.

`ByteChannels.writeFully` is the one place this boundary and PRINCIPLES §5 pull against each other, and the client resolves it by not needing the loop. §5 exists because a NIO `channel.write` may write fewer bytes than the buffer holds and leave half a frame on the wire; `OutputStream.write` cannot do that — its contract is that every byte is written or an exception is thrown. So the client has no short-write loop rather than a second, more forgiving copy of one, and the surface stays four types wide.

## The client reads an answer the way the broker reads a request, and numbers its own questions

**Decision.** `BrokerConnection` owns one socket and carries one call at a time. It assigns correlation ids from 1 upwards, and reads every answer through the guard `RequestReader` uses pointed the other way: read exactly four bytes, believe the length only inside `[ResponseFrame.MINIMUM_LENGTH_BYTES, maxResponseBytes]`, and allocate nothing until it does. `maxResponseBytes` defaults to the broker's own `max.request.bytes` — 4 MiB, the cap the broker serves a fetch under — plus a kibibyte of envelope headroom, and it is a configuration field, so a client pointed at a broker with a larger bound says so rather than meeting it as a broken frame. An answer whose correlation id is not the one that was sent, a body that does not parse, and an error code carrying a body are all the same verdict: this connection cannot be believed, so it is closed. A broker error code is not — it is an answer, and the connection stays usable after one. The socket is a `java.net.Socket` with a connect timeout and `SO_TIMEOUT`, and a fetch's `SO_TIMEOUT` is its own `maxWaitMs` plus the configured margin rather than a fixed number.

**Alternative rejected.** Trusting a length because the broker is what wrote it, and matching answers to requests by the order they arrive in. A `SocketChannel`, which is what the broker's own side of this wire uses, with one blocking read after another. One read timeout covering every api, fetch included.

**Why.** A client is not a privileged reader. The thing on the other end of the socket is whatever answered on that port, and four bytes from it can ask for two gibibytes just as easily as four bytes from a client can ask the broker for them. The guard is the same shape on both sides because the hazard is the same on both sides, and the cap is stated as a number a deployment can change rather than derived from a constant the broker might not share.

Order as identity would work today, because this connection has one call in flight. It would stop working the first time it did not, and it would stop working silently: the answer to the previous question would be read as the answer to this one. The correlation id costs four bytes and turns that into a check, and a check that fails is not a request that failed — it is a client that has lost its place in the stream, which is why it closes the connection instead of raising an error the caller could retry.

A `SocketChannel` is what the broker uses and it is the wrong tool here: a blocking channel read cannot be bounded, because `SO_TIMEOUT` applies to a socket's streams and not to a channel's reads. A client that must be able to say "the broker did not answer" needs that bound. The margin is the other half of it. One flat timeout means that raising a fetch's `maxWaitMs` above it turns a long poll the broker is serving correctly into a client-side timeout, and the caller who raised it has to know to raise a second, unrelated number. Adding the wait to the margin makes the client's bound follow the request's own wait, and the margin keeps its plain meaning: how long the broker gets to answer once it has stopped waiting. A read that does time out closes the connection, because the answer it gave up on may still be on its way, and a reused connection would read it as the reply to the next request.

## Creating a topic is a client of its own

**Refined in Slice 6.** The last paragraph below predicted that describing topics and describing groups would both arrive next to `create`. Half of that held. Describing topics did land there, because it is about topics. Describing a group did not: a group is not a topic, and putting the two behind one type would have made `ShrikeTopics` the grab-bag this entry rejected, one method later. `ShrikeGroups` is its own client for the reason `ShrikeTopics` is — see "Describing lives with the thing described" below.

**Decision.** `ShrikeTopics.create(name, partitionCount)` in `shrike-clients`, an `AutoCloseable` of its own over its own connection.

**Alternative rejected.** A `createTopic` method on `ShrikeProducer`, which is where the caller that needs it already is. A single `ShrikeAdmin` type collecting everything that is neither produce nor fetch.

**Why.** A producer exists for as long as there is something to send; a topic is created once, usually by whoever sets a deployment up and often from a different program entirely. Putting the two behind one type would mean every producer carries a method it must never call twice, and it would make the first thing a reader learns about producing be a sentence about topics. Splitting them costs one small class and buys each of them one reason to change.

`ShrikeAdmin` would be a name for "the rest", and the rest is one method. The types this repository bans — `Manager`, `Helper`, the grab-bag `Processor` — are banned because they are named after their own vagueness, and a type named after what it is not would be the same mistake with a better-looking word. When describing topics and describing groups arrive, they arrive next to `create` in a class already named after the thing they are about.

## The flagship test is five processes, a ready file, and a killed process tree

**Decision.** `ClientProcessIT` starts a broker, two producers, and two consumers as separate operating-system processes with `ProcessBuilder`, using the `java` of the JVM running the test and the classpath it was given. It learns the broker's port by waiting for the ready file under one deadline with a short poll interval, speaks to the broker through the client library, reads every process's exit code with a bounded `waitFor`, and parses `field=value` lines out of each process's redirected output. An `@AfterEach` destroys every process it started — descendants first, then the process itself, forcibly, under a bound — on every outcome, including an assertion failure and a wait that gave up. `maven-failsafe-plugin` runs it, pinned to the version surefire is pinned to, so that the `*IT` name keeps it out of the fast unit loop and `verify` is what fails on it. The resume half of the flow reads the committed offsets out of the broker's own `groups/<groupId>.offsets` file and starts the replacement consumer process from them.

**Alternative rejected.** Threads in the test JVM, which is what every broker test in `shrike-core` already uses and what is cheapest to write. Scraping the port from the broker's standard output. Handing the replacement consumer the offsets the first consumer said it committed. Cleaning up in a `finally` inside the test method.

**Why.** Threads share a heap, and a heap is the one thing a client and a broker must not share. A client that reached past the protocol — held a reference to a partition, read a field it should have asked for — would still pass a test that ran both in one JVM, and would fail the first real deployment. Here the only things that cross a boundary are a TCP socket, a file, an exit code, and lines of text, so what the test proves is that the protocol carries the meaning.

The ready file is the port's only way out of a broker started on port 0, and it appears in one atomic move, so a reader either sees the whole file or no file. Standard output has neither property: it is interleaved with log lines and it arrives a character at a time. Waiting for the file is the one place this repository polls, because there is no lock to hold and no condition to signal across a process boundary — so the poll lives in one helper, with an absolute deadline, a short interval, and a failure that quotes the broker's own output, and it gives up early if the broker process has already died.

Reading the committed offsets out of the broker's file rather than trusting what the first consumer printed is what makes the resume worth testing. The numbers the replacement starts from are then the numbers the broker stored, so a commit the broker acknowledged and lost fails this test; if the consumer's own output were passed along, the second half would prove only that a consumer can be told where to start. No api read a committed offset back when this test was written, and that is the honest reason a file is read at all — the *test* knows a format that DESIGN.md fixes, while the client library knows only the protocol. Slice 6's describe-group api reads one back now, and this test still reads the file, because the file is what the broker actually stored and an api answering from memory would prove one thing less.

Destroying the tree is not tidiness. A leaked broker holds a port and a data directory, and the next run of the same test would meet it; a leaked child of a child is a process nothing has a handle on at all. `descendants()` before `destroyForcibly()` covers the second, and running the destruction from `@AfterEach` rather than a `finally` inside the test covers the first for every path — including the ones nobody remembered to wrap, which are exactly the paths a failing test takes.

## A topic name and a group id are case-insensitive, because the paths they name are

**Refined by the security re-review.** The fold decided the name a group's file is *written* under and said nothing about a file already sitting in that directory under another casing, which turned a routine restart into a permanent, loud failure. A data directory holding `Readers.offsets` — from an unreleased build of this branch, or from something else that wrote into it — opens, and then the first ordinary commit writes `readers.offsets` beside it on a case-sensitive filesystem; from that moment every start refuses with "names one group twice", and nothing in the tree can repair it. So opening the store now renames a file whose name is not folded onto the folded one, durably and through the same machinery a commit uses: one `ATOMIC_MOVE` and then the directory forced, which is `DurableFile.rename` — the last two steps of `DurableFile.replace` and none of the others, because the bytes are already on the device. After the rename, memory and disk agree everywhere, and a WARN names the file that was renamed and why. The genuinely ambiguous case — both casings present at once — still fails the start, and its message now spells out the repair a human has to make: keep whichever of the two holds the offsets that group should resume from, name it `<folded id>.offsets`, and remove the other.

**Alternative rejected.** Refusing that single unfolded file too, and demanding the same manual repair for it. It is the tidier rule, and it charges the wrong person. One file under one casing is not ambiguous: there is exactly one set of committed offsets and exactly one name this build stores them under, so the only thing a human would add is the typing. Refusing would also turn a fold introduced to prevent silent data loss into a broker that will not start over a directory it can read perfectly — the same failure mode the recovery entry above rejected for a torn tail, arriving for a file that is not even damaged. Ambiguity is where a refusal belongs, and the colliding pair is the only ambiguity there is.

**Decision.** A topic is held under `SafeName.fold(name)` — the name lowercased with `Locale.ROOT`, which for the ASCII the name rule allows is exactly a case fold — and so is a consumer group. `orders` and `Orders` are one topic: a create whose name folds onto a topic that is already here is `TOPIC_ALREADY_EXISTS`, and a produce, a fetch, or a commit naming any casing reaches the one topic that exists. The topic keeps the spelling it was created with, because that is what the registry file lists and what its directories are named. A group's *file* takes the folded id, `groups/<folded group id>.offsets`, since a group has no registry and its file name is its identity; the topic inside a group's offsets is folded too, so a commit and the fetch that follows it cannot key the same partition two ways. A registry file listing two names that fold together, or a groups directory holding two files that do, fails the start with a message naming both.

**Alternative rejected.** Case-sensitive names, plus a documented requirement that this broker runs on a case-sensitive filesystem. The other alternative was folding only the create-time guard and leaving lookups exact.

**Why.** A partition's identity on disk is `<dataDirectory>/<topic>-<partition>/`, and on APFS and on Windows that directory name does not tell two casings apart. So `create("orders")` followed by `create("Orders")` used to give two `Topic` objects with two locks, two `SegmentedLog`s, and two open channels over the same segment file — two writers that hand out the same base offsets and overwrite each other's acknowledged records. The rule that closes it is one sentence: a name's identity must be at most as fine-grained as the identity of the path it becomes. Since the coarsest filesystem this could run on folds case, the fold is where identity is decided, on every filesystem, so the behaviour a test proves on Linux is the behaviour macOS gets.

Requiring a case-sensitive filesystem is the alternative that costs nothing to write and everything to rely on: it is a condition no code checks, that a developer on macOS breaks by existing, and whose failure mode is silent data loss rather than a refusal. Folding the guard but not the lookup is worse than either: the broker would answer "that topic already exists" to a create and "no such topic" to a produce naming the same string, which is two different truths about one name.

The cost is stated plainly: two topics that a case-sensitive filesystem could have kept apart can no longer both exist, and a name is echoed back in the spelling it was created with rather than the spelling a caller used. That is the same trade every case-insensitive namespace makes, and it is a refusal at create time rather than a surprise at read time.

What the fold settles is APFS-style case-insensitivity, and that is the whole of the claim. Windows is named above for the shape of its path identity rather than as a platform this build runs on: Win32 folds more than case — `nul`, `con`, `aux`, and `com1` are reserved device names, and `SafeName` admits all four — so a Windows port would need a rule about those as well. It is out of reach today in any case, because forcing a directory means opening it for reading and Windows refuses that, which the committed-offsets entry above already states as a loud failure rather than a quiet one.

So that rule is deferred rather than dropped, and #10 says so in the same words: it is contingent on Windows support this build does not have and cannot have while a commit's durability depends on an fsync of a directory. Writing it now would be a rule nothing here could exercise — no platform to run it on, no test that could fail without one — and a name rule that is not exercised is a name rule that drifts, which is the defect the entry above this one exists to have removed. It rides with the port, or not at all.

## A fetch's wait and its `minBytes` are clamped to what this broker can serve

**Decision.** `BrokerConfig` grew `maxFetchWaitMs`, 30 seconds by default, and a fetch's wait is `min(maxWaitMs, maxFetchWaitMs)`. Its `minBytes` is clamped too, to `min(maxBytes, max.request.bytes)` — the most bytes that fetch could ever be answered with. Both clamps are pure functions on `Partition` with tests of their own. While waiting, a wakeup that finds the high-water mark exactly where the last read left it waits again without re-reading the log.

**Alternative rejected.** Refusing an out-of-range `maxWaitMs` or `minBytes` as `INVALID_REQUEST`, and leaving the read on every wakeup because it is simple and obviously correct.

**Why.** Both numbers are int32 fields a client fills in, and the codec only refuses them for being negative — as it should, since neither is a statement the bytes can be wrong about. Taken at face value, `maxWaitMs` of `Integer.MAX_VALUE` parks a connection thread and its slot under the connection cap for about twenty-five days, so 64 of them are the whole broker. A `minBytes` above what can be served is worse than long: it is a predicate no append can satisfy, so the fetch sleeps out its entire deadline while the records it asked for sit readable on disk. Clamping turns both into what they always were — a caller's preference, met as far as the broker is willing — and it keeps a well-behaved client's request untouched, which refusing would not. Refusing would also break a client that raised `maxWaitMs` for a reason, at the moment it needed the answer, and it would put a number the operator can change into the protocol's error surface where it does not belong.

The skipped re-read is the other half of the fix and it is small: bytes readable from a fixed offset can only change when the high-water mark moves, and nothing in this build removes records. Without it, one tiny produce woke every waiter on the partition into a full `readRange` of up to `max.request.bytes` — 63 waiters re-reading 4 MiB each to discover they still could not be filled. What is *not* fixed, and is worth naming: the waiters that do read still read one after another under the partition lock, because that lock is what makes the log a single writer. Cutting that cost means serving many fetches from one read, which is a change to how a fetch is answered rather than to when it wakes up.

## The partitions a broker will open are budgeted

**Refined by the group budget.** The closing paragraph below named the number of consumer groups as the one thing this build did not budget. It is budgeted now — `maxTotalGroups`, and "The consumer groups a broker will hold are budgeted" at the end of this file — so that paragraph reads as the statement of a gap that has since been closed, and #11 with it. Nothing this entry says about partitions moved: the two budgets are separate numbers over separate resources, and the group budget was written to the shape this one set.

**Decision.** `BrokerConfig` grew `maxTotalPartitions`, 1024 by default. A create that would push the number of open partitions past it is refused with `INVALID_REQUEST`, counted across every topic and enforced under the same lock that makes a create atomic. A registry that already lists more than the budget still opens every partition it lists, and says so in a WARN; the budget stops the next create instead.

**Alternative rejected.** Leaving the per-request cap of 1024 partitions as the only bound. Refusing to start when the stored partition count is past the budget.

**Why.** The per-request cap bounds one request and nothing else: a thousand creates of a thousand partitions each is a million directories, two open file handles apiece, and the process meets `EMFILE` long before that. What arrives then is not a bad answer to a create — it is `accept()` failing on the acceptor thread, connections that cannot be served, and a broker that is up and useless. A budget makes the same limit arrive as a refusal that names the number it crossed, at the request that asked for it, while the broker is still healthy. Both numbers earn their keep: one create still cannot ask for more than the whole budget, and the budget is what makes many creates add up to something bounded.

Refusing to start over a stored count past the budget was the tempting symmetry, and it is the wrong call. Those partitions were created under whatever budget was configured at the time, their records are acknowledged records, and rebuilding a `BrokerConfig` with a smaller `maxTotalPartitions` should not turn a broker's data directory into one it will not open. Opening what exists and refusing what is new keeps the budget a bound on growth rather than a retroactive verdict, and the WARN is what keeps that from being silent.

What is *not* budgeted is the number of consumer groups: partitions, connections, request bytes, and fetch waits all have a number, while every distinct group id creates a `groups/<id>.offsets` file and an in-memory entry that outlive the connection that committed and survive a restart. Tracked in #11.

## One name rule, and it lives where names become paths

**Decision.** `SafeName` moved from `io.shrike.core.protocol` to `io.shrike.core.log`, and `SegmentedLog`'s own `[a-zA-Z0-9._-]{1,249}` pattern is gone: opening a log calls `SafeName.require(topic, "topic")`. One rule, one place, applied by the protocol as a request is decoded and by the log as a path is built.

**Alternative rejected.** Leaving the copy in `SegmentedLog` alone, since it was stricter than the filesystem and nothing had gone wrong. Making `SegmentedLog` import `io.shrike.core.protocol.SafeName` where it stood. A package of its own for one class.

**Why.** The two rules had already drifted: 249 characters in the log against 200 in the protocol, which is a name the log would accept and the broker would refuse, and a difference nobody would notice until a name landed between the two numbers. That is what a second copy of a rule is for — being more generous than the first — and the fix is to have one rather than to keep them in step by hand.

Where it lives is decided by which import would be a cycle. `io.shrike.core.protocol` already depends on `io.shrike.core.log`, because `WireRecords` parses the very frames `RecordFrame` writes, so a log that imported the protocol would close a loop between two packages. Pointing the dependency the other way costs nothing and reads better than the accident it replaces: the log package is where a name becomes a path — `<dataDirectory>/<topic>-<partition>/` is built there — and it is already where `DurableFile` and `ByteChannels` live for the same reason. A package holding one final class with two static methods would be a boundary drawn for tidiness, and this repository already decided that question when `DurableFile` went into the log package rather than into one of its own.

## Loopback only, no authentication, and no read timeout yet

**Refined in Slice 6.** The bind address became nameable, once, by the process that starts the broker — see "The bind address is an argument to a second `start`, and everything else gets loopback" below. What binds by default did not move, and the paragraph on authentication and the idle connection stands as written.

**Refined again, on the read timeout.** There is one now, and it is scoped: see "The read bound covers idling and mid-frame reading, and never covers serving" at the end of this file. The write side has one too — "The write bound is a bound on making no progress, not on how long an answer takes" — so all three of the things #9 asked for exist: a nameable bind address, a bound on idling and reading, and a revisit of what a connection can still cost, which is now `connectionCap` × `max.request.bytes` of memory and a bounded amount of time in either direction. #9 is closed by that and by nothing more. What none of it changes is the paragraph below on authentication: there is still none, it is a [non-goal](README.md#non-goals) of this build rather than an open issue, and the loopback default is still what stands in for it.

**Decision.** The listener binds `InetAddress.getLoopbackAddress()`. There is no authentication, no authorization, and no transport security, and the bind address is not configurable — that last clause was true when this entry was written and stopped being true in Slice 6, as the refinement above says; the rest of the paragraph still holds. There is also no server-side read or idle timeout: a connection that opens and then says nothing holds its slot under the connection cap until it is closed or the broker stops. This entry, the README, and the `ShrikeBroker` class javadoc all say so.

**Alternative rejected.** A configurable bind address now, defaulting to loopback. A read timeout implemented with `SO_TIMEOUT`.

**Why.** A bind address is one line of code and a promise this build cannot keep: the moment it is configurable, somebody sets it to `0.0.0.0`, and what is on the other side of that port is a broker that will append whatever it is sent by whoever can reach it. The knob belongs to the slice that makes exposure defensible — authentication first — and until then the loopback bind is the access control. What the review asked for, and what this entry is, is that the fact lives somewhere a reader finds it before deployment rather than only in a class javadoc.

The idle connection is an accepted, deferred exposure and is named as one. `SO_TIMEOUT` is not the tool: it bounds reads on a socket's *streams*, and the broker reads through a `SocketChannel`, whose blocking reads it does not bound at all — which is the same asymmetry the client entry describes from the other side. A real fix is a reaper thread that closes connections idle past a configured bound, with the bookkeeping to know what "idle" means for a fetch that is legitimately waiting 30 seconds. That is a slice's worth of work, and today the controls are the two this build does have: the loopback bind, so only a local process can hold a slot, and the connection cap, so the number of slots that can be held is a number rather than a hope. Both deferrals — the configurable bind address and the read or idle timeout — were tracked in #9, and both have since been done, as the two refinements at the top of this entry say.

## A key picks its partition on the client, and CRC32C is what picks it

**Decision.** Routing lives in `shrike-clients`. `PartitionRouter.partitionOfKey(key, partitionCount)` is `Math.floorMod((int) crc32c(key), partitionCount)`, and a record with no key takes each partition in turn starting at 0. A caller that names a partition is obeyed whatever its key would have hashed to: `ShrikeProducer.send(topic, partition, key, value)` is that path and it is unchanged. The broker does not route — a produce request has always carried an explicit partition and still does, so nothing about this decision is on the wire. The mapping is pinned by a table of literal vectors in `PartitionRouterTest`, for two partition counts, one a power of two and one not.

**Alternative rejected.** Routing on the broker, so a client could send a key and let the side that knows the partition count decide. A murmur-style hash, which is what a partitioner usually reaches for. A test that hashes the keys itself and checks the modulo it computes.

**Why.** Routing on the broker would be a protocol change — a produce that names no partition — and it would move a decision that belongs to whoever chose the key onto the one component that has to stay simple: the broker's produce path is a single writer per partition and knows nothing about keys, groups, or members, and every entry in this file that keeps it that way is worth more than the convenience. It would also make the partition a record landed on depend on the broker's build rather than on the sender's, which is the failure this decision is trying to avoid, only harder to see.

CRC32C is not the best-mixing hash available, and it is the right one here. It is already a dependency of the record frame — every stored record carries a CRC32C, `java.util.zip.CRC32C` ships with the JDK, and the hardware runs it — so choosing it adds no code to write, no code to test, and no second thing to freeze. A murmur-style hash would have to be implemented and then defended byte for byte forever, in a repository whose core depends on the JDK alone. What a partitioner needs is a spread across a handful of buckets, not resistance to somebody choosing keys to collide; `PartitionRouterTest` asserts that 400 keys reach all four partitions, and that is the property being bought. `Math.floorMod` rather than `%` because a CRC32C read as an `int` is negative for about half of all keys, and `%` would answer those with a negative partition.

The vectors are literals because a test that hashes the keys the same way the code does agrees with every rule, including a rule that changed between two releases. A changed mapping is not a loud failure: the records already stored stay where they are, the new ones go somewhere else, and one key's history is quietly split across two partitions with its order gone. Freezing eight keys, four raw byte arrays, and two partition counts costs twelve lines and turns that into a failing build.

## A member's partitions are arithmetic, and nothing rebalances them

**Decision.** A consumer group member is configured with three numbers — `GroupAssignment(groupId, memberIndex, memberCount)` — and owns the partitions where `partition % memberCount == memberIndex`. That is the whole assignment. The broker stores committed offsets keyed by group, topic, and partition, and nothing else: no members, no sessions, no heartbeats, no generations. A `memberCount` below 1, or a `memberIndex` outside `[0, memberCount)`, is refused where it is configured with a message naming both numbers. A group with more members than the topic has partitions is allowed, and the members past the last partition own nothing. A member that dies is replaced by a process started with the same index and count, which resumes from the last offset that index committed.

**Alternative rejected.** A coordinator on the broker: members register, heartbeat, are given partitions, and are declared gone by a session timeout. Letting a member discover the partition count from the broker rather than being told it.

**Why.** Dynamic rebalancing is a stated non-goal of this build, and this is what that non-goal costs and buys. A coordinator is not one feature: it is registration, heartbeats, a session timeout, a generation number, and a fencing rule for the member that was declared dead and comes back mid-batch anyway — and every one of those is a way for records to be delivered twice or not at all, on the broker, where this repository has been keeping the number of moving parts down on purpose. Arithmetic needs no state on either side, survives every process being restarted, and can be checked by reading two numbers off a command line.

What it costs is said plainly rather than hidden. The partitions of a member that is not running are read by nobody until an operator starts one with that index again — there is no other member that picks them up. Changing the size of a group means restarting its members with a new `memberCount`, and while that is happening the group is briefly inconsistent about who owns what. And two live processes configured with the same index is a mistake nothing here can detect, because nothing here talks to the other process: they read the same partitions and both commit, so records are processed more than once. That is the failure direction this design chooses — extra redelivery, which at-least-once delivery already allows, rather than a record nobody read. Fencing the second process would need exactly the broker-side membership this entry is refusing.

The partition count is a number the caller passes rather than one the client asks for, because this build has no api that describes a topic. A member is told the same three or four numbers a producer is told, and when a describe api arrives it can fill them in without changing what an assignment means.

## Records are processed before the offset that covers them is committed

**Decision.** `ShrikeConsumer.processThenCommit` hands records to a `RecordHandler` and commits the offset to read next — one past the last record handed over — only after that handler has returned. A handler that throws is not caught: the exception reaches the caller and nothing is committed, so the same records are read again. An empty list commits nothing at all. How many records go into one call is the caller's choice, so a commit can cover part of what one fetch answered with, and the records that were not handed over are simply read again next time.

**Alternative rejected.** Committing as soon as the records are handed over, or as soon as a fetch answers. Catching the handler's failure and committing anyway so the group keeps moving. Committing on a timer in a thread of the library's own.

**Why.** Every ordering here is a choice between doing work twice and never doing it at all, and this build has said which one it takes since its first README line. Committing first turns a process that dies mid-batch into records that nobody processed, that no consumer will ever be handed again, and that nothing in the system will report — silent loss, which is the one outcome a log-structured broker exists to prevent. Committing after means a process that dies between the work and the commit does that work again when it is replaced: duplicates are possible, and no record is lost. The cost is real and it is the caller's to handle — the offsets a handler is given are what an effect can be keyed on to make repeating it harmless.

Swallowing the handler's exception is the same trade wearing a disguise: the group moves on, the records are gone, and the only sign is a log line. A timer is worse than either, because it decouples the commit from the work entirely — the offset moves while a slow handler is still in the middle of the batch, and what is lost depends on the clock.

## The redelivery test kills a member that is holding work it never committed

**Decision.** `ConsumerGroupRedeliveryIT` runs five operating-system processes: a broker, a producer that lets a `PartitionRouter` place 40 keyed records over 4 partitions, the member that is killed, the member started in its place with the same index, and the group's other member. Each member writes one line per record into a journal of its own and forces that line to the device *before* the record counts as processed, and hands records over four at a time, which is what commits them. The member that is going to die is told to pause at one partition and offset: it journals that record and then waits on a latch nobody counts down. The test tails its journal for that exact line under a bounded await and only then calls `destroyForcibly()`. The replacement is started from the offsets read out of the broker's own `groups/<groupId>.offsets` file. The assertions are over the multiset union of the journals: every record produced appears at least once, every record the killed member journaled past its last committed offset appears twice, the replacement's journal for each owned partition is exactly the offsets from the stored commit to the high-water mark, and no partition appears in two members' journals. Two of the assertions exist only to stop the test passing on an empty run: the produced set is non-empty, and so is the set of records that came twice.

**Alternative rejected.** Killing the member after a delay, or after counting N records go by, and hoping the kill lands inside a batch. Asserting on what the member printed to standard output rather than on what it forced to a device. Starting the replacement from the offsets the killed member said it had committed.

**Why.** A kill that is timed is flaky in both directions and the bad direction is silent: land it a moment late and the member has committed everything it journaled, the redelivered set is empty, and every "appears at least once" assertion still passes over a test that proved nothing. The pause turns the kill point into a place in the data — when that journal line exists, the member has, provably, journaled two records past a commit the broker acknowledged, and it can no longer commit them because it is parked. From then on the test can take as long as it likes.

The journal is fsynced per line because SIGKILL runs no shutdown hook and flushes no buffer: what is on the device is the whole of what that process can be said to have done. Standard output would be a claim about intent — a `println` that never reached the file proves nothing about work that was done, and one that did proves nothing about work that was durable.

Reading the broker's group file rather than the dead member's own output is the same argument `ClientProcessIT` makes: the numbers the replacement starts from are the numbers the broker stored, not the numbers a dying process claimed. It does not follow that this test would catch a commit the broker acknowledged and then lost — the expectations here are derived from the same file the replacement is handed, so a lost commit moves the expectation and the observation together and the assertions still hold. `ClientProcessIT` is the test that catches that, because it pins the committed offsets it expects as literals. No api read a committed offset back when this test was written, which is why it reads a file whose format this document fixes; Slice 6's describe-group api reads one back now, and the argument above is why this test was not moved onto it.

## Retention deletes whole sealed segments, aged by the timestamps inside them

**Decision.** `LogConfig` grew `retention.ms` and `retention.bytes`, both `long`, both defaulting to −1, which means "no bound" and deletes nothing. `retention.ms` deletes a sealed segment once **the largest record timestamp that segment holds** is at least that many milliseconds behind the moment retention is evaluated at. `retention.bytes` then deletes the oldest sealed segments, one at a time, until the log files of that partition add up to no more than the bound. Only whole sealed segments are ever deleted, and the segment still taking appends is never one of them — a partition of one segment deletes nothing, whatever its age or size — so a partition can legitimately sit above `retention.bytes` by the size of that one segment, and this is stated in the README rather than rounded off.

The largest timestamp is tracked as the segment fills, and it is fixed when the segment is sealed. A segment reopened as sealed at startup has nothing to remember it from, because nothing writes it down: it reads the timestamp back out of the log file, and out of the **last frame** of it. That read costs a lookup in the sparse index for the position of the last indexed record and then a walk of at most `index.interval.bytes` of frames, so it is bounded by the index interval rather than by the size of the segment. A segment whose last frame cannot be believed reports no timestamp at all, and a segment with no timestamp is one time-based retention keeps.

**Alternative rejected.** Aging a segment by the file's modification time, which the operating system already keeps and which needs no read at all. And, for the age itself: the *first* record's timestamp, so a segment expires once its oldest record is old enough. Also considered: writing the largest timestamp into a small per-segment metadata file so a restart could read it in one syscall.

**Why.** A modification time is a fact about this copy of these bytes, not about the records in them. Restoring a partition from a backup, copying a data directory onto a new machine, or a filesystem that updates the time for a reason of its own would all reset every segment's apparent age to now — so a broker that trusted mtime would keep a week of data forever after a restore, and, worse, the same trust points the other way: a tool that preserved mtimes across a copy could make a freshly restored partition look ancient and have retention delete all of it on the first sweep. The timestamps are already in every frame, written from the injected `TimeSource`, and they say when the record was produced, which is the thing `retention.ms` is actually about. `SegmentedLogRetentionTest#datesAReopenedSegmentFromItsLastRecordRatherThanFromTheFilesOnDisk` sets every file's modification time to the instant the test runs and then proves the segments are still deleted, which is a test that fails the moment anybody reaches for `Files.getLastModifiedTime`.

Judging a segment by its oldest record would delete records inside their retention window: the segment holding offsets 0 and 1 goes as soon as offset 0 is old enough, taking offset 1 with it. The bound has to hold for every record in the unit being deleted, and the newest record is the only one that speaks for all of them.

Reading the last frame rather than remembering the number in a metadata file keeps the log the single source of truth, the same rule the offset index already follows: a number stored beside the data is a second copy that can disagree with it, and after a torn tail or a truncation it would disagree exactly when it mattered. The cost is one bounded walk per sealed segment at startup, which is the same order of work the index check beside it already does.

Defaulting both bounds to off is the last piece and it is not timidity. Retention is the only thing in this broker that deletes acknowledged records, so it deletes none of them until somebody has said, in the `LogConfig` a partition's log is opened with, how many and for how long. A default that kept a week or a gigabyte would be this document choosing what a user's data is worth. `LogConfigTest#keepsEveryRecordUntilRetentionIsAskedForByName` is the proof that a log opened without naming retention behaves exactly as it did before this slice existed.

## Deleting a segment: the start offset first, then the list, then the files

**Decision.** One deletion is three steps and the order is the whole of it. First `logStartOffset` — a volatile field on `SegmentedLog`, not a walk of the segment list — advances to the base offset of the segment that follows. Then that segment comes out of the in-memory list. Only then are its two files unlinked. A read below `logStartOffset` is refused with `OffsetOutOfRangeException` carrying that offset, and it is refused whether or not the file is still on disk.

**Alternative rejected.** Deleting the files first and letting the list and the start offset catch up, which is the order most naturally written. And, for readers already inside a file: copying each segment away, or reference-counting open readers and deferring the unlink until the last one is done.

**Why.** The two failure shapes are different sizes. Take the files away first and a reader that is part way through the segment list can find a segment that names a file which is no longer there, and the answer it gets is an I/O error about a missing path — a broker failing on its own housekeeping. Advance the offset first and the worst a reader can meet is the refusal it was always going to meet, one moment early, carrying the number it needs to carry on. The field is volatile for exactly that reason: the ordering is only worth anything if a thread that sees the shortened list cannot also see the stale offset beside it.

Reference counting is the part that is not needed, and POSIX is why. `unlink` removes a name from a directory; the inode and its blocks survive until the last open file descriptor on them is closed. A fetch already inside a segment therefore reads on to the end of what it asked for, from the file it opened, and gets whole frames that still checksum — the space comes back when it closes. That is not a claim taken on trust here: `SegmentedLogRetentionTest#readsASegmentWholeThroughAChannelOpenedBeforeRetentionDeletedIt` opens a channel, reads one frame through it, deletes the segment under it, reads the next frame through the same channel, and asserts the bytes match what was on disk before the deletion and still decode to the records they were. Copying a segment aside before deleting it would double the disk cost of retention to buy the property the filesystem already provides.

## Retention is one named thread, and it takes the partition's own lock

**Decision.** A thread named `shrike-retention` — one, for the whole broker — asks the topic registry to delete what it no longer keeps, once every minute. Between sweeps it waits on its own stop signal, a latch the broker counts down as it shuts down, rather than sleeping: the predicate is "this sweep is stopping", so a shutdown ends the wait at once instead of after the rest of an interval, and stopping the broker waits for a sweep in flight before any log is closed. The sweep itself is `RetentionSweep.runOnce()`: one synchronous method that reads the injected `TimeSource` once and does the whole decision on the calling thread. Deletion enters a partition through `Partition.deleteRetiredSegments`, under the same `ReentrantLock` that every produce and every fetch of that partition takes. A sweep that throws is a WARN and the thread lives; a partition that cannot be trimmed is a WARN and the sweep moves on to the next one.

**Alternative rejected.** A retention thread per partition. A `ScheduledExecutorService`. Doing the work on the appending thread, after the append that rolled a segment. And, for the lock: a second lock owned by retention, or a lock-free hand-off in which retention only marks segments and the next reader removes them.

**Why.** `SegmentedLog` says plainly that nothing in it is safe to call from two threads at once, and the segment list retention shortens is the same list a fetch walks. A second lock would be a second answer to who may touch that list, which is the shape of every concurrency defect that survives review. Taking the partition's own lock means retention is not a new concurrency story at all — it is one more caller taking its turn, and what it holds the lock for is a couple of file closes and an unlink rather than a read of the log, so a sweep is not a pause a connection can feel. Marking and deferring would move the deletion onto a connection thread, which is the one thread whose latency this broker is trying to protect.

One thread rather than one per partition, and rather than an executor, because the work is a walk of a handful of partitions once a minute: a thread per partition would be a thread per partition asleep, and an executor would be a pool and a queue in a place where the queue can only ever hold one thing. One named thread is also the only one of the three that a thread dump explains — PRINCIPLES §4 reserves the name, and `RetentionSweepTest#sweepsOnItsOwnNamedThreadUntilItIsClosed` proves the sweeping thread carries it and that closing ends it.

Splitting the decision out as `runOnce()` is what keeps the tests honest. Every retention test in this repository advances an injected clock and calls the sweep by hand; not one of them waits for a minute to pass, because how often production asks is not what retention means. The interval is a constant rather than a setting for the same reason a knob with no code behind it was refused earlier: nothing yet needs to tune it, and a partition that sits over its bound for up to a minute is what a bound on storage costs.

## Offset out of range is the one error that carries a body

**Decision.** An error response is still a code and an empty body, for eight of the nine codes. `OFFSET_OUT_OF_RANGE` — code 2 — now carries an eight-byte int64 body: the offset that partition can still be read from. The encoder and the decoder are symmetric about it and both are exact. `ResponseFrame.encodeError` refuses code 2 outright and points the caller at `encodeOffsetOutOfRange`, so a code 2 with no body cannot be written; the decoder refuses bytes behind any other code, refuses a code 2 whose body is not exactly eight bytes, and hands the number back as an `OptionalLong` that is present when and only when the code is 2. It reaches a caller of the client library as `BrokerErrorException.logStartOffset()`. No api key was added and no operation was added: keys 4 and 5 stay reserved and unimplemented.

**Alternative rejected.** Leaving the code as the whole answer and letting a consumer that has fallen behind retention guess — start again from 0, or skip to the end. A new api key that asks a partition for its offset range. Putting the number in the fetch *response* body instead, so that no error carries anything.

**Why.** Retention is what made the old rule insufficient. Before this slice a fetch was only ever out of range past the high-water mark, and a consumer that got there knew what to do: it had just been told the mark. Below the range was unreachable, because nothing deleted anything. Now a consumer whose committed offset was deleted while it was down gets code 2 and, without a number, has two choices that are both wrong — re-read everything that survived, or skip records that are still there. Neither is a decision it can make; both are decisions it would be guessing at. Eight bytes turn it into a decision its author makes with the number in hand.

The reasoning that kept error bodies empty still holds everywhere else, and this exception does not weaken it. What that rule protects against is a broker describing its own internals to whoever is probing it: which field a parser choked on, which of its files was unreadable. A log start offset is not that. It is the oldest offset the broker will serve to anybody who asks for it, so a caller learns nothing from the error that a legal fetch would not have told it a moment later.

A new api key would be the tidier-looking option and it costs a round trip on every occurrence of the case it exists for — and the case is a consumer that is already behind. It would also leave the same client able to receive a bare code 2 from a broker that had not been asked, which is the ambiguity this change removes. Putting the number in the fetch response was rejected because there is no fetch response: the request was refused, and inventing a success-shaped answer for a refusal would mean a client had to inspect a body to find out whether it had been served. The decoder's exactness is what keeps the wire honest either way — a frame that breaks either half of the rule is refused rather than half-read, which `ResponseFrameTest#refusesAnOffsetOutOfRangeResponseWithoutItsLogStartOffset` and `ResponseFrameTest#refusesAnErrorResponseThatCarriesABody` prove from both sides.

## A fetch's records go from the segment file to the socket, and one setting takes that back

**Decision.** `BrokerConfig` grew `fetch.zero.copy`, on by default. With it on, a fetch reaches the wire in two writes rather than one: `ResponseFrame.encodeFetchHeader` lays out the length field, the correlation id, the code, the high-water mark, and the size of the records block — the length already counting every record byte to come — that header goes out through the same `writeFully` every other frame uses, and then `FileChannel.transferTo` sends the record frames themselves out of the segment file, looping until the byte count the header promised has gone. With it off, the range is read into a buffer and written as one frame, which is what this broker did before the setting existed. Both paths ask `LogSegment` for the same range, located by one walk in one place, and `Partition.readable` is the only method the setting reaches.

**Alternative rejected.** Two settings, one for the fallback and one for the benchmark. Making the transfer unconditional and keeping no way back to the buffered path. And, for the shape of it: passing the choice down through `Partition` and `Connection` as a boolean argument.

**Why.** One setting does both jobs because both jobs want the same thing: the older path, unchanged, one restart away. A fallback that shares its new code with the thing it is falling back from is not a fallback, so `fetch.zero.copy=false` selects the path that was already there rather than a variant of the path that replaced it — the buffered read still goes through the segment's own channel and still allocates the array it always did. The A/B of the benchmark sub-slice is the same switch for the same reason: measuring a difference means running one broker twice with one thing changed, and that one thing has to be the whole of the difference. This is not the knob-with-no-code-behind-it that the flush entry refused, either; both paths ship with the setting, and each is proven by the same tests as the other.

The boolean never becomes an argument, because PRINCIPLES §2 bans that and because the alternative is better anyway: instead of a flag travelling with the data, the data got a shape. `Partition.fetch` answers with a `FetchedRecords` that is either `Copied` or `Pinned`; `Answer` gained a `Streamed` beside `Served`; and `Connection`'s switch over `Answer` will not compile if a shape is forgotten. Two small sealed variants buy a connection loop that cannot mistake a range that owns a file for an ordinary body.

What must not vary is the bytes, so the envelope is written in one place — `putEnvelope` — by both the whole-frame encoder and the header-only one, and `BrokerZeroCopyFetchTest#servesByteForByteTheSameResponseWithZeroCopyOnAndOff` compares raw socket bytes from the two settings over **one** data directory: the same files, the same correlation ids, six fetches covering a whole log, a fetch from the middle, one frame, a `maxBytes` landing inside a frame, an empty answer at the high-water mark, and the first-frame exception. Two directories would have compared two encodings — different timestamps, different checksums — and proved something else. Nothing here claims the transfer is quicker. Whether it is, and by how much, is a measurement, and the benchmark entry below is the one entitled to say.

## Sending bytes the operating system has not written out is safe, and the high-water mark is what bounds it

**Refined in Slice 5.** The flush sub-slice arrived, so two phrases below have moved. "Very nearly all of them" is now true of `interval` and false of `per-record`, where an acknowledged record has already been forced by the append that made it readable; and the last sentence — that a produce is acknowledged when its bytes are with the operating system and that this is the whole durability claim — is replaced by one sentence per mode in "Two flush modes, and whichever bound comes first is the one that forces". What this entry decides is unchanged in both modes and is the part worth keeping: a fetch never waits for a flush, and what bounds a range is the high-water mark rather than what has been forced.

**Decision.** A transfer may cover records that have been appended and not forced, which today means very nearly all of them. Nothing waits for a flush before a fetch is served, and the range is bounded by the high-water mark exactly as the buffered read is.

**Alternative rejected.** Forcing the segment before sending a range over it. Serving only the bytes below the last position that was forced, and making a consumer wait for the rest.

**Why.** There is nothing to wait for. The transfer reads the same file the append wrote, through the same page cache, so a record acknowledged a moment ago is readable at its position whether or not the device has seen it — the kernel does not have two ideas about the contents of one file. Forcing per fetch would turn every read into a write barrier and would quietly make the fetch path decide the durability policy, which belongs to the flush sub-slice and to nothing else.

The bound that matters here is visibility rather than durability, and it is already in place: a range is located against the high-water mark, so no byte of a record the broker has not finished acknowledging can be in one. What a produce promises is unchanged by this slice and is stated where it was — a produce is acknowledged when its bytes are with the operating system, and that sentence is still the whole durability claim.

## A transfer reads through a channel of its own, so retention can delete under it

**Decision.** The rule, in one sentence: **a range that leaves the partition lock carries a descriptor nobody else can close.** `LogSegment.openRange` opens a second, read-only `FileChannel` on the segment's log file, under the partition lock; the `RecordRange` that carries it is what closes it, on the connection thread, once the response is complete. Retention's three steps are unchanged from earlier in this slice — start offset, list, then close the segment's own channel and unlink its two names — and it never touches a descriptor a fetch is using. Nothing is reference-counted and no unlink is deferred.

**Alternative rejected.** Lending the connection the segment's own channel. Leaving the segment's channel open after the unlink until the log is closed. Reference-counting readers and deferring the unlink until the last one is done. Pausing retention while any fetch is in flight.

**Why.** Lending the segment's channel is the option that looks free and is not. Closing a `FileChannel` while another thread is blocked in an I/O operation on it raises `AsynchronousCloseException` in that thread — and that thread has already written a response header promising a byte count. What the client gets is a frame that stops in the middle and a stream it can never resynchronize, which is the one failure this protocol has no answer for. That is not an argument from the manual: the deletion-race test was first run against a build that lent the segment's channel, and it failed with the connection closed part way through the length the broker had promised. `BrokerZeroCopyDeletionRaceTest#finishesAFetchAlreadyOnTheWireWhenRetentionDeletesTheSegmentItIsBeingSentFrom` is what stands where that build failed: it takes a few bytes of a response of nearly four mebibytes off a socket with a sixteen-kibibyte receive buffer — so the broker is provably still sending — sweeps retention by hand, and then reads the rest of the promised length and checks it against the deleted segment's own bytes.

Leaving the segment's channel open past the unlink would leak a descriptor per deleted segment for as long as the broker runs, which is the opposite of what retention is for. Reference counting was refused earlier in this document and the reason has not changed: POSIX already gives this property to anybody holding a descriptor, so the cheapest way to hold one is to open one. The cost is a single `open` per served fetch, on an inode the kernel has open already, set against a copy of the whole range that the transfer no longer makes.

The lock is what makes it two cases instead of three. The channel is opened under the same partition lock the deletion takes, so either the range exists before the unlink — and then the inode and its blocks stay alive until the range is closed, however many names are left pointing at them — or it is located after the segment left the list, and then the offset is refused with the start offset that deletion has already published. There is no window between them for a fetch to fall into.

The last piece is what happens when something does go wrong. Once the header has gone, the response is finished or the connection is: `RecordRange.transferTo` raises an `IOException` rather than an unchecked exception, and `Connection` writes its `INTERNAL` frame only from the path where not a byte has been written yet, so a broker never puts a second frame on top of half of one. `RecordRange.close` logs rather than throws for the same reason — by the time it runs the bytes are already with the client, and a descriptor that would not close must not turn into an answer to a request that was already answered.

## Two flush modes, and whichever bound comes first is the one that forces

**Decision.** `LogConfig` grew three settings: `flush.mode`, an enum with two values and no third, plus `flush.interval.ms` and `flush.interval.bytes`. The default is `interval`, 100 milliseconds and 1 mebibyte.

What each mode promises, in the only terms this repository states it in:

- **per-record** — a produce is acknowledged only after `force()`, so an acknowledged record survives an operating-system or power failure.
- **interval** — acknowledged records survive a process crash (they are in the page cache), but up to one flush interval of acknowledged records can be lost on an operating-system or power failure, after which recovery truncates the torn tail.

Neither sentence says anything about delivery, and that is deliberate. Delivery is at-least-once in both modes, this slice does not touch it, and the two are separate axes: a flush mode says what a failure of the machine may cost, and at-least-once says what a failure of a consumer may cost. Neither may be described as implying the other.

"Whichever comes first" is two triggers in two places. The volume bound is checked by the append that crosses it, inside `SegmentedLog.append`, before that append returns. The time bound is `SegmentedLog.flushIfDue(nowMillis)`, one synchronous method that the `shrike-flush` thread calls once per `flush.interval.ms` and that a test calls by hand. Every force is `force(true)`, metadata included, and it covers the log file alone. `flush.interval.ms` is measured from the last *interval* flush rather than from the last force of any kind, and sealing a segment resets the unforced byte count without touching that clock.

**Alternative rejected.** A third mode, `none`, forcing nothing at all. Checking the volume bound on the flush thread too, so that every force happens in one place. Restarting the interval clock on every force. Forcing the index with every flush. A string setting rather than an enum.

**Why.** A byte count only moves when something is appended, so an append is the only moment at which it can be seen crossing its bound. A volume bound checked once an interval is not a bound at all: a partition taking records quickly would sail past a mebibyte by however much arrived in between, and the setting would name a number the log does not respect. That is the same reasoning that puts a roll on the record that would exceed `segment.bytes` rather than on a sweep that notices afterwards, and it is what makes "whichever comes first" exact rather than approximate.

The interval clock is the other half of the same honesty, and it is the subtle part. `shrike-flush` asks exactly as often as `flush.interval.ms`, and a poller that asks every interval about a threshold of one interval can only hold the exposure to one interval if the two stay in phase. Measuring from the last interval flush keeps them in phase: an off-schedule force — the volume bound, a seal, a per-record append — empties the unforced bytes without moving the clock, so the next record is still forced at the first pass that comes a whole interval after the last one. Restarting the clock on every force is the reading that looks more natural and is wrong: a record appended just after a volume flush would then wait almost two intervals for the next pass, while this document went on promising one. A log that has never flushed on the interval has no phase yet, so it is due at the first ask rather than at a moment it guessed at when it opened — which is also why opening a log reads no clock at all. Sealing resets the byte count for the opposite reason — the seal already forced those bytes, so counting them again would flush a new segment early on a debt that has been paid.

The index is not forced with a flush because it is derived data and the tail segment's index is rebuilt from its log at every start: forcing it would be a second fsync per flush buying a file that recovery is going to rewrite anyway. `seal()` still forces it, because a sealed segment's index is only checked at startup and rebuilt only when that check fails.

A `none` mode was refused because it is a name for what `interval` already does when nobody asks it to flush, and because it would let a deployment switch off the one mechanism that makes the interval sentence true while the sentence stayed in the README. The mode is an enum rather than a string for the reason PRINCIPLES §1 gives: a spelling this build does not understand has to be a compile error, not a broker that starts and quietly keeps a promise nobody chose.

`interval` is the default because an fsync per record is a cost a deployment should choose rather than inherit — the numbers that make the choice are under Benchmarks in the README — and because it is the mode in which the recovery this repository has already proven does the work it was built for. `per-record` is what a deployment picks when losing an acknowledged record is worse than answering slowly, and the entry below is what it costs.

## An fsync is taken under the partition's own lock, on whichever thread asked for it

**Decision.** Every force goes through the partition's `ReentrantLock` — the same one every produce, every fetch, and every retention sweep takes. Which thread is holding it depends on the trigger: a connection thread for a per-record produce and for the append that crosses `flush.interval.bytes`, and `shrike-flush` for the interval. Nothing is forced outside that lock. There is no second lock, no volatile counter, and no lock-free hand-off.

**Alternative rejected.** Deciding due-ness under the lock, taking a copy of the channel, and performing the `force()` after releasing it — the shape that keeps an fsync off a lock, and the one that has to be argued against rather than ignored. A lock of flushing's own. Forcing through a descriptor of its own, the way a zero-copy range reads through one.

**Why.** What decides whether a flush is due is the log's own mutable state: how many bytes are unforced, when the interval was last measured from, and which segment is the active one. That state has exactly one guard, and it is this lock. Forcing outside it would mean publishing three fields to a second thread and proving they stay consistent with each other and with a roll happening between them — a new concurrency story bought to save latency on a path that is not the one it appears to be.

Ownership of the channel is the second half of the argument, and it is the concrete one. `close()` closes the active segment's channel under this lock, and closing a `FileChannel` while another thread is inside an I/O operation on it raises `AsynchronousCloseException` in that thread — which is exactly the failure the zero-copy entry above documents from the other direction. A flush running outside the lock would need a descriptor of its own to be safe, the way a `RecordRange` does, and that is an `open` per interval per partition spent to avoid a lock this broker already takes to read a single record.

What the lock costs is worth stating rather than waving at. An fsync serializes with the appends and the reads of one partition — the same partition whose log is a single writer by construction, whose retention sweep takes this lock to unlink a file, and whose fetches take it to read bytes off a disk. What it does not cost is a waiting fetch: `await` releases the lock, so a long poll holds nothing while it waits and a flush cannot lengthen anybody's `maxWaitMs`. And in `per-record` the serialization is not a cost at all but the promise itself — a produce is waiting for its own force, so a partition answers one produce at a time at the speed of its device, which is what per-record durability means when it is priced honestly.

`shrike-flush` is one thread for the whole broker rather than one per partition, for the reason `shrike-retention` is: a thread per partition would be a thread per partition asleep, an executor would be a pool and a queue where the queue can hold one thing, and one named thread is the only one of the three that a thread dump explains. PRINCIPLES §4 reserves the name, and `FlushSweepTest#flushesOnItsOwnNamedThreadUntilItIsClosed` proves the flushing thread carries it and that closing ends it. Stopping the broker closes that sweep before any log is closed, so a pass in flight finishes with its lock rather than meeting a channel that has just been closed under it.

## The benchmarks are test code, so JMH rides in test scope and runs from a profile

**Decision.** `shrike-core` takes one new dependency — `org.openjdk.jmh:jmh-core`, **test scope** — plus `jmh-generator-annprocess` on the annotation-processor path of the *test* compilation alone. The benchmarks live in `shrike-core/src/test/java/io/shrike/core/bench/`. They are compiled by every build and run by none of it: surefire excludes `**/bench/**`, and the one way to run them is `mvn -pl shrike-core -P bench test-compile exec:exec`, a profile nothing activates by itself. The `bench` profile runs `org.openjdk.jmh.Main` through `exec-maven-plugin` with `classpathScope=test` and the executable `java`, which resolves through the jdk toolchain this reactor already requires. Nothing in `src/main` names JMH, and the enforcer rule that bans every non-test dependency of core is unchanged: it is what proves the engine still depends on the JDK alone, rather than this paragraph.

**Alternative rejected.** A fourth module, `shrike-bench`, depending on core with JMH at compile scope — the arrangement JMH's own documentation recommends. And, in the other direction, hand-written timing: a loop, `System.nanoTime`, and an average, so that no dependency arrives at all.

**Why.** A separate module would put a benchmark harness at compile scope in something this reactor builds and publishes, and it would buy a boundary that test scope already draws — JMH cannot reach `src/main` from where it is, and the rule that keeps it out is a build failure rather than a convention. It would also cost the thing that makes benchmarks worth keeping in a repository at all: these compile against the log in every `mvn verify`, so a benchmark that no longer matches the code it measures fails CI like any other class. A benchmark kept outside the build is a benchmark that rots quietly and produces a number nobody can reproduce.

Hand-written timing is the alternative that looks free and is wrong in the direction that flatters. A loop around `nanoTime` measures a method the JIT has not finished compiling, in one JVM whose profile is polluted by whatever ran before it, and it can produce a mean and nothing else — and a mean is exactly the statistic that hides the fsync tail this slice exists to price. Forks, warmup, dead-code elimination, and per-invocation samples are all things JMH already does correctly, and four test-scope jars is what they cost.

Two smaller pieces of the wiring are worth writing down because both are failures waiting for whoever removes them. JMH generates a runner class per `@Benchmark` named `<benchmark>_jmhTest`, which surefire's default `**/*Test.java` include matches, so without the exclusion `mvn verify` would hand JMH's generated runners to JUnit and count them among the tests. And the executable is `java` rather than a path so that the toolchain resolves it: `exec:java` would have run the harness inside the JVM that launched Maven, which on this machine is a Java 25 JVM the reactor deliberately does not build with, while `exec:exec` through the toolchain runs the harness on the same JDK 21 the tests run on and JMH's forked JVMs inherit it from there. Which JVM actually ran is not taken on trust either: it is a field in the raw JMH result that the benchmark commit records.

## A throughput and a p99 are two different measurements, and closed-loop says which p99 this is

**Decision.** Two benchmarks, and what each one publishes is stated rather than inferred. `FlushPolicyBenchmark` measures one `SegmentedLog.append` under each `flush.mode` in **two** JMH modes: `Mode.Throughput` for the rate and `Mode.SampleTime` for the tail. `FetchPathBenchmark` measures one fetch of a fixed 1 MiB range served both ways, into a connected pair of loopback `SocketChannel`s drained by a thread named `shrike-bench-drain`, plus a third method that writes the same bytes into that same pair with no log behind it, so that what both fetch paths pay for the socket is a committed measurement rather than a remark. Both run one thread, 2 forks, 3 one-second warmup iterations and 5 one-second measurement iterations, with no JVM arguments of their own; the whole suite takes about two minutes. **Every percentile this repository publishes is labelled closed-loop service time**, in the README table and here. The raw JMH JSON is committed as it was written, and the README quotes the commit, the machine, and the exact `java -version` beside every number.

**Alternative rejected.** Reading a p99 off `Mode.Throughput` or `Mode.AverageTime`, which are the modes a rate wants and are one run rather than two. A null `WritableByteChannel` as the fetch sink, or a second file. A benchmark-only flag choosing between the two fetch paths. And, for the tables: a ratio — "N times" — instead of two rows side by side.

**Why.** A throughput mode and an average mode both aggregate every invocation of an iteration into a single number before anything else sees it, and a mean cannot be turned back into a percentile: the samples a tail is made of are exactly the ones the mean has already dissolved. `Mode.SampleTime` timestamps individual invocations and keeps a histogram of them, so it is the only mode a p99 can honestly be read from. It is not free — two `nanoTime` calls ride on every sampled invocation — which is why both modes are run rather than one: the throughput row is what a rate should be quoted from, and the sample row is what a tail should be quoted from. It also decides how many samples there are to speak from, and that count is not the number of invocations, which is why it is published beside the percentile rather than left to be inferred from the rate. JMH's sampling stub times an invocation only when a cheap random mask says to, and once the samples it has kept in an iteration pass `targetSamples` — twenty per millisecond of iteration, so twenty thousand for the one-second iterations here — it halves the buffer it holds and widens the mask by a bit, then goes on sampling at half the rate it did. That decimation is the mechanism, and it is why the two counts do not stand in the ratio the two rates do. `per-record` never reaches the bound: at roughly four milliseconds an append there are only some 2 500 invocations in the ten measured seconds to sample, and it keeps 2 492 of them, near enough every one. `interval` crosses it repeatedly: its 333 677 samples are what survives decimation out of some 4.86 million invocations — reading that count off the throughput row — or about seven per cent of them. The reason to print both counts is that a p99 over two thousand samples is a thinner number than a p99 over three hundred thousand, and the reason to call them samples is that the larger one is not a count of appends. `SampleTime` runs take two forks for the same reason: one JVM's compilation and page-cache history is not a sample of anything.

Closed-loop is the other half of reading those percentiles correctly. The harness issues the next append only once the previous one has returned, so there is no arrival process and nothing queues behind anything: what is measured is **service time** — how long the log took — and not response time, which is service time plus whatever a request waited behind. Under an open-load arrival rate the broker does not control, waiting is most of what a p99 is made of, so a closed-loop percentile understates it. That is a fine thing to publish and a terrible thing to publish unlabelled, because an unlabelled p99 reads as a promise about what a client will see. Hence the label in every row, and hence this paragraph.

The sink is a socket because `transferTo` is only itself when the destination is one. `FileChannel.transferTo` reaches the kernel's file-to-socket path for a `SocketChannel`; to an arbitrary `WritableByteChannel` the JDK falls back to reading into a buffer and writing it — which is the other path exactly, so a null sink would have compared the buffered path with itself and reported the difference as noise. A second file is refused for a different reason, and the mechanism matters: a `FileChannel` destination is a trusted target rather than an arbitrary one, so a transfer of this size maps the region and writes it through rather than taking the buffered fallback. A file sink would have measured a real transfer path — just not the one this broker takes, which is a fetch going out of a segment file onto a connection. A loopback pair with a drainer is what the broker does minus the network, and the cost is stated rather than hidden: both rows include loopback TCP and the drainer thread, so neither is a measurement of a disk, and the difference between them is what is left when both have paid the same socket. The drainer exists because a benchmark writing into a socket nobody reads measures a socket buffer filling up.

What that shared socket costs is a third `@Benchmark` in the same class rather than a remark beside the table, and that is the correction worth recording. `FetchPathBenchmark.writeRangeToTheSinkAlone` writes the same 1 048 478 bytes into the same loopback pair with no log behind it — no range located, no file read, no descriptor opened — under the same forks, the same warmup, and the same `-rff` plumbing as the two fetch paths, so its score lands in the same committed JSON theirs do and the three can be compared without reaching across runs. It measured 14 637.6 ± 213.2 writes a second: 68.3 µs to put the mebibyte on the socket, against 389.5 µs and 443.8 µs to serve it. The sink is therefore 17.5% of the transfer row's time and 15.4% of the buffered row's — neither row is bound by it, and neither row is free of it. Taking the same 68.3 µs off both widens the 13.9% the two published rows differ by to 16.9%, which is the direction that matters: the table understates the difference between the two paths rather than flattering it. It is deliberately not a row in that table, because it is not a path a fetch can take.

**Alternative rejected.** What this section said before: a probe run by hand, outside the harness, and never committed. Its number was 27% above what the committed benchmark measures, and the percentages derived from it were wrong by about as much. The qualitative reading survived — the socket was never what either row was bound by, so the `transferTo` difference was always real — but the figures did not, and there was no artifact in the repository against which anyone could have found that out. A number this repository publishes has to come from a file this repository commits; the cost of that rule is one more `@Benchmark` and about sixteen seconds of suite time, which is not a cost.

The A/B is the `fetch.zero.copy` switch itself. `Partition.readable` chooses between `log.openRange(...)` with `RecordRange.transferTo` and `log.readRange(...)` with `ByteChannels.writeFully`, and the two `@Benchmark` methods call those two pairs and nothing else — a third path written for the benchmark would have measured the benchmark. The same reasoning as the zero-copy entry above, arriving from the other end: measuring a difference means changing one thing, and that one thing has to be the whole of the difference. The setup refuses to run unless both paths locate a range of the same size, because two byte counts compared is not two paths compared.

No ratio is printed, and that is a rule rather than a formatting preference. "N times faster" is the sentence that survives being copied out of a table and away from the machine, the commit, and the footnote that qualify it, and this repository has no way to make it true of a machine it never ran on. Two rows beside each other say the same thing to a reader who wants it and carry the conditions with them. The percentages in the sink paragraph above are as close as this comes to one, and they are kept where their conditions are: in prose, with this machine named beside each of them, and there to say that the tables understate a difference rather than to sell it. Neither table prints one. The footnote those numbers most need is the one the README makes largest: `per-record` was measured where `FileChannel.force()` is `fsync(2)` and not `fcntl(F_FULLFSYNC)`, so the force being timed does not push the drive's cache to the media — a weaker durability than the sentence `per-record` mode is described in, measured on the platform this repository is developed on and stated where the number is.

## Describing topics and describing a group are read-only apis that disagree about what "not here" means

**Decision.** Api key 4 is describe topics and api key 5 is describe group, both at version 0, and neither writes a byte. A describe-topics request is a count of names and then that many of them, where a count of zero means every topic this broker holds rather than none of them; each topic is answered with its folded name and one entry per partition, carrying the partition number, its log start offset, its high-water mark, how many segments it spreads over, and one byte count that is its log files and its index files added together. A describe-group request is one group id, and it is answered with one entry per partition that group has committed an offset for — topic, partition, and the next offset to read — in the order the store keeps them, which is topic and then partition. **A describe that names a topic this broker does not hold is refused with `UNKNOWN_TOPIC_OR_PARTITION`; a describe of a group this broker has never heard of is answered with `NONE` and no entries at all.**

**Alternative rejected.** One `describe` api with a flag saying which of the two things is being asked about. A new error code — `UNKNOWN_GROUP` — so that the two apis refuse a missing thing the same way. A `describesEveryTopic` boolean beside the list, rather than an empty list meaning all. Reporting the spelling a topic was created with instead of its folded name. Reporting log bytes and index bytes as two numbers, since the log already knows them apart.

**Why.** A topic and a group are not the same kind of thing, and the apis say so rather than pretending otherwise. A topic exists because somebody created it: it has a registry line, a directory per partition, and a partition count that cannot change, so "is there a topic called this" has an answer and a caller that spelled a name out is owed it. A group has none of that. There is no create-group api and no group registry — a commit is what brings a group into being — so a group that has committed nothing and a group that does not exist are the same state, all the way down to the filesystem, where both are the absence of one file. An `UNKNOWN_GROUP` code would be this broker claiming to know a difference it cannot observe, and the error codes are frozen precisely so that a code never comes to mean "we guessed". The empty answer says exactly what is true: this group has committed nothing here.

One api with a flag would be a boolean parameter on the wire, which is the protocol-shaped version of the flag parameter PRINCIPLES §2 bans; two api keys cost two numbers out of an int16 and let each one grow a version of its own. The empty list means "all" for the same reason: the wire carries a count, "describe no topics" is a request nobody sends, and a second field to say so would be a second thing that can disagree with the first. `DescribeTopicsRequest.everyTopic()` and `describesEveryTopic()` are what keep that from reading as a magic number at either end.

The folded name is the identity. `orders` and `Orders` are one topic — that entry is above — so folding is what makes a describe of a topic and a describe of a group name the same topic the same way, and a caller can match one answer against the other without folding anything itself. The created spelling is what the registry file lists and it is one `topics` file away for anyone who needs it; what an api answers about is identity. Bytes are one number for the same reason the caller is asking: what a partition costs on a disk is the sum, and the split between records and the index that finds them is the log package's business, which a later index format could change without changing what a disk holds.

Both bodies are decoded under the rules the request codec already had: a count is refused if it is negative, if it is past the cap a request may name, or if the frame does not hold the fewest bytes that many entries could occupy, and nothing is sized to a count until it has survived all three. That rule runs on the *response* side too, in the client's codec, because a client reading four bytes off a socket is in exactly the position the broker is: the thing on the other end is whatever answered on that port.

## Describing lives with the thing described: topics on `ShrikeTopics`, groups on a `ShrikeGroups` of its own

**Decision.** `ShrikeTopics.describe(List<String> names)` and `ShrikeTopics.describeAll()` sit beside `create`, and `ShrikeGroups.describe(String groupId)` is a new client with the same shape as `ShrikeTopics`: `AutoCloseable`, a constructor taking a `BrokerConnection` it then owns, and a `static open(ClientConfig)` that opens one of its own. Each method is one line over `BrokerConnection.call`, and each returns the protocol's own records — `List<TopicDescription>`, whose partitions are `PartitionDescription`s, and `List<GroupOffset>` — rather than a client-side copy of them.

**Alternative rejected.** A `ShrikeAdmin` collecting both describes, which is the type this repository has already turned down once. Describing a group on `ShrikeConsumer`, which is where a group id already appears. A separate `describe(String name)` overload for the one-topic case, and a varargs `describe(String... names)` where no argument means all. Client-side records — a `TopicReport`, a `CommittedOffset` — so that the client library's return types are its own.

**Why.** `ShrikeAdmin` would be a name for "the rest", and this document rejected it when `ShrikeTopics` was written: the types this repository bans are banned for being named after their own vagueness. Two describes are two things about two subjects, and each one goes where its subject already is. `ShrikeConsumer` is the wrong home for the group describe for the reason `ShrikeProducer` was the wrong home for `create`: a consumer is a member of one group doing work, and it lives as long as there is work; the thing asking where a group has got to is usually watching from outside, often from another program, and it has no records to process. It also has no member index, which every other group-shaped thing in this library needs.

An empty list means "every topic" on the wire, and `describeAll()` is what keeps that from reading as `describe(List.of())` — which at a call site says "describe nothing" and does the opposite. Varargs would put the same trap in the language: `describe()` compiles, means all, and looks like a mistake. Two named methods cost one line each and neither can be misread.

The description records come from `io.shrike.core.protocol` and are handed straight back, which the boundary entry above already allows — "the request and response records" are on the client's side of the line. It is the `StoredRecord` argument again: a second, identical record would be free to disagree with the first about what a partition count or a committed offset means, and there is nothing for the copy to add. What the client library owns is the *call* — bounded, blocking, one at a time, with a typed failure — not a second spelling of the answer.

## The process harness is published as a test-jar rather than copied into the module that needs it

**Decision.** `shrike-clients` attaches its test classes as a second artifact through `maven-jar-plugin`'s `test-jar` goal, so that `shrike-admin` can start a real broker process for its own integration tests without a second copy of the harness. Four members become public — `JavaProcess.start`, `JavaProcess.output`, `JavaProcess.destroyTree`, and `Await.brokerPort` — and everything else in those two classes stays package-private; `BrokerProcessMain` was already public because a child JVM has to name it on a command line. The plugin version is pinned in the reactor parent, like every other plugin this build runs.

**Alternative rejected.** Copying `JavaProcess`, the ready-file half of `Await`, and `BrokerProcessMain` into `shrike-admin`'s test sources — around 260 lines. Also rejected: leaving the helpers package-private and writing `shrike-admin`'s integration tests in the `io.shrike.clients` package so that they could still see them.

**Why.** The harness is not a convenience; it is where this repository's rules for process tests actually live. A child JVM is started with the `java.home` the fork runs on and the classpath the fork was given. A ready file is either whole or absent, so waiting for a broker is an existence check rather than a guess. The wait is bounded, gives up early when the process it is waiting for has already died, and quotes that process's output when it fails. The destroy takes descendants first and runs on every outcome. Two copies of those rules are two places for one of them to rot, and the copy would rot silently, because no test compiles both. Publishing costs one pinned plugin and four `public` keywords.

Writing the admin tests in `io.shrike.clients` would have kept the helpers hidden, at the price of a package name that lies about which module its classes belong to. That is the worse trade: a test-jar is a published artifact, and the part of it another module uses is public on purpose rather than by accident.

## The admin facade reads a running broker over the wire, and never reads its files

**Decision.** `shrike-admin` is a client of a broker that is up. Every number it publishes arrives over the TCP protocol through `shrike-clients`: describe topics for the two topic endpoints, and describe group followed by describe topics for the lag endpoint. It opens no file the broker owns, and it is configured with a host and a port and no path at all — `shrike.broker.host` and `shrike.broker.port` are the whole of what it knows about the broker. A facade pointed at a broker that is not listening answers 503 rather than falling back to anything.

**Alternative rejected.** Reading the data directory read-only: listing `<topic>-<partition>/`, parsing segment file names for base offsets, reading the tail of the active segment for a high-water mark, and parsing `groups/<groupId>.offsets` for the commits. No socket, no dependency on the broker being up, and no protocol version to keep in step.

**Why.** The broker is the single owner of its state, and that is worth more than the convenience. A second reader of those files is a second implementation of segment naming, index layout, torn-tail recovery, and the group file format, kept in step with the first by nothing but attention — and the day they disagree, the facade is the one telling an operator a number that is not true. It would also race the broker it is describing: retention deletes a segment between the listing and the read, an append lands while a frame is half-written, and the reader either fails or reports a state that never existed. Over the protocol none of that is reachable. The broker reads a partition's five numbers in one pass under that partition's own lock, so a description names one instant, and the facade is shown exactly what any other client would be shown and nothing more.

The cost is real and accepted: this facade is useless while the broker is down. That is the honest position, because a broker that is down has nothing to describe, and a 503 saying "broker unreachable" is a truer answer than a number recovered from files nobody is maintaining.

## Three GET endpoints, response records of the facade's own, and one shape for every failure

**Refined by the security review.** "One shape for every failure" was true of every failure a handler raised and false of four routes that never reached one. `/error` is a path like any other and answered Spring Boot's own body — with `Accept: text/html`, its whitelabel page; `/WEB-INF/x` and `/META-INF/x` are refused by Tomcat inside the container, forwarded to `/error`, and answered there in that same foreign shape, timestamp and caller's path included; and a request target Tomcat will not parse — a broken percent-escape, a request line longer than the header buffer — was answered with an HTML page written before a servlet existed to be asked. The two properties this entry names were doing what they claimed and were never enough on their own, because both of them are about the dispatcher, and none of those four go through it.

Two things close it. `ErrorEndpoint` implements Spring Boot's `ErrorController`, which stands `BasicErrorController` down and makes `/error` — the one place all of the servlet container's forwards arrive — answer in `ErrorBody` like everything else; it resolves the status the forward carried, and it answers a *direct* `GET /error`, which carries no forward and therefore no original status, as 404 rather than inventing a failure that did not happen. `ShrikeAdminApplication.containerErrorReports` then removes Tomcat's `ErrorReportValve` from the host's pipeline, so a request refused before the servlet stack is answered with its status code and an empty body. Turning that valve's `showReport` and `showServerInfo` off is not enough and Spring Boot has already done it: those two drop the report table and the version footer, and the page around them — a title and a heading naming the status — is written regardless. The alternative rejected was a template named `error`, which would have answered browsers with a page and machines with the framework's body, which is two shapes rather than none.

The 4xx logging changed with it, and for a reason that is not about shape: every failure was logged with its throwable, so a caller could spend forty stack frames of somebody else's disk per 404 it chose to send. A 4xx is now one line at debug and no throwable; a 5xx keeps its level and its cause. `ShrikeBroker` applies exactly that rule to the connections it refuses, and this is the same argument in the same words.

**Decision.** `GET /api/v1/topics` answers `{"topics":[{"name":"orders","partitionCount":3}]}`, and a broker holding no topics answers `{"topics":[]}` with status 200. `GET /api/v1/topics/{topic}` answers `{"name":"orders","partitions":[{"partition":0,"logStartOffset":0,"highWaterMark":42,"segmentCount":1,"bytes":1234}]}`. `GET /api/v1/groups/{group}/lag` answers `{"group":"g1","partitions":[{"topic":"orders","partition":0,"committedOffset":10,"highWaterMark":42,"lag":32}]}`. Those bodies are records in `io.shrike.admin` — `TopicListing`, `TopicSummary`, `TopicDetail`, `PartitionDetail`, `GroupLag`, `PartitionLag` — rather than the protocol's own records handed to a JSON codec.

**Lag is computed here, and the order the two answers are read in is the reason it is safe.** The broker does not subtract anything: it answers what a group committed and what a partition holds, and `PartitionLag.between` takes the difference. The group is described **first** and the topics **second**, so `committed_before <= committed_now <= highWaterMark_now <= highWaterMark_after` and the difference cannot come out negative. It is checked anyway and refused as an internal failure if it ever does.

**Every failure is `{"error":"<one sentence>"}` and nothing else.** Unknown topic — the broker's `UNKNOWN_TOPIC_OR_PARTITION` — is 404. A group that has committed nothing is 404. A path this facade does not serve is 404 and a method it does not answer is 405. A name the protocol will not carry is 400, with the name rule's own sentence. A broker that cannot be reached or does not answer in time is 503. An answer this client cannot believe is 502. Anything else at all is 500 with the words `internal error` and no other detail. `server.error.include-message`, `include-exception`, `include-stacktrace`, and `include-binding-errors` are pinned to their own defaults in `application.properties`, `spring.web.resources.add-mappings` is false, and `spring.mvc.throw-exception-if-no-handler-found` is true, so an unserved path reaches the same advice as everything else instead of Spring's default error body.

**Alternative rejected.** Serializing `TopicDescription`, `PartitionDescription`, and `GroupOffset` from `io.shrike.core.protocol` straight to JSON, which is what the client library itself does with them. Letting the broker compute lag and answer it in the describe-group response. Describing the topics first and the group second. Spring's `ProblemDetail` body, or Spring Boot's default error attributes, instead of a shape of this facade's own. Answering every failure with the exception's message.

**Why.** The client library hands the protocol's records back because a second copy of a wire record could only disagree with the first. A JSON body is a different thing: it is published to programs outside this repository, so it must be able to hold still while a wire record moves, and it must be able to carry a field — `lag` — that the wire does not have. Owning the records is also what makes the shape reviewable: the JSON is the record declaration, in order, rather than whatever a codec's introspection decides to expose today.

Lag belongs here because the broker cannot compute it without inventing a coupling it does not have: the group store and the partition would have to be read together, under two locks, to answer a question no producing or consuming client asks. Reading the topics first would put an append between the two answers and let a group appear to have read records that did not exist when it committed — a negative lag, which is a number no reader should ever have to interpret.

One shape for every failure means a caller writes one parser. Excluding the exception's message from that shape is not shyness — it is that these messages are written for a log, they name correlation ids and byte counts and sometimes the caller's own hostile input, and an admin facade that echoes them is an admin facade that leaks. The one exception is the name rule, whose message is a sentence about the rule and a quoted, truncated copy of what the caller itself sent; and it is reached only through `UnusableNameException`, so an `IllegalArgumentException` raised by anything else is answered as the 500 it is. Everything a caller is not told is logged here with its cause.

A last detail worth writing down: the path variables are named in the annotations, `@PathVariable("topic")` rather than `@PathVariable`, because this build does not compile with `-parameters` and a name that only exists in debug metadata is a name that can vanish.

## The facade opens a connection per request and closes it before it answers

**Decision.** Every endpoint opens the client it needs inside a try-with-resources and closes it in the same method. The lag endpoint opens two in turn — groups, then topics — and never both at once. Nothing is pooled, cached, or kept between requests.

**Alternative rejected.** One long-lived `BrokerConnection` shared by every request, opened at startup.

**Why.** The wire protocol is one socket carrying one call at a time: a request is written, its answer is read, and the correlation id is what proves the two belong together. Sharing one connection between HTTP requests would therefore mean a lock, and every concurrent request would queue behind it — an admin facade that serializes itself. Worse, a connection closes itself on a timeout or an I/O failure, because a socket that failed part way through a frame cannot be resynchronized; a shared one would take every later request down with it until something noticed and reopened it. A connection per request costs one TCP handshake to loopback, is thrown away the moment it misbehaves, and cannot be poisoned by the request before it. For a facade a person refreshes now and then, that is the right trade.

## `shrike-admin` takes one framework dependency, and it is `spring-boot-starter-web`

**Refined by the security review.** This module was put on Spring Boot 3.5.16 — the last release of the 3.5 line — and that line's free support ended on 2026-06-30, before the version was written into this POM. Adopting a version past its community end of life was not noticed at the time and is recorded here rather than quietly corrected, because the cost is ongoing and somebody reading this build should meet it here rather than in a scanner's output. What it costs: no further patch releases will arrive on this line for free, so every advisory against something the BOM pins has to be answered by hand. Two already were. `shrike-admin`'s own `dependencyManagement` now imports `jackson-bom` and pins the three `tomcat-embed` artifacts **above** the `spring-boot-dependencies` import, because the first declaration of a coordinate is the one Maven keeps and a `<properties>` override — the mechanism `spring-boot-starter-parent` documents — does nothing at all to a BOM that is imported rather than inherited. Every such override is a version this build now owns and has to watch, which is exactly the maintenance the line was supposed to save.

**The intended path is a move to the 4.1.x line, as a slice of its own.** Not a bump inside another commit: Boot 4 moved packages, and the two things this module leans on hardest — `ErrorController` and the way the embedded Tomcat factory is customized — both live in packages that were rearranged, so the change is a slice with tests to re-run and a DESIGN entry of its own rather than a version number edited in passing. Until that slice, this build states what it is on: a Boot line whose free patches have stopped, with the two coordinates that needed patching pinned by hand, and no third-party dependency in the two modules that matter — `shrike-core` runs on the JDK alone, and `shrike-clients` names nothing but `shrike-core`.

**Decision.** `spring-boot-starter-web`, declared without a version because the `spring-boot-dependencies` BOM imported by this module pins it. It brings the embedded server, the request mapping, and the JSON codec. Nothing else Spring publishes is on this build's path — no actuator, no security, no template engine, and no `spring-boot-starter-test`; the tests are JUnit 5 and the JDK's own `HttpClient`. The `repackage` goal of `spring-boot-maven-plugin` is activated so that the module produces a runnable `shrike-admin-<version>.jar`, and failsafe is given `<classesDirectory>${project.build.outputDirectory}</classesDirectory>` because after repackaging, the module's classes live under `BOOT-INF/classes` where no plain classloader looks.

**Alternative rejected.** Writing the three endpoints on the JDK's own `com.sun.net.httpserver.HttpServer` and a hand-rolled JSON writer, which would have kept the whole repository framework-free. Also rejected: `spring-boot-starter-test`, for the integration tests.

**Why.** The module boundary is what makes a framework affordable. `shrike-core` is enforced JDK-only, `shrike-clients` carries no Spring coordinate, and the engine can still be tested and shipped without a framework anywhere near it — so the starter buys request routing, content negotiation, and a JSON codec inside the one module where none of that is the interesting part. Hand-rolling them would put a second JSON encoder in a repository that is meant to be read, for the sake of a purity the enforcer rule already guarantees where it matters.

`spring-boot-starter-test` was not needed. The integration tests start the application with `SpringApplication.run(..., "--server.port=0")` and read the bound port off the context, then talk to it over real HTTP with the JDK's client — which is what a caller does, and what a mocked servlet stack would not be. This repository has no mocking framework and this slice did not become the reason to add one.

## The bind address is an argument to a second `start`, and everything else gets loopback

**Decision.** `ShrikeBroker.start(BrokerConfig, TimeSource)` binds `InetAddress.getLoopbackAddress()`, exactly as it always has, and every existing caller keeps that behaviour byte for byte. A second `start(BrokerConfig, TimeSource, InetAddress)` binds the address it is handed, and it is the only way this broker comes to listen anywhere else. `BrokerConfig` is untouched: the bind address is not one of the numbers a configuration carries, so no default, no test helper, and no call site that builds a configuration can widen it. `BrokerMain` — the entry point this slice adds — passes what `SHRIKE_BIND_ADDRESS` names, and when that variable is unset it passes the loopback address. The container image in this repository sets it to `0.0.0.0` in its own Dockerfile, and that file is the only place in this build where a wider address is written down.

**Alternative rejected.** Keeping the structural loopback bind and smoke-testing the image from inside the container with `docker exec`. Running the container with `--network host`. A `bindAddress` component on `BrokerConfig`, defaulted to loopback by `BrokerConfig.defaults`.

**Why.** Publishing a port maps a port on the host onto the container's own interface, not onto the container's loopback, so a broker bound to `127.0.0.1` inside a container is a broker nothing outside it can reach. `docker exec` gets around that by asking from inside, which proves the image runs and proves nothing at all about the port a user would connect to — and the port a user would connect to is the whole reason the image exists. Host networking makes the loopback bind work again by deleting the network namespace, and it is not portable: on macOS and Windows the container runs inside a virtual machine whose host network is not the user's.

An argument rather than a component on `BrokerConfig` is the smaller and the safer of the two. Smaller, because a component means the record header, its javadoc, its validation, `defaults`, and every canonical-constructor call site in the test helpers — against one delegating method and one line inside `bind` — and this work is rebased onto another slice that is editing those same declarations. Safer, because a configuration is a value that gets built, copied, and handed around, and the canonical constructor is what the helpers call: a component would put "listen to the whole network" one positional argument away from anybody assembling one. An argument to `start` puts the decision at the one statement that opens a socket, in a method a caller has to name deliberately, and the value is parsed and refused before that — a bind address that is not an address fails on the characters in hand, with one sentence naming the variable to fix.

**What it costs, plainly.** This build used to be able to say "the broker cannot listen beyond loopback", and now it says "the broker listens beyond loopback only when the process that starts it says so in so many words". That is weaker, and it is stated as weaker in the README rather than left for a reader to discover: there is still no authentication, no authorization, and no transport security, so an operator who sets `SHRIKE_BIND_ADDRESS` is taking on the reachability they arrange. What has not changed is the default — every existing test binds loopback through the two-argument `start` and none of them was edited, which is the evidence that the property did not quietly move.

## The broker image is built in one stage and run in another, by a user that is not root

**Refined by the security review.** The image gained a `HEALTHCHECK`, and it is a TCP connect to `SHRIKE_PORT` and nothing else: it opens a connection, closes it, and reports what that cost. Bash is what opens it, by redirecting onto `/dev/tcp`, because the JRE image ships bash and the alternative — a probe that started a JVM every interval — would spend more on watching the broker than the broker spends serving. The two richer probes were rejected for the same reason in different words. A probe that spoke the wire protocol would be a second client living inside this image, kept in step with the broker's framing by attention rather than by the compiler. A probe that read `shrike.ready` would report what was true when the broker started, which is the one thing a health check must never be. The base images stayed pinned by tag rather than by digest: nothing in this repository moves a pinned digest — there is no Dependabot or Renovate configuration — so a digest would freeze the runtime's operating system at whatever it held on the day it was written, and turn base-image patching into another thing a person has to remember. That is the same cost the Spring entry above now records for a line past its end of life, taken on deliberately there and declined here.

**Decision.** One `Dockerfile` at the repository root, holding the broker and nothing else. The build stage is `maven:3.9-eclipse-temurin-21`; it writes a `toolchains.xml` naming the JDK that image already ships and runs `mvn -B -DskipTests package`. The runtime stage is `eclipse-temurin:21-jre` and takes exactly one file out of the build — `shrike-core`'s jar, copied to a path with no version in it. It creates the user `shrike` with a fixed uid, gives it `/var/lib/shrike`, declares that path a `VOLUME`, exposes 9750, and runs `java -cp /opt/shrike/shrike-core.jar io.shrike.core.net.BrokerMain` in exec form as that user. The image's environment names the data directory, the port, and `SHRIKE_BIND_ADDRESS=0.0.0.0`; the ready file is left to its default, which puts it inside the volume.

**Alternative rejected.** A single stage, shipping the Maven image with the source and the local repository still in it. Running the reactor's tests during the image build. Running as root, because the process writes only to a volume anyway. A `Main-Class` manifest entry so the entry point could be `java -jar`. Loosening the toolchain requirement so that a build without a `toolchains.xml` would work.

**Why.** What a running broker needs is a JRE and a jar. A single stage would ship Maven, javac, the source tree, and a local repository holding every dependency of `shrike-admin` — hundreds of megabytes of things that cannot run and can only need patching. Two stages make the runtime image's contents an enumeration: a JRE, one jar, one user, one directory.

Tests are skipped in the image build because CI already owns them. `mvn -B verify` runs on every push and every pull request, and that is where a failing test is meant to stop something. Running the suite again here would run process tests inside a container nobody is watching, fail an image build for a reason CI had already reported, and — when it passed — prove nothing CI had not proved first. `-DskipTests` rather than `-Dmaven.test.skip` on purpose: the test sources are still compiled, so an image build still notices when they no longer compile against what it is about to ship.

The user is not root because nothing here needs to be: the port is above 1024 and the only thing written is one directory. The id is fixed rather than allocated so that the files in a named volume belong to the same user after the image is rebuilt, and the directory is created and handed over *before* the `VOLUME` instruction, because a fresh named volume is seeded from the image's own directory with its ownership — a `chown` after that line would apply to a path the volume then covers.

A plain classpath rather than a manifest is the smaller change: `shrike-core` depends on the JDK alone, so the classpath is one entry, and a `Main-Class` would mean configuring `maven-jar-plugin` inside the module to serve one line of a Dockerfile. Writing the `toolchains.xml` by hand is the same kind of choice made the other way: the reactor requires a Temurin 21 toolchain so that what CI tests is what a JDK 21 user runs, and relaxing that requirement to suit a container would remove the guarantee for everybody. Six lines of XML in the build stage keeps it.

## A describe takes the partition's own lock, because retention moves the numbers it reports

**Decision.** `Partition.statistics()` reads all five of a partition's numbers — log start offset, high-water mark, segment count, log bytes, index bytes — inside one acquisition of the same `ReentrantLock` a produce, a fetch, a flush, and `Partition.deleteRetiredSegments` take, and copies them into a `PartitionStatistics` before releasing it. `RequestDispatcher.describe` then builds a `PartitionDescription` out of that copy. `PartitionDescription` refuses a high-water mark below its log start offset and a segment count below one, and those refusals stay: the description is strict and the read is atomic, rather than the read being loose and the description tolerant.

**Alternative rejected.** Dropping the checks from `PartitionDescription`, or clamping a high-water mark up to the log start offset when the pair arrives inverted, so that a torn snapshot describes something rather than throwing. And, from the other end: five separate accessors on `Partition`, each taking the lock for itself, which is what the four numbers a fetch does not need would have looked like if they had been added one at a time.

**Why.** The two slices meet exactly here. Retention runs on `shrike-retention`, a thread of its own, and `SegmentedLog.deleteOldestSegment` advances `logStartOffset`, shortens the segment list, and unlinks two files — so it moves the first number, the third, and both byte counts in one go. A describe that read them one at a time could take a start offset from after a sweep beside a high-water mark from before it, and the record's own rule would then throw an `IllegalArgumentException` on the way out. That exception is not caught in the dispatcher, so it would leave as `ErrorCode.INTERNAL` on a read-only request that any client on the port may send: a remotely triggerable internal error, reachable without writing a byte to the log. Taking the lock once costs a describe what a fetch of nothing costs and rules the whole class out.

Loosening `PartitionDescription` would have been the wrong repair even though it is the smaller diff. The invariant it states is true of every partition this broker can hold — a log's first segment cannot begin after its last one ends, and the segment taking appends is never deleted — so a description that tolerated the impossible pair would be a type that had stopped saying anything, and the tear it was tolerating would still be there, showing up next as a lag row computed against a high-water mark from the wrong instant. The check is worth keeping precisely because it is the thing that would have caught the tear.

Five accessors would have been the same bug spread over five methods. `PartitionStatistics` exists so that the atomicity is in one place and visible: a caller cannot hold the lock for four of the numbers and forget it for the fifth, because there is nothing to forget.

`PartitionDescribeRetentionRaceTest` is what holds it shut. A partition with two-record segments and `retention.ms=0` takes five hundred appends on the test's thread while one thread sweeps retention and another builds the dispatcher's own `PartitionDescription` as fast as it can; the describing thread's failure is carried back to the test rather than lost. Moving the five reads outside the lock fails it on every run. The test also asserts that segments were actually deleted and that descriptions were actually taken after the start offset had moved, so a build where retention had quietly stopped could not pass it by racing nothing.

## Lag is measured against the high-water mark, not against what retention left

**Decision.** `PartitionLag.between` subtracts a group's committed offset from its partition's high-water mark and nothing else. A group that fell far enough behind for retention to delete the records it had not read has a committed offset below the partition's log start offset, and its lag still counts those deleted records.

**Alternative rejected.** Clamping the committed offset up to the log start offset, so the lag counts only what the group could still fetch. Or reporting two numbers, a lag and a "lost" count, from the facade.

**Why.** Lag answers "how far behind is this group", and a group whose backlog was deleted is not less behind than it was the moment before the sweep — it is further behind, and permanently. Clamping would report that group as almost caught up, which is the one reading an operator must not be given: the number would improve at the instant the data was lost, and the graph would go the wrong way at the worst moment. A lag of zero has to keep meaning one thing, that the group has read everything, and only a group that has read everything can be allowed to show it.

The facade does not compute a second number for what was lost because it does not need to: `GET /api/v1/topics/{topic}` already reports `logStartOffset` per partition, the group's committed offset is in the lag row beside it, and the difference is the reader's own subtraction to make. What the *consumer* is owed is a different thing again, and it is already answered elsewhere: its next fetch is refused with `OFFSET_OUT_OF_RANGE` carrying the offset the partition now starts at, which is the number it needs to resume. `GroupLagTest#countsTheRecordsRetentionDeletedInTheLagOfAGroupThatFellBehindIt` pins the arithmetic, and `BrokerDescribeTest#reportsTheOffsetRetentionMovedToBesideACommitThatFellBehindIt` pins the pair of broker answers it is computed from.

## Every documented setting is one environment variable, and the records keep their bounds

**Decision.** `BrokerLaunch.from(List<String>, Map<String, String>)` reads one environment variable per setting this build documents — nineteen of them, of which `SHRIKE_DATA_DIRECTORY` is the only one with no default — and builds the `LogConfig` and the `BrokerConfig` a broker starts with. One rule names them all: `SHRIKE_` followed by the setting's own name in capitals with each dot an underscore, so `retention.ms` is `SHRIKE_RETENTION_MS` and the README's table is that rule applied nineteen times rather than a second list to keep in step. What `from` does is conversion — text to a whole number, to one of the two `FlushMode` spellings, to a `true` or a `false` — and nothing else. The bounds are not restated here: they stay in the compact constructors of the two records, where they run for every caller those records have, and a refusal from one of them is caught in `from` and rethrown with the variable that set the field in front of it, so `segmentBytes must not exceed 1073741824, ...` reaches an operator as `SHRIKE_SEGMENT_BYTES was set to a value this broker cannot use: segmentBytes must not exceed 1073741824, ...`. A variable that is unset, or set to nothing at all, leaves its field at what `LogConfig.defaults()` and `BrokerConfig.defaults` already gave it, and `BrokerLaunchTest#runsTheDefaultsItAlwaysRanWhenNothingButTheDataDirectoryIsSet` compares the whole record to prove that a deployment which sets none of them starts the broker it started before. Anything else stops the start: `BrokerMain` prints the sentence and exits 2.

**Alternative rejected.** A configuration file — `shrike.properties` beside the data directory, or a YAML document at a path named by a variable — parsed at startup, with environment variables overriding it. Also rejected, in the other direction: converting *and* range-checking in `BrokerLaunch`, so that every refusal could name its variable without a record's exception being caught.

**Why.** A file is three problems where a variable is none. It needs a format, and this module depends on the JDK alone, so that is either `java.util.Properties` — which has no types, no comments a parser respects, and an encoding rule of its own — or a dependency the enforcer would refuse. It needs a search path, which is a list of places a broker looks for a file nobody may have written, and the first one that exists wins by an order somebody has to remember. And once the environment can override it, it needs precedence rules, which is the class of question that ends with an operator reading source code to find out why the value they set is not the value the broker ran. A single-process broker shaped for a container has none of those problems already solved for it and every reason not to acquire them: `docker run -e`, a compose file, and a systemd `Environment=` line all speak this surface without being taught to, and the image in this repository already sets three of these variables that way.

Testability is the other half, and it is why the seam is where it is. `from` is a function of two maps: a command line and an environment. Every one of these settings, and every refusal, is tested by passing a `Map.of(...)` literal — no file to write, no temp directory, no reading of the machine the suite runs on, and nothing to clean up. A file would put the interesting part behind I/O and make the configuration tests the slowest kind of test in a repository whose configuration is otherwise the easiest thing in it to check.

Keeping the bounds in the records is what makes both halves honest. Duplicating them in the environment layer would mean two places to change when a bound moves, and the day they disagreed the broker would either refuse a value the record accepts or accept one the record then refuses from a stack somewhere else. What the duplication would have bought is a message naming the variable, and that is bought instead by catching the record's `IllegalArgumentException` and putting the variable in front of the sentence it already carries: every one of those sentences begins with the field it is about, one variable sets one field, and the table from field name to variable in `BrokerLaunch` is that mapping written down. The cost is stated plainly: the table is keyed on the first word of a record's own message, so a record whose sentence stopped beginning with its field name would degrade to a refusal that names no variable — which is why `refusesASettingOutsideItsRangeNamingTheVariableThatSetItAndKeepingTheRecordsSentence` asserts on both halves and fails the build if either goes.

**A refusal is loud because the alternative is a broker keeping a promise nobody asked for.** `SHRIKE_FLUSH_MODE=per_record` — an underscore where the documented spelling has a hyphen — must not start a broker running `interval`, because the difference between those two is what an acknowledged record survives, and a deployment that thought it had bought an fsync per record would find out from a power failure. So an unknown spelling is refused with the two that work, and `Boolean.parseBoolean` is named here as the thing `SHRIKE_FETCH_ZERO_COPY` does not call: it answers `false` to every word that is not `true`, which would turn `yes` into the path this broker does not take by default and do it in silence. Two spellings, in whatever letters they arrive in, and a refusal for the rest.

What this costs is a wider surface. Four variables could be listed in a sentence; nineteen need a table, and every one of them is a way to start a broker that behaves differently from the one CI tested. That is the trade an operable configuration is: the settings were already real — validated, read on live paths, exercised by the suite — and what was missing was any way to reach them without writing Java. Building `LogConfig` and `BrokerConfig` by hand is still the other way, unchanged, for an application that embeds this broker.

## The read bound covers idling and mid-frame reading, and never covers serving

**Decision.** `read.timeout.ms` — `SHRIKE_READ_TIMEOUT_MS`, 30 000 ms by default, on `BrokerConfig` beside `connectionCap` — bounds a connection's *read phase* and nothing else. A connection is in its read phase from the moment it is accepted until `Connection.serve` has a whole request frame, and again from the moment an answer is on the wire until the next whole frame arrives. Everything in between — decoding, dispatching, a long poll's wait inside `Partition.fetch`, writing the answer — is serving, and no number here applies to it. That sentence was written before there was a write bound and it stopped one clause short: what bounds serving is `max.fetch.wait.ms` for the wait, `write.timeout.ms` for an answer no byte of is moving — "The write bound is a bound on making no progress, not on how long an answer takes", below — and the api's own work for the rest of it, which nothing here bounds and which is bounded instead by the sizes every request is clamped to. The bookkeeping is one volatile `long` per connection, `readPhaseStartedAtNanos`, stamped from the injected `MonotonicTimeSource` in the constructor and again after each answer, and set to a sentinel the instant a frame is in hand — elapsed time rather than the wall clock, for the reason "A deadline is elapsed time; a timestamp is the wall clock" sets out at the end of this file. A thread named `shrike-conn-reaper` — built like `RetentionSweep` and `FlushSweep`, waiting on the stop signal between passes rather than sleeping — asks once per bound and calls `Connection.close()` on whatever has crossed it. There is no value that turns the bound off, and none that means "no bound": the smallest it takes is 1 ms, and an operator who wants a long read sets a long number, which the record accepts up to an hour — see "The settings a caller can spend have ceilings" at the end of this file for where that hour comes from.

**Alternative rejected.** A whole-connection timeout: one stamp per connection, refreshed on every request, and a reaper that closes anything quiet for longer than the bound. Simpler bookkeeping — no sentinel, no two states, one write per request instead of two. Also rejected: `SO_TIMEOUT`, and a non-blocking rewrite around a `Selector`.

**Why.** A whole-connection timeout breaks the one api this broker holds a connection open for on purpose. A long-poll fetch waits inside `Partition.fetch`, under the partition lock, on its own connection's thread, for up to `max.fetch.wait.ms` — 30 seconds by default. To a whole-connection bound that is a connection that has said nothing for 30 seconds, which is exactly what it exists to close, so the default configuration would turn every consumer on a quiet partition into a broken connection once per bound. Making the bound larger than the fetch wait does not fix it either: it only moves the failure to whoever raises `max.fetch.wait.ms`, and it makes two settings that mean different things secretly depend on each other. The distinction the two-state bookkeeping buys is the honest one — a fetch waiting is *this broker* waiting to write, and a connection that has sent three bytes of a frame is *a caller* failing to speak — and it costs one sentinel and one extra store per request. `BrokerReadTimeoutTest#keepsALongPollFetchThatWaitsFarPastTheReadTimeoutAndServesItItsRecords` is the regression: a one-second bound, a thirty-second wait, the reaper asked 29 times while the fetch waits, and the records served at the end.

`SO_TIMEOUT` is not an option at all, which the entry above already said from the other side: it bounds reads on a socket's *streams*, and this broker reads through a `SocketChannel`, whose blocking reads it does not bound. A `Selector` and a non-blocking rewrite would bound reads properly and would replace the thread-per-connection model this build is built on, its cap, and every test of both — a slice of its own, and not one this problem justifies.

**What it costs.** Six things, stated plainly. A stalled connection is closed on the first pass after it crosses the bound, so it holds its place under the cap for between one and two bounds rather than exactly one — the same overshoot the flush interval has, and for the same reason: a pass walks every open connection, and halving the overshoot would double the walking. A client that means well but is slow — one that takes longer than 30 seconds to put a request frame on a socket — is closed with no reply, and gets no error code saying why, because a connection being reaped is not a request being refused; the DEBUG line naming the connection and the bound is on the broker's side only, and it is DEBUG because which connections stall is decided by whoever is connecting. And the reaper closes sockets and nothing else: the place a reaped connection held comes back on that connection's own thread as its blocking read fails and `serve` returns, which is the one path that releases a slot however a connection ends, so there is nothing here that can release one twice or forget to.

The other three are what this bound leaves open, and they are stated here because a number that is described as bounding a connection would be read as bounding all of it. **The write side is not this bound's to cover, and it now has one of its own.** `closeIfStalled` leaves alone anything that is serving, and a connection blocked in `ByteChannels.writeFully` — or in the `transferTo` loop a zero-copy fetch sends its records through — is serving by that definition; a peer that asked for a large fetch and then stopped reading the answer therefore held its thread and its place under the connection cap for as long as it cared to, which is the same denial a stalled reader mounts, entered from the other end of the socket. Closing it is a different mechanism rather than a wider sweep, and "The write bound is a bound on making no progress" below is that mechanism: a second stamp per connection, walked by the same reaper on the same pass. What stands unchanged from the paragraph this replaces is why it had to be a mechanism of its own — a blocking `SocketChannel` write has no deadline a JDK caller can set, there is no send-side `SO_TIMEOUT`, and `StandardSocketOptions` offers no timeout at all.

**The reaper may not die, and that is now what the code says rather than what it meant.** One thread named `shrike-conn-reaper` enforces this bound and the write bound both, so a thread that ended would take away every bound this broker has on how long one peer can hold a place under the connection cap — and it would do it silently, since the thing that would report it is the thread that is gone. A pass that failed was already meant to be a WARN and nothing more, but the catch around it named `RuntimeException`, and the failures a pass has under load are not all runtime exceptions: walking the open connections allocates an iterator, a DEBUG line allocates a message, and closing a socket can fail with whatever the operating system has left. An `OutOfMemoryError` from any of those went straight through the catch and ended the thread, under exactly the memory pressure where a stalled peer holding a slot costs the most — which is the denial this bound and the write bound exist to close, arriving through the mechanism that closes it. The catch is `Throwable` now, drop-and-continue, and the WARN itself is guarded the same way `ShrikeBroker.warnHandoffFailed` is and for the same reason: what has just failed may be the logger, there is nowhere left to report the failure of reporting, and a bound that stopped being enforced over one unwritten line would be the larger outage. That is the second of the two places that drop a throwable thrown by writing a log line, and this paragraph is what PRINCIPLES §3 asks for in exchange. Those two are not the whole of what this codebase drops, so the rest is named here rather than counted wrongly a third time. There are six sites in three shapes. Two drop a throwable from writing a WARN, because the thing that failed may be the logger: this one and `ShrikeBroker.warnHandoffFailed`. One drops what an unwind throws — `ShrikeBroker.abandon` — because that *is* the path everything is given back on, so there is nothing left to give a failure of it to. Three drop what a close throws while a start or an open is already failing with the more useful exception: `DataDirectoryLock.closeQuietlyAfterFailedTake`, `TopicRegistry.closeQuietlyAfterFailedOpen`, and `SegmentedLog.closeQuietlyAfterFailedOpen`. Every one of the six carries a `Dropped on purpose` comment pointing at the paragraph that justifies it, so `git grep 'Dropped on purpose'` is the list — which is what this sentence points at, rather than a number that goes stale the next time one is added. `ConnectionReaperTest#keepsReapingAfterAPassThrowsAnErrorRatherThanLosingBothBoundsWithThatPass` is the regression: a pass that throws an `Error`, and two more passes on the same named thread afterwards.

**The window between a frame completing and the sentinel being stamped is real, and it is one instant wide.** A frame becomes whole inside `RequestReader.readFrom`, and `readPhaseStartedAtMillis` is set to `NOT_READING` only after that call returns, so a connection that finishes a request at the moment the reaper reads its stamp is closed for a read phase it had just ended. What follows is a request served into a socket that is gone: the api does its work — a produce appends, a commit is forced — and the write of the answer fails, so the client is never told what happened to it. At-least-once delivery is the promise that already covers that, in both directions: a produce nobody was told about is retried and may duplicate, and a commit nobody was told about is either made again or paid for by redelivery. Closing the window means stamping the sentinel before the frame is whole, which would exempt a connection part way through a frame from the bound and give back the stall this entry exists to close. An instant-wide window on a path whose failure the delivery semantics already describe is the cheaper side of that trade, and it is the reason this is written down rather than left for somebody to find.

**And the bound has a ceiling, not an off switch.** `readTimeoutMs` is an `int` of milliseconds with a floor of 1 and no sentinel meaning "never reap", so the longest read phase this broker can be told to allow is `BrokerConfig.HIGHEST_CONNECTION_HOLD_MILLIS` — one hour, where this entry originally left the width of an `int` and 24.8 days. An operator who wants a long bound sets a long number and gets it, and a deployment that genuinely needs a connection to sit silent for longer than an hour has to close it and open it again. That is a consequence of choosing a bound with no way to disable it, which is the choice this entry made on purpose: a setting whose value 0 means "off" is one an operator can turn off by accident, and the resource it protects is the connection cap.

## The consumer groups a broker will hold are budgeted

**Decision.** `BrokerConfig` grew `maxTotalGroups`, 1024 by default and `SHRIKE_MAX_TOTAL_GROUPS` from the environment — the same number as the partition budget, deliberately, because both answer "how many of these may one broker for one machine accumulate" and one number is one thing for an operator to raise. A commit naming a group the store does not hold creates it; a commit that would create one past the budget raises `TooManyGroupsException` instead, and `RequestDispatcher` turns that into `INVALID_REQUEST` — code 5, the code the partition budget already uses, with no new error code and no new message on the wire. The check sits inside `GroupOffsetStore.commit`, under the one `lock` every commit holds and before the map is touched at all: the group is looked up, the budget is read, and the entry is inserted as one step, so two commits arriving together cannot both find the last place free, and a refused commit leaves the store exactly as it found it — no file, no entry, nothing for the failure-rollback to undo. A commit by a group already held is never refused by the budget, whatever it is set to. `TooManyGroupsException` is public where `TooManyPartitionsException` is package-private, for the one reason a package boundary gives: it is thrown in `io.shrike.core.group` and caught in `io.shrike.core.net`. Its constructor is package-private, so only the store can raise it.

**Startup over a directory already past the budget: open it, warn once, refuse only what is new.** `GroupOffsetStore.open` loads every group file it finds — a hundred of them under a budget of ten — logs one WARN naming the count, the budget, and the consequence, and returns a store that serves all of them. Only the group after them is refused.

**Alternative rejected.** Refusing to start when the directory holds more groups than the budget. Also rejected: evicting the oldest or least recently committed groups to make room, instead of refusing. And, in the other direction, leaving the number unbudgeted and relying on the operator not to point a group-per-request client at the broker.

**Why.** Every other cost this broker can be made to carry has a number on it — partitions, connections, request bytes, fetch waits — and this one did not, while being the cheapest of them to run up: a commit is one request, it needs nothing but a socket, and the group it creates outlives the connection, the client, and every restart afterwards. What #11 measured is the shape of it: one connection committing under fresh group ids created new groups at tens a second, each one a file that is opened and parsed at every start from then on, and a directory of twenty thousand of them added seconds to startup with every entry resident for the life of the process. Nothing in this build deletes a group, so the directory only ever grows, and "do not do that" is not a bound.

Refusing to start over a directory past the budget is the tempting symmetry, and it is the wrong call twice over. PRINCIPLES §3 says startup fails only on genuinely unusable state — an unreadable data directory — and a hundred readable group files are not that: they are committed offsets, acknowledged to the clients that sent them, and the most valuable thing in the directory to a consumer that is about to resume. A broker that refused them would turn *lowering a setting* into an outage, and into the worst kind: the fix would be to raise the number again, but the operator would find that out from a broker that will not come up. It is also exactly the call the partition budget already made, for the same reason and in the same words, and two budgets in one record that disagreed about what a lowered number does to a start would be a surprise waiting for whoever met the second one first.

Eviction is worse than either. To make room for a new group by removing an old one is to delete a committed offset, and a consumer whose offset is deleted does not fail — it silently resumes from wherever its client decides, re-reading a partition from the start or skipping to its end, and at-least-once delivery no longer describes what happened to it. A refusal costs the caller an error code it can act on; an eviction costs somebody else their place in a log, quietly, and the broker cannot even name who. Between refusing the new thing and destroying the old one, a store whose whole job is remembering offsets refuses the new thing.

What it costs is stated plainly. A deployment that legitimately needs more than 1024 groups must raise the number before its 1025th group commits, and it finds out by a refusal rather than in advance — the same shape the partition budget has. The budget counts groups that have ever committed rather than groups that are active, because this broker has no notion of an active group at all: there are no sessions and no heartbeats, so "in use" is not a question the data answers. And a group file removed by hand from the directory while the broker is down gives its place back at the next start, which is the only way to give one back; that is a deliberate consequence of having no api that deletes committed offsets, not an oversight this entry is hiding. One more, stated because a reader of `commit` will find it there: the rollback that runs when a write fails before its file reaches the directory un-creates the group when the commit that failed was the one creating it, and not only the offset that commit was putting there. The alternative — restoring the inner map and leaving the outer entry — would leave a group with no file behind it, answering nothing, loaded by no restart, and holding a place under the budget for the life of the process; and that is a place anything able to make a write fail could take, a full disk being enough and retention being off by default, one failed commit at a time under a fresh group id until the budget was gone and legitimate groups were refused. So a commit refused by the budget leaves the store exactly as it found it — nothing was written and the map was not touched — and so does a commit that failed before anything took the group's name on the device. What happens when something did is a decision of its own, below.

## What a failed commit rolls back is decided by the move, and by nothing else

**Decision.** Memory never disagrees with the device about which groups exist. `DurableFile` replaces a file in four steps — written, forced, moved, directory forced — and only the third puts a group on the device: before it the new bytes are in `<group>.offsets.tmp`, which carries no group's name and which `GroupOffsetStore.open` does not load; at it, `<group>.offsets` is a file every later reader of that directory finds, this process and the next start alike. So `commit` wraps the observer it was opened with, watches for the move, and rolls its in-memory change back only when the move did not happen. A creating commit that failed at the write or the force un-creates its group and gives its place under the budget back. A creating commit that failed after the move keeps the group, keeps the offset, and keeps the place — and still throws, because nothing confirmed the write was durable and the client must be told that. The same line decides the ordinary case: a commit replacing an offset restores the old one only when the move did not happen, since after it the file holds the new one and a restart would read it. What is on the device is what this store says it holds, in both directions.

**Alternative rejected.** Unlinking `<group>.offsets` after a post-move failure — deleting the file and forcing the directory again — so that "nothing durable landed" becomes true once more and the rollback can stay unconditional. Also rejected: leaving the rollback unconditional and accepting the divergence as rare.

**Why.** An unlink cannot be relied on to undo a move, and the moment it is asked for is the moment it is least likely to work. Removing a file durably means the same two operations the commit just failed at — a directory change and a force of that directory — on a device that has already refused one. If the unlink fails, the file stays and memory has forgotten it, which is the divergence again with a wasted write attempt in front of it; if only the force fails, the file is gone from this process's view and may return after a power cut, so memory would be wrong in the other direction. Keeping the entry needs no I/O at all, and it is right whichever of those the device would have done. Accepting the divergence is worse than either, because it does not stay one group wide: a group dropped from memory hands back a place a later commit spends on a second file, so the directory grows one group past the budget for every failure of this shape and every start after that opens over more groups than it allows — the WARN in `open` firing for groups nobody created. The cost of the choice made here is a group that exists because a commit failed: it has a file, it holds a place under the budget, and it answers the offset that file holds, which is exactly what a restart over that directory produces. The client was told the commit failed, and at-least-once delivery covers the rest — it commits again, or it is redelivered. The claim this replaces said a commit that never reached the device leaves the store exactly as it found it whichever way it ended; that was true of a budget refusal and of a failure before the move, and false after one, so it now says only the part that is proven.

Learning how far a write got means reading `DurableFile.StepObserver`, which until now was described as a test seam and nothing else. It is still the only way a JVM can observe this sequence — the point of it has not changed — but a caller with something to undo needs the same trace a durability test does, so its javadoc says so and the store wraps whatever observer it was opened with, recording the step before passing it on. Recording first is what makes the injection in the test honest: a step is reported once it has run, so an observer that throws stands for a device that failed after that step, and a move that ran is a move the store must not pretend away.

`GroupOffsetStoreTest#forgetsAGroupWhoseCreatingCommitFailedBeforeItsFileWasMovedIntoPlace` and `GroupOffsetStoreTest#keepsAGroupWhoseCreatingCommitMovedItsFileIntoPlaceAndThenFailed` are the regression, one for each side of the move, and between them they inject a failure after every one of the four steps and assert both halves each time: what the directory holds afterwards, and how many places under the budget are left. The second fails at both its steps without the change above.

## A deadline is elapsed time; a timestamp is the wall clock

**Decision.** There are two clocks in this broker, and they answer different questions. `TimeSource` answers "what time is it": it stamps a record, it ages a segment against `retention.ms`, it decides when `flush.interval.ms` has gone by, and it is what a fetch's `maxWaitMs` expires against, because all of those are about a moment somebody outside this process can name. `MonotonicTimeSource` answers "how much time has gone by": a reading is nanoseconds since that source was built, never negative and never smaller than a reading already handed out, and `SystemMonotonicTimeSource` produces one by subtracting a `System.nanoTime()` taken in its constructor. Every deadline a connection is held to is measured on the second one. `Connection.readPhaseStartedAtNanos` is stamped from it, `ConnectionReaper` reads it once per pass, and `StalledConnections.closeStalledConnections` takes that reading — so what the reaper compares is two readings of the same climbing counter, and the subtraction between them is the only thing the bound is made of.

**How it is injected.** `ShrikeBroker.start(config, timeSource)` and `start(config, timeSource, bindAddress)` build a `SystemMonotonicTimeSource` themselves; a package-private third overload takes one, and this package's own tests are the only callers. That asymmetry is deliberate. The wall clock is injectable in public because which clock stamps a record is a decision an application embedding this broker may legitimately want to make. There is only one elapsed-time clock on a host, no operator configures it, and a public way to name another would be a public way to stop every deadline this broker holds — so the seam exists where the tests are and nowhere else.

**Alternative rejected.** Leaving both jobs on `TimeSource`, which was already injected everywhere and which the read-bound tests already moved. Also rejected: adding a second method to `TimeSource` rather than a second interface beside it.

**Why.** A wall clock is a number that moves in both directions and is not this broker's to control. A time-synchronization daemon correcting a drifted host, an operator setting the date, a virtual machine resuming from a snapshot — each of those steps it, and a bound built by subtracting two of its readings inherits the step. Forwards by an hour: every connection part way through a request frame, and every connection idle between requests, crosses the bound in the same instant and is closed, including the honest slow ones — and a reaped connection is not a refused request, so none of those clients is told anything at all. Backwards by an hour: every bound in flight is stretched by an hour, which is a stalled connection holding a place under `connectionCap` for an hour longer than the number an operator set, at exactly the moment the machine is least well. Elapsed time cannot do either, and `BrokerReadTimeoutTest#measuresTheBoundOnElapsedTimeSoAWallClockStepDoesNotMoveIt` steps the wall clock an hour in both directions with the elapsed clock held still, asserts the reaper closes nothing, and then closes the connection by moving elapsed time alone.

A second method on `TimeSource` would have made one type answer both questions, and every implementation of it — including the lambdas this suite is full of, and whatever an embedder passes — would have to answer both. The two are not the same question, and a test that freezes the date to assert a timestamp would then also be freezing every deadline in the broker it was testing. Two interfaces, each with one method, cost one more field on `ShrikeBroker` and one more lambda in the tests that care about both.

The sentinel is the small print, and it improves. `NOT_READING` is `-1`, held in the same field as the stamp, and a wall-clock reading of `-1` is a real epoch millisecond — one millisecond before 1970 — so the collision was impossible in practice and not by construction. An elapsed reading is never negative by the interface's own rule, which `SystemMonotonicTimeSourceTest` holds the implementation to, so the sentinel is now a value no reading can take.

What it costs: the DEBUG line a reaped connection writes converts its nanoseconds back to milliseconds, because an operator reading it is holding a `read.timeout.ms` in milliseconds; a test that cares about both clocks injects both; and the places that wait for a thread rather than bound a connection — `joinBounded`, the acceptor's backoff — still measure real time directly, since how long a shutdown has waited is a fact about this machine that no test may freeze.

## The write bound is a bound on making no progress, not on how long an answer takes

**Decision.** `write.timeout.ms` — `SHRIKE_WRITE_TIMEOUT_MS`, 30 000 ms by default, on `BrokerConfig` beside `read.timeout.ms` — bounds the time one connection's answer spends with not a byte of it leaving. The bookkeeping is a second volatile `long` per connection, `writeProgressAtNanos`: set from the elapsed-time clock as a write begins, set again from inside the write loops every time bytes actually go, and set back to a sentinel in a `finally` when the write ends however it ends. `shrike-conn-reaper` asks about it on the same pass it asks about the read phase, and a connection can only be in one of the two states, so one pass closes a connection for one reason. The reaper's interval is now the shorter of the two bounds, which keeps the overshoot on either at between one and two of its own bounds. Closing the socket is the whole of what happens here too: the closed channel ends the parked write with an `AsynchronousCloseException`, `serve` returns down the path a client hanging up already took, and the connection's own thread gives back the map entry and the place under the cap — the one release path, which runs once and only once whether the connection ended on a stall-close, on a completed answer, on an exception, or on a shutdown.

What counts as bytes leaving is reported by the two loops that write: `ByteChannels.writeFully` says what each `write` returned, and `RecordRange.transferTo` says what each transfer moved, both through `WriteProgress`, a one-method interface whose other implementation does nothing and is what the log's own appends pass. A long poll is not covered, because it is not writing: `Partition.fetch` waits before `Connection` writes a byte, so `max.fetch.wait.ms` bounds that and this bounds what follows it.

**Neither loop asks the operating system for more than a mebibyte at a time**, and that is not an optimization. A blocking `write(2)` and a blocking `sendfile(2)` both return only once everything they were asked for has gone: measured here, one `transferTo` of eight mebibytes to a socket whose peer was reading 16 KiB at a time returned once, after all eight had been taken. A loop that reported per call would therefore report nothing at all for the whole of a large answer, and the bound would close exactly the slow-but-progressing peer it exists to spare. So `WriteProgress.MAX_BYTES_BETWEEN_REPORTS` caps the ask at one mebibyte, which makes the honest statement of the bound "a peer that has not taken a mebibyte of its answer in `write.timeout.ms`" — 35 KiB a second at the default — and costs one system call per mebibyte on a path that moves gigabytes a second. The benchmark in Slice 5 transfers a 1 048 478-byte range, which is one ask either way, so what it measured is what this still does.

**Alternative rejected.** A cap on total serve time: stamp when an answer begins, close the connection if it has not finished within the bound. Simpler by one stamp and by the whole reporting interface. Also rejected: a `Selector` and a non-blocking rewrite, and `SO_SNDBUF` tuning as a substitute for a deadline.

**Why.** A total-serve cap cannot tell a peer that is being served slowly from a peer that is not being served at all, and the difference is the whole point. A consumer on a slow or busy link legitimately takes a four-mebibyte fetch in pieces; under a 30-second total cap it is closed part way through, with no error code — a reaped connection is not a refused request — and it retries, and is closed again at the same place, for ever. Raising the cap to fit the slowest legitimate peer raises it for the hostile one too, so the number would have to be either an outage for slow clients or a much weaker bound for stalled ones. A progress bound has no such trade: it is crossed only by a peer that has stopped taking bytes, whatever the answer's size, and `BrokerWriteTimeoutTest#servesAnAnswerLargerThanTheSocketBuffersToAPeerThatDrainsItSlowly` is the regression — an answer of nearly eight mebibytes, drained sixteen kibibytes at a time, with the clock moved to one nanosecond short of the bound past the last progress before every one of the reaper's passes, so the transfer costs many bounds of elapsed time and is never closed. The same class closes the stalled peer and counts the place it held coming back.

`SO_SNDBUF` is not an answer either, and it is worth saying why since it is the option a reader reaches for: a smaller send buffer makes the broker block sooner, which is the opposite of a deadline — it changes how much of an answer a stalled peer can absorb before the thread parks, not how long the thread stays parked.

**The window between an answer's last byte and its stamp being cleared is real, and it is one instant wide** — the mirror of the window the read bound's entry describes. A connection clears `writeProgressAtNanos` in a `finally` on its own thread, which runs after the client already has the last byte, so a reaper pass landing in between judges a finished write by when it last moved. In real time that instant is microseconds and the bound is 30 seconds, so nothing can cross it without a thread being descheduled for the whole bound — at which point closing that connection is the right answer anyway. Against an injected clock it is reachable, which is why `BrokerReadTimeoutTest` gives its broker a write bound larger than any step it makes: a test that moves time by a whole bound inside that instant is testing the instant rather than the bound.

**What it costs. Neither this bound nor the read bound bounds a connection's life, and the largest number they leave is a large one.** Both are bounds on a *phase*: one read phase, one answer with nothing moving. A peer that pays the cost of one small request per bound, or that takes one mebibyte of an answer per bound — about 35 KiB a second at the default — is making progress by both definitions and is never closed, so it holds its place under the connection cap for as long as it cares to, legitimately. That is not a hole to be plugged: it is what "a bound on making no progress" means, and the alternative is the total-serve cap this entry rejected above. What follows from it is worth stating as a number rather than leaving to be worked out. One answer's worst case is `ceil(answerBytes ÷ 1 MiB) × write.timeout.ms`, because that is how many times the bound can be restarted by a peer taking the least the loops will report — at the maxima, a gibibyte of records at an hour per mebibyte is 1024 hours, near enough 43 days, and up to twice that once the reaper's one-to-two-bound overshoot is counted. At the defaults the same arithmetic is a fetch of 4 MiB at 30 seconds a mebibyte: two minutes. Throughout such a hold, a zero-copy fetch also keeps the descriptor its range reads through open, which retention already tolerates by design and which is what keeps a deleted segment's bytes on disk until that peer is done. So the honest summary of both bounds is that they bound how long a connection can hold a slot *while making no progress*, and that the connection cap — not time — is what bounds a peer that keeps paying.

**What it costs, continued.** Four more things. A peer slower than a mebibyte per bound is closed, which is the resolution the paragraph above buys and the README states in the same words rather than claiming "no byte at all". The bound has a ceiling and no off switch, exactly as the read bound does: at least 1 ms, at most an hour of them, and a broker that wants a long bound sets a long number. A connection closed mid-answer gets no error code and cannot: the frame it was being sent is half-written, and the only honest thing left to do with that stream is end it. And a fetch's records are read from the file inside the transfer, so a stalled peer still holds one descriptor on a segment — which retention already tolerates by design, since a range holds a descriptor of its own — for as long as the bound allows and no longer.

## One broker at a time owns a data directory, and a lock file is how it says so

**Decision.** A start takes an exclusive `FileLock` on `<dataDirectory>/shrike.lock` before it opens anything, and a start that cannot have it refuses with one sentence naming the directory and the file that holds it. `DataDirectoryLock.take` is where that happens, and *where in `ShrikeBroker.start` it happens* is the point of it: after `Files.createDirectories`, which the lock file needs, and before `TopicRegistry.open` — so no partition log is recovered, no registry is rewritten, and no group offsets file is renamed onto its folded name inside a directory another broker is already writing to. The file holds no bytes at all; the claim lives in the operating system's lock table and the file is a handle to hang it on. It is released, and its channel closed, on the way out of `close()` — last, after every log has been closed, because the directory is the next broker's the instant this one lets go of it — and on every failed start, through the same quiet close a failed start already gives the listening socket, so the lock is let go once and only once whichever way a start or a stop ends. Nothing deletes the file, here or anywhere: a lock file left behind is a file and not a claim, and the next start locks it without noticing.

**Alternative rejected.** A pid file: write this process's id into the data directory at startup, and have a start that finds one probe whether that process is still alive before deciding whether to run. Also rejected: `FileLock.lock()` rather than `tryLock()`, so a second broker waits for the directory instead of being refused it.

**Why.** A pid file cannot answer the question it is asked. It outlives the process that wrote it, so every start has to guess what a file it finds means, and the only probe a JDK offers — `ProcessHandle.of(pid)` — asks about a number the operating system recycles: a pid that belongs to something else by the time it is read answers "still running" and turns a broker that crashed into a directory nobody can start over, which is the outage the mechanism was supposed to prevent arriving from the mechanism itself. A `FileLock` needs no probe, because the kernel already knows: it goes when the channel is closed, when the process exits, and when the process is killed, so a crash leaves the lock free and the file behind, and reclaiming it is a start rather than a repair. `BrokerDataDirectoryLockTest#startsOverALockFileLeftBehindByABrokerThatIsNoLongerRunning` is that half written down, and `#startsOverTheSameDataDirectoryOnceTheBrokerHoldingItHasStoppedCleanly` is the other.

Waiting for the lock is worse than refusing it. Two brokers over one directory is an operator's mistake — a unit file started twice, a container run twice over one volume — and a second broker that blocks on it looks to whoever started it like a broker that hangs: no port bound, no ready file, and nothing said. Refusing says the true thing in the words the entry point already prints, `shrike cannot start: <sentence>` and exit 2, which is the shape a port already bound has always arrived in.

**Two ways to be refused, one sentence for both.** Another process holding the lock makes `tryLock()` answer null. This same JVM already holding it makes the same call throw `OverlappingFileLockException`, because a lock is held per JVM rather than per channel — and a second `ShrikeBroker` in one process is exactly that, whether it is an application embedding two of them or a test starting the second. An unhandled `OverlappingFileLockException` would be a stack trace where a sentence belongs, so both become the same `ShrikeIOException`, and `BrokerDataDirectoryLockTest#refusesToStartOverADataDirectoryABrokerIsAlreadyRunningOverAndLeavesThatBrokerServing` proves the same-JVM half with the first broker still serving afterwards. The two-process half is the branch a suite inside one JVM cannot reach, and it is the simpler of the two: `tryLock()` returns null and the same sentence is thrown from the same line.

**Refined by the security review: the same-JVM refusal used to release the lock it was refusing.** The refusal above was implemented by opening a channel, catching the `OverlappingFileLockException` that `tryLock()` throws, and closing that channel again — a refusal must close what it opened or leak a descriptor for the life of the process. That is wrong on POSIX, and it is wrong in the quietest possible way. The JDK implements `FileLock` with `fcntl` record locks, and POSIX drops **every** lock a process holds on a file the moment that process closes **any** descriptor on it. The second attempt never held a lock at all — `tryLock()` throws out of the JVM's own `FileLockTable` before a system call is made — so closing its channel released the *running* broker's claim as a side effect, silently, from the code path whose whole job was to protect it. A repro proved the shape end to end: a process holding the lock, an outside process correctly refused, a second start inside the JVM refused with the right sentence, and the same outside process then granted the lock over a broker that was still serving on its port. The fix is that a start claims the directory in this JVM **before** `FileChannel.open` — a process-wide set of claimed directories, entered atomically, keyed on `toRealPath()` so that a relative spelling, a symbolic link, or a `..` cannot become two claims on one lock file — and a start that cannot have the claim is refused without opening anything. On that path the descriptor whose closing did the damage is never created — which is not the same as never at all, and the re-review paragraph two below is what that turned out to cost. The claim is given back in `close()`, in a `finally`, so that a release that failed still ends this broker's claim rather than making the directory unstartable in this JVM for ever. `BrokerDataDirectoryLockTest#keepsTheRunningBrokersLockOnTheDataDirectoryAfterRefusingASecondBrokerInThisJvm` is the regression, and it asks the question from where the bug lives: a separate JVM, because a lock is held per process and a second question inside this one is answered by the JDK's table rather than by the kernel. It asks three times — before the refused start, after it, and once the broker has stopped — and the third answer is what keeps the first two honest.

**Alternative rejected.** Leave the descriptor open *instead of* claiming the directory: catch the overlap, refuse, never close the channel the refusal opened, and add nothing else. It is a one-word change and it fixes the release, because the lock is only dropped when a descriptor is closed.

**Why.** On its own it trades a silent unlock for a silent leak, and the leak is unbounded in exactly the case that produces it: an embedder or a supervisor that retries a start it expects to be refused leaks one descriptor per attempt until the process runs out of them, which is a broker that stops accepting connections because it once tried to start twice. The claim costs one entry in a set for as long as a broker runs, and it takes that retry off the path that opens anything at all — which is what makes not closing affordable where the claim cannot help, below. **This set is static mutable state, which PRINCIPLES §2 forbids, and this paragraph is the exception that section's preamble requires.** What it holds is a fact about the operating-system process rather than about any object inside it — the JDK's own `FileLockTable` is static for the same reason — and there is nowhere to inject it from: `ShrikeBroker.start` is what takes a lock, and the caller that must be refused is precisely an embedder starting a second broker, so a registry handed in would be a registry that could be handed in twice.

**Refined again by the security re-review: the claim and the lock table do not key on the same thing.** The residual named above — "what is left of the overlap path is some holder in this JVM that is not a broker" — was too kind to itself by one case, and that case is a broker. A claim is kept under `dataDirectory.toRealPath()`; the JDK's `FileLockTable` is kept under the lock file's device and inode. Two directories that really are two directories, whose `shrike.lock` is one file — a hard link, a bind mount, a symbolic link to the lock file rather than to the directory holding it — are therefore two claims over one lock: the second start takes a claim nobody else holds, reaches `FileChannel.open`, and lands in the overlap branch with a running broker's lock at stake. Closing the channel there did exactly what the fix above was written to stop, and a probe confirmed it, answering `FREE` for a directory a broker was still serving over. So that branch was made to refuse **without closing anything**, and its cost was put at one descriptor per aliased start attempt, held until the process ends — which is the claim the entry below measures and finds false, because a channel nothing references is not a channel anybody is holding. What survives of this paragraph is its diagnosis: the claim and the lock table did not key on the same thing, and that is what the fix below finally addresses. `BrokerDataDirectoryLockTest#keepsTheRunningBrokersLockWhenRefusingAStartOverADirectoryThatSharesItsLockFile` is the regression it left behind, and it is where the next entry starts, because what that test asserted was true only for as long as it took to ask.

**And the claim itself is given back structurally now, on every way out.** It used to be removed in three places — the null `tryLock`, the overlap, and the `IOException` — which is every failure anybody had written down and not every failure there is. An `Error` out of `FileChannel.open` or `tryLock` under memory pressure, or anything else thrown between the claim and the return, left the entry behind for the life of the process, and the entry is a path with nothing behind it: every later start over that directory in this JVM would then be refused by a claim no broker was holding, which is the same outage a stale pid file causes and the reason a pid file was rejected in the first place. So `take` sets a flag on the one line that succeeds and gives the claim back in a `finally` whenever that flag is unset, which covers the failures nobody has thought of as well as the three that were listed. `close()` gained the mirror of it: the removal there is guarded by a compare-and-set, because the entry names the directory rather than the lock, and a second close of an already-closed lock would otherwise take away the claim of whatever broker holds that directory now. Neither is reachable through today's callers — `ShrikeBroker.close` is idempotent behind its own compare-and-set — and both are one flag each, which is cheaper than the reasoning it would take to keep them unreachable.

**Refined a third time by the delta review: a descriptor nothing is holding on to is not a descriptor that is kept.** "One descriptor per aliased start attempt, held until the process ends" describes a channel somebody references, and the refusal above referenced nothing — it caught the overlap, threw, and left the channel it had opened unreachable. A `FileChannel` the JDK opens for itself has a cleaner registered on it that closes the descriptor once the channel is phantom-reachable, so that refusal did not keep a descriptor: it scheduled one to be closed at the next collection, and on POSIX that close drops every lock this process holds on the file. A repro measured all of it. The probe answered `HELD` immediately after the refusal and `FREE` after a collection that 390 MB of ordinary allocation was enough to cause — no `System.gc()` anywhere, just the garbage serving requests makes — while the running broker's `FileLock.isValid()` went on answering `true`, which is the whole reason nothing noticed. And 20 000 aliased attempts peaked at 3 215 open descriptors rather than 20 000, which is the same fact from the other side: the reclamation was happening all along, and every reclamation was the close that cost the lock. So the previous fix moved the unlock off the refusal's own line and onto a collection some milliseconds later, which is worse than where it started rather than better, because nothing in a stack trace points at it.

**What replaced it.** A claim is kept under the lock file's identity now rather than the data directory's path: `Files.readAttributes(lockFile, BasicFileAttributes.class).fileKey()`, the device and inode pair the JDK's own `FileLockTable` is keyed on, read by a `stat` that opens no descriptor at all. Two directories whose `shrike.lock` is one file map to one claim, so an aliased start is refused **before** `FileChannel.open`, exactly as a second start over the same path already was — no descriptor, no cleaner, and nothing that grows when a supervisor retries. Reading an identity wants a file to read it from, and the first start over a directory is the one where there is none, so `take` creates it with `Files.createFile` — `O_CREAT|O_EXCL` — and that choice is load-bearing rather than incidental: on a file that already exists the call fails inside the kernel without a descriptor ever existing, so it cannot close one on an inode a broker is holding. An open-then-close there, even one that never asked for a lock, would be this entry's own bug rebuilt in the one place nobody would think to look for it.

**The overlap branch survives as a backstop, and pins what it opens.** Two things still reach `FileChannel.open` with somebody's lock behind it: the moment between reading the identity and opening the file, in which another thread of this JVM can take the lock, and a holder in this process that took no claim because it is not a broker. That branch keeps its channel in a second static field, `PINNED_REFUSED_CHANNELS`, because a strong reference is the only thing a garbage-collected runtime offers that actually keeps a descriptor open — a pinned channel survived ten forced collections in the repro that closed an unpinned one. Anything else thrown out of the open or the lock is treated the same way, since a channel an `Error` left behind is on the same hazard as one an overlap left behind. **That field is the second static mutable field PRINCIPLES §2 forbids and this file documents**, on the same grounds as the first: an open descriptor is a fact about the operating-system process rather than about an object inside it. It was a set when this entry was written; the entry below makes it a map keyed by what a claim is keyed by, and the last entry of this section puts a third field beside it.

**Refined a fourth time by the round-4 review: "neither is a thing a retry repeats" was false, and the repro measured it.** What that sentence bounded the pinned descriptors by was rarity — nothing which reaches the backstop, it said, is something a supervisor repeats. Three shapes say otherwise, and the first of them is ordinary. A holder of `shrike.lock` inside this JVM that is not a broker plus a start retried against it pinned one descriptor per attempt, 200 out of 200; under `ulimit -n 200` the 193rd pin was followed by an unrelated log segment failing to open and an unrelated listener failing to accept, which is descriptor exhaustion arriving from the branch written to prevent an unbounded leak. The other two are the same fact through the claim's own edges. A lock file that cannot be stat'ed at claim time — a symbolic link to a name that is not there yet — falls back to a path key, so a second directory aliasing that same file keys on the identity instead, the two keys never collide, and every retry over the second one reaches the backstop. And a filesystem with no `fileKey()` at all puts every start on path keys, where the same thing happens for the same reason. In each of the three the claim cannot refuse the retry, so the retry pins.

**What replaced it: the kept channels are keyed by the lock file's identity, and the one already open is what every later start over that file asks.** `PINNED_REFUSED_CHANNELS` is a `ConcurrentMap` from the lock file's `fileKey()` to the single channel kept for it, and `take` reads it **before** `FileChannel.open` — where it has an identity to read it by, which the last entry of this section is about. A start over a file this process is already keeping a descriptor on opens nothing at all: it asks that descriptor for the lock and gets one of the same three answers — refused by the kernel, refused by the JVM's lock table, or granted, in which case the entry is handed over to the lock that now holds it and closed with it. So the cost is one descriptor per lock file, held until a start takes the lock through it or until the process ends, whichever comes first. What makes that bound exact rather than nearly so is that the map is keyed by what the claim is keyed by: a take reads or writes the entry for a key only while it holds the claim on that key, and a claim admits one holder at a time, so no two takes can be opening a descriptor for one file at once and there is no racing pair that keeps two. That is the bound wherever `fileKey()` answers, which is what this map is for. Where a claim falls back to a directory's real path there is no identity to key on, and this entry first said the fallback key would do — one per key, it said, being the honest statement. It will not do, for a reason that is about soundness rather than about counting, and the last entry of this section is the correction: nothing kept on that path is asked for a lock at all.

**Alternative rejected.** Refuse a start whose file is already kept outright, without opening anything and without asking anything: it bounds the descriptors exactly as well and it is one line rather than five.

**Why.** It turns a transient condition into a permanent one. The holder that made a start reach the backstop lets go — it is something in this process that is not a broker, and the test for this branch has it let go — and a start refused by the entry alone would still be refused afterwards, for the life of the process, by a record of a holder that is gone. That is precisely the outage a stale pid file causes, which is the thing this whole mechanism was chosen over, and swapping an exhausted descriptor table for a data directory this JVM will never start over again is trading one availability defect for another. Asking the descriptor that is already open keeps the bound and the availability both, and it costs a `tryLock` that opening a second descriptor would have cost anyway. `BrokerDataDirectoryLockTest#keepsOneDescriptorPerLockFileHoweverManyStartsANonBrokerHolderRefuses` is the regression and it asserts both halves: 25 retried starts against a holder that does not let go add nothing to the count after the first — against the previous implementation that assertion reads `expected: <1> but was: <26>` — and the start that follows the holder's release puts the count back where it began, because the descriptor went with the lock.

**An edge that stays, named rather than left to be found.** A filesystem with no identity to give answers `null` to `fileKey()` — Windows is the usual one — and the claim falls back there to `dataDirectory.toRealPath()`, which is what every claim used to be and which the backstop covers. What the backstop does on that path is worth stating in one sentence rather than leaving to be inferred from two entries: a refused channel is kept, it is never asked for a lock, and one is kept for every refused attempt rather than one for the file. It is never asked because a key that names a directory cannot say which file a descriptor is open on, so handing one over would be a lock on whatever inode it happened to hold rather than on `shrike.lock`; and every one is kept because a channel kept nowhere is a channel the cleaner closes, which is the close that drops this process's lock. So a supervisor retrying a start on such a filesystem spends a descriptor a turn, which is what this cost before the map was keyed and is the price of a filesystem that cannot identify a file. The usual such filesystem is one this build does not run on and cannot while a commit's durability depends on an fsync of a directory, which "A topic name and a group id are case-insensitive" says in the same words; what reaches the fallback here is a lock file that cannot be stat'ed, which any filesystem can produce. And an identity is a file's, so a `shrike.lock` unlinked out from under a running broker leaves that broker's claim and lock on an inode with no name, and the next start creates a new file and locks it. What that costs inside this JVM is more than the "same hole rather than a new one" this entry first called it, and the entry below is the correction: it is a refusal the path key used to make. The two-process half of it is real and is the oldest reason nothing here deletes the file.

**Refined a fifth time by the same review: keying a claim on the identity alone gave up a refusal the path key used to make.** "Deleting that file already did precisely this to another process, so it is the same hole rather than a new one" was true of another process and false of this one. With a claim kept under `dataDirectory.toRealPath()`, a second start after `rm shrike.lock` under a live broker was refused; with one kept under the lock file's identity, that start creates a file of its own, reads an identity nobody holds, and takes it — two `DataDirectoryLock`s over one data directory inside one process, each `isValid()`, each on a different inode, which is the thing this class exists to refuse. A repro ran it both ways against the two implementations. So a take claims both keys now — `fileKey()` and `dataDirectory.toRealPath()` — and either being somebody's already is the refusal: an alias is caught by the identity, a lock file that has been replaced underneath its broker by the path. A take that cannot have both takes neither. `claimAllOrNone` rolls back exactly what it had added, so a refused start touches nothing of the incumbent's; the keys are added in one order, identity then path, so two takes that share a key collide on it in one place and only the loser rolls back; the failure path in `take` gives back the same list it made, before which it keeps whatever descriptor it opened; and `close()` gives that list back once, behind the compare-and-set it already had. `BrokerDataDirectoryLockTest#refusesASecondBrokerOverADirectoryWhoseLockFileWasDeletedUnderTheBrokerHoldingIt` is the regression, and against the previous implementation it fails with `Expected io.shrike.core.log.ShrikeIOException to be thrown, but nothing was thrown`.

**What the second key still does not cover, said here rather than found later.** The other process. A broker elsewhere on the machine, started over a directory whose `shrike.lock` was deleted under the broker holding it, creates a new file and locks it, because the kernel's lock went with the inode and there is nothing on the new file to collide with. Nothing inside this JVM can refuse that, a claim was never what would, and it is the oldest reason nothing here deletes the lock file. What the second key restores is the half of that hole this process can answer, which is the half an embedder or a supervisor is on.

**Refined a sixth time by the round-5 review: a descriptor is only worth asking where the key is the file's own identity.** The entry above bounded the kept descriptors by keying them, and keyed them by whatever the claim was keyed by — which is the identity where there is one and the data directory's real path where there is not. Asking a descriptor kept under an identity is sound because an identity *is* the device and inode: the descriptor is provably open on the file the next start is asking about. Asking one kept under a path is not, and the difference is not a matter of degree. A path names no inode, so the file behind a descriptor kept under one may be an inode `shrike.lock` has stopped naming — the lock file was replaced, or it is a symbolic link to a name that has since become a different file — and a start handed that descriptor takes the lock on the orphan and never opens `shrike.lock` at all. A repro planted such a descriptor and ran a real `take` over a directory whose `shrike.lock` was a symbolic link to a name that was not there: the take reused it, an outside process found the file it had really locked `HELD`, and the file `shrike.lock` named did not exist — so the next broker over that directory would have created it and locked it, which is two brokers over one data directory, the thing this class exists to refuse. So the read before `FileChannel.open` happens only where `fileKey()` answered, and a take with no identity opens a descriptor of its own every time.

**And the keeping had to change with it, in the same commit, because the naive half of that fix rebuilds an older bug.** Scoping the read while leaving the keeping alone — one channel per key, `putIfAbsent` — would mean a second refusal over a path-keyed directory finds the slot occupied, is not stored, and is referenced by nothing; a channel nothing references is closed by the cleaner the JDK registers with it, and that close drops every lock this process holds on the file. That is the third-refinement bug arriving through the code written to bound it. So refused channels with no identity go into a list per key that nothing ever reads for a lock, and every one of them is kept: one descriptor per refused attempt, which is exactly what this cost before the map was keyed, paid only where the filesystem cannot identify a file. **That list is the third and last static mutable field PRINCIPLES §2 forbids and this file documents**, on the grounds the other two carry: an open descriptor is a fact about the operating-system process rather than about an object inside it, and there is nowhere to inject a process fact from. `BrokerDataDirectoryLockTest#opensItsOwnDescriptorRatherThanAskingOneKeptForALockFileItCannotIdentify` and `#keepsEveryRefusedDescriptorWhereTheLockFileHasNoIdentityToBoundThemBy` are the regressions, and against the previous implementation they fail with `expected: <true> but was: <false>` — the open never ran — and `expected: <25> but was: <1>`, which is twenty-four descriptors left for the cleaner. What those two cannot do is reach the keeping through a refusal, and they say so in their own javadoc: a refusal that keeps a descriptor is one whose open landed on an inode this JVM already locks, and on a filesystem that answers `fileKey()` that cannot be arranged with a lock file whose stat fails, because such a file's open either creates a fresh inode nobody holds or would have been stat'ed. What is left of that shape is the race between the stat and the open, and a filesystem with no identities at all. So the tests hand `DataDirectoryLock` exactly what such a refusal hands it and assert what a take does with it afterwards.

**Alternative rejected.** Key the fallback on something narrower than the directory — the lock file's real path, say — and go on reusing, so that the bound stays one descriptor per file everywhere.

**Why.** A path is not an identity however narrow it is, and that is the whole finding rather than a detail of which path. `toRealPath()` resolves the name that exists when it is read; nothing binds the descriptor kept under it to the file that name resolves to when the next start reads it again, which is precisely the window an unlinked or replaced lock file opens. The other candidate — refuse a start outright where there is no identity — was rejected once already, two entries above, and for the same reason it was rejected there: it turns a transient holder into a data directory this JVM can never start over again. Keeping the descriptors and never asking them is the only answer that is sound under a collector and still lets the directory start once the holder lets go, and its cost is a descriptor an operator can see in `lsof` on the one kind of filesystem that charges it.

`BrokerDataDirectoryLockTest#keepsTheRunningBrokersLockWhenRefusingAStartOverADirectoryThatSharesItsLockFile` is the regression for the first half, and it fails against the previous fix twice over: the refusal it asserts opened nothing carries an `OverlappingFileLockException`, and the probe it asks after a bounded run of collections answers `FREE` where it now answers `HELD`. `#keepsTheLockOfANonBrokerHolderInThisJvmWhenTheStartThatMetItIsRefused` is the regression for the backstop and the only test that reaches that branch at all now: something in this JVM that is not a broker holds the lock file, the start that meets it is refused after opening a channel, and the probe still answers `HELD` on the far side of the collections. Neither test sleeps, which §4 and §6 would both have something to say about: each round drops a canary, asks for a collection, and waits on a `ReferenceQueue` until that canary's phantom reference is enqueued — a bounded wait on a reference-processing pass rather than a guess at how long one takes. That is what the canary witnesses and no more: it orders nothing about the cleaner that closes an unreferenced `FileChannel`, which runs on a thread of its own after the enqueue. So an unlucky schedule can make either assertion pass because nothing has got round to closing the descriptor yet, which is a false pass and not a flake — neither test can fail for a schedule, and a failure is a descriptor that was closed, which is the bug.

**Alternative rejected.** Close the refused channel and re-take the lock immediately afterwards, so the window in which the running broker holds nothing is small rather than absent. Also rejected: a reference queue of this class's own, or a shutdown hook, so that pinned channels are closed eventually rather than held for ever.

**Why.** A small window is still a window, and the kernel decides who wins it: between the close and the re-take, anything on the machine may take the lock on a directory a broker is serving, and the broker that re-takes it cannot tell it ever lost it — a `fcntl` lock says nothing about who held it a moment ago. The second is worse than it looks. A queue that closes pinned channels is a queue whose whole job is to close descriptors on a file this process holds a lock on, which is the bug with a scheduler in front of it; and a shutdown hook runs when those locks are being given up anyway, so it saves nothing and adds a thread to the worst moment of the process's life. Holding the descriptor is the only answer that stays true under a collector, and its cost is a number an operator can see in `lsof`.

**What it costs**, stated plainly. One more file in a data directory — created by the claim now rather than by the open a moment later, and by `O_CREAT|O_EXCL` so that creating it can never disturb one that is already there — one open channel for the life of the process, and one more channel per lock file the backstop refuses a start over — one per refused attempt where the filesystem cannot identify that file, which is the edge two entries above. An application that embeds two brokers over one directory now gets a refusal where it used to get two brokers quietly sharing, which is a behaviour change and the intended one. The lock binds what takes locks — every broker — and nothing else: a program that writes into the data directory without asking for one is not stopped by this, and neither is a data directory on a network filesystem whose locking is a fiction, which has larger problems than this anyway.

## The settings a caller can spend have ceilings, and each ceiling is a resource

**Decision.** Five settings on `BrokerConfig` decide how much memory and how much time somebody with a socket can make this broker hold, and each of them now has a largest value as well as a smallest one. `maxRequestBytes` is at most `HIGHEST_MAX_REQUEST_BYTES`, 1 073 741 824 — one gibibyte, which is `LogConfig.MAX_SEGMENT_BYTES`, the number that already caps a segment and a record: the largest request this broker will hold is the largest record it can store, so the two are one number rather than two that can disagree. `connectionCap` is at most `HIGHEST_CONNECTION_CAP`, 1024 — a platform thread and an open file descriptor each, which is about a gibibyte of thread stacks before a byte of request buffer, and the default `ulimit -n` on Linux. And `maxFetchWaitMs`, `readTimeoutMs`, and `writeTimeoutMs` are each at most `HIGHEST_CONNECTION_HOLD_MILLIS`, 3 600 000 — one hour, one number for the three because they measure one thing between them: how long one connection may hold its place under the cap while nothing about it moves. A value past any of them is refused exactly as a value below a floor already was, in the record's own compact constructor, and `BrokerLaunch` puts the variable that set the field in front of the sentence, so `SHRIKE_CONNECTION_CAP=65536` stops the start with `connectionCap must not exceed 1024, a platform thread and a file descriptor each, but was 65536` behind the variable's name. `BrokerLaunchTest#refusesEveryCappedSettingOneOverItsCeilingNamingTheVariableThatCrossedIt` walks all five one over the line and `#takesEveryCappedSettingAtItsCeilingExactly` sets all five to the line itself, so each ceiling is proved from both sides.

**What this buys, in one line of arithmetic.** The memory one client can make this broker hold is `connectionCap` × `max.request.bytes`, and the javadoc on `DEFAULT_CONNECTION_CAP` has always stated it at the defaults: 64 × 4 MiB, 256 MiB. At the maxima it was not a statement at all — 64 × 2 GiB is 128 GiB with the cap left alone, and there was no configuration this record would refuse — so the sentence was true of the broker CI tested and of no other. Now the same sentence has a second half that holds everywhere: 1024 × 1 GiB, one tebibyte, is the most any configuration this record accepts can be asked for. That is a large number and it is meant to read as one. It is the *most* a deployment can name, not a recommendation, and naming it takes two deliberate edits; what changed is that the number exists at all, which is the difference between a bound and the width of two `int` fields.

**And the line of arithmetic has a second reading, which `fetch.zero.copy` decides.** With zero-copy fetch on — the default — the product above is exact: the largest thing a connection holds on the heap is the request frame it is reading, and a fetch's records go from the segment file to the socket without being read into memory, so the answer costs a header. With `fetch.zero.copy=false` the same product roughly doubles, because that path reads the range into a byte array and then `ResponseFrame.encode` allocates a whole frame and copies the records into it: for the moment before the write, a fetch's records are on the heap twice. A deployment that turns zero-copy off — which "A fetch response carries the log's own bytes" describes and which exists for filesystems where `transferTo` misbehaves — should therefore read the envelope as about `2 × connectionCap × max.request.bytes`, and the two edits that reach the maxima are three edits on that path.

**Alternative rejected.** Bounding the product instead of the factors: refuse a configuration whose `connectionCap` × `maxRequestBytes` passes some number of bytes, and leave both settings otherwise open. Also rejected, in the other direction: ceilings small enough to make that product comfortable — 64 MiB of request bytes, say, and 256 connections, which is 16 GiB.

**Why.** A product refused is a refusal that cannot say what to fix. An operator who raised the connection cap for a reason and the request bound for another reason would be told that the two of them together are too much and left to decide which of their two reasons to give up, in a message that names neither the variable they last edited nor a number they can put back. A ceiling per setting is refused where it was set, names the variable that set it, and is the same shape every other refusal in this build already has — and each of the five can be justified on its own resource, which is what makes the numbers defensible rather than arbitrary: a thread and a descriptor, a gibibyte the log itself caps, an hour of a slot.

Small ceilings were the tempting other end, and they buy a comfortable product by breaking configurations that work today. `max.record.bytes` may be set up to a gibibyte, and a record that large can only be produced and fetched by a broker whose `max.request.bytes` is at least as large, so a 64 MiB request ceiling would make records this build can *store* records it cannot *receive* — an incoherence between two settings that an operator would meet as a produce that closes the connection with no reply. Tying the request ceiling to `MAX_SEGMENT_BYTES` keeps the two coherent by construction, and it takes exactly one configuration away: a request bound above a gibibyte, which is only reachable by a deployment producing a record of the largest size this build allows plus its envelope. The connection cap's ceiling breaks nothing at all — 1024 platform threads is sixteen times the default and past where this broker's shape stops being the right one — and an hour is a hundred and twenty times each time bound's default, so a deployment that has raised one of them by more than two orders of magnitude is describing a client that should be reconnecting rather than a broker that should be waiting.

**`maxTotalPartitions` and `maxTotalGroups` keep their floors and get no ceiling, and that is a decision rather than an omission.** The security review that produced the five above asked the same question of these two, since they have the same shape: a floor of 1 and nothing above. The answer is that they are guards rather than multipliers. Nothing about `maxTotalPartitions = 2147483647` costs this broker anything by itself: partitions come into being one create at a time, each one costs a directory and two descriptors when it is made, and the process runs out of file descriptors long before the number is reached — the budget exists to turn that into a refused create naming the number it crossed, and a budget set past what the machine can hold is a guard an operator switched off, which is a thing an operator is allowed to do. The five settings above are not like that: no request has to arrive for `connectionCap` × `max.request.bytes` to be what 64 sockets can hold at once, and `read.timeout.ms` is how long they can hold it. A ceiling on a guard would be a second guard on the first, and it would refuse a start over a data directory whose partition count the operator had deliberately stopped bounding. The floors stay because a budget below 1 is a broker that can hold nothing.

**What it costs.** A deployment already running one of these five past its new ceiling does not start after this upgrade: it is refused at startup, naming the variable and the number, which is the loud half of the trade this build makes everywhere else and the reason the ceilings are generous. The three time bounds share one constant, so raising the hour raises it for all three — deliberate, since they are one question, and the record would need three constants and three sentences to make them separately settable. And a ceiling is a number in a record rather than a fact about a machine: 1024 connections on a host with a 256-descriptor `ulimit` is still a start that ends in descriptors this broker cannot open, and the acceptor's own handling of that is what covers it.

## A startup refusal echoes the operator's value through the same scrubber a rejected name goes through

**Decision.** Every raw environment value that appears in a `BrokerLaunch` startup refusal — the number that would not parse, the flush-mode or `fetch.zero.copy` word this build does not know, the port, the bind address — is echoed through `SafeName.quote` rather than concatenated straight into the sentence. That primitive already cuts a rejected string to 200 characters and replaces every byte that is not printable ASCII with `?`, because a rejected topic name is hostile input on its way into a log line; a rejected environment value is the same shape of thing, so it takes the same path. The one change to `SafeName` is that the method is now visible past its own package.

**Refined by the security review: what a refusal is *caused by* is part of the refusal.** Scrubbing the sentence left the cause chain under it untouched, and the JDK's own exceptions carry the value whole — `Integer.parseInt` names the text in `For input string`, and ten thousand digits are ASCII digits, so they pass the digit check and reach it; `InvalidPathException` embeds the path it could not make; an `UnknownHostException` *is* the name it could not resolve, newline and all. `BrokerMain` prints only `getMessage()`, so nothing this build ships ever printed one — but `BrokerLaunch.from` is public api, and an embedder that logs a start it could not make logs the causes with it, which is the forged line and the flooded file arriving one layer below the sentence that had scrubbed them. So a JDK failure read here is translated rather than chained: the refusal says which variable and what it was given, through `SafeName.quote`, and nothing behind it says the value a second time. What that costs is the type of the underlying failure, whose one meaning the sentence already states — and it is a deliberate translation rather than a swallowed exception, which is the distinction PRINCIPLES §3 draws. `BrokerLaunchTest#carriesNoneOfAHostileValueInWhateverARefusalIsCausedBy` walks the whole chain of every kind of value this class refuses, including a spelled-out setting that is never parsed at all, so that a scrubber call cannot be quietly removed from any of them.

**Alternative rejected.** A second scrubber next to the parse code, sized and shaped for environment values. Also rejected: echoing the value raw, on the argument that a startup refusal is read by the operator who set the value and not by a stranger. And, for the cause chain: keeping the JDK's exception as the cause with its message rewritten, rather than dropping it — rejected because rewriting the message of an exception somebody else threw is a lie about what threw it, while a translation says plainly that this class refused the value.

**Why.** A value read from the environment is chosen by whoever can set the environment, which in a container is whoever writes the compose file or the orchestrator manifest — not always the operator reading the log. A value with a newline in it forges a second log line that reads like the broker's own, and a value a mebibyte long floods the standard-error stream the refusal is the only intended line of; both are the log-forgery and log-flooding a name that becomes a path was already scrubbed against. A second scrubber is a second chance to be more generous than the first — the exact thing `SafeName`'s own comment says one copy exists to prevent — so reusing the one that is already reviewed and tested is both the smaller diff and the safer one. Echoing raw was rejected because the two-halves refusal this file already describes quotes the value on purpose, and a sentence that quotes an attacker's bytes verbatim is a sentence the attacker writes half of.

## Which width a setting is read at is pinned by a test, because the compiler will not object

**Decision.** Every numeric variable `BrokerLaunch` reads is covered by a test that hands it 2147483648 — one past the largest number an `int` holds — and says what must become of it. The ten that land in `int` fields are refused in the width's own sentence, `must be a whole number from -2147483648 to 2147483647`. The four that land in `long` fields — `retention.ms`, `retention.bytes`, `flush.interval.ms`, `flush.interval.bytes` — take the number and keep it, which is asserted on the value the record ends up holding rather than on the absence of a refusal. And the port, the one number read in a range narrower than its field, is refused in the range a port is read at. `BrokerLaunchTest#refusesEverySettingItReadsAsAnIntAtANumberOnePastAnIntsLargest`, `#keepsEverySettingItReadsAsALongAtANumberOnePastAnIntsLargest`, and `#refusesAPortOnePastAnIntsLargestInTheRangeAPortIsReadAt` are the three, and between them they name every numeric setting this broker reads.

**Alternative rejected.** Leaving the width to the compiler, which is what every version before this one did: the field's type picks the `wholeNumber` overload, the overload picks the parse, and the code is correct by construction. Also rejected: deriving the widths by reflection over the record components, so the table could never fall behind the records it describes.

**Why.** Correct by construction is the problem rather than the answer here. Retyping `segmentBytes` from `int` to `long` — to raise a ceiling, or to make one byte count match another — is a one-word edit that compiles, passes every test, and silently changes what an operator may set from about two gibibytes to nine exabytes, in a field whose bound was reviewed at the narrower width. The reverse edit is quieter still: a `long` narrowed to an `int` turns a `retention.ms` of a hundred days into a refusal an operator meets in production rather than in review. Neither shows up anywhere, because the width a setting is read at is not a behaviour any other test asks about — the bounds tests ask what the record refuses, and a record refuses the same way at either width. Pinning it costs one case per setting and turns both edits into a red test naming the variable, which is the loud half this build asks for everywhere else. Reflection was rejected for the reason a generated table always fails at this: it would agree with whatever the records say and follow the retyping rather than object to it, which is the whole of what these three tests are for.

## A number is read only in ASCII digits, though the JDK's own parse would take more

**Decision.** Before `Integer.parseInt` or `Long.parseLong` is called on anything `BrokerLaunch` reads — the port and every `SHRIKE_*` whole number, through one `requireAsciiDigits` the three parse sites share — the trimmed text must be ASCII digits behind at most one leading ASCII `-`. Text that is not throws the `NumberFormatException` the parse itself would have thrown, from inside the same `try` the parse sits in, so a value refused for the script it is written in is refused in the words a value refused for its letters has always been refused in: the variable that set it, the range the field is read at, and the value quoted through the scrubber the entry above describes. The minus sign stays legal because `retention.ms` and `retention.bytes` are switched off with `-1` and an operator sets that from the environment, which `BrokerLaunchTest#takesTheMinusOneThatSwitchesRetentionOff` keeps true; the plus sign, which the JDK accepts, does not, because one spelling of a number is enough.

**Alternative rejected.** Trusting the JDK parse, which is what every version before this one did. Also rejected: refusing the script in a sentence of its own — "must be written in ASCII digits" — rather than in the sentence a number that will not parse already earns.

**Why.** `Integer.parseInt` and `Long.parseLong` accept a Unicode decimal digit from any script: `Long.parseLong("٤٢")` is 42, so `SHRIKE_MAX_REQUEST_BYTES` written in Arabic-Indic digits would not be refused as unreadable — it would start this broker on a 42-byte request bound, a number nobody typed on purpose and nobody can read back out of the running configuration afterwards. A configuration surface whose whole rule is "what a variable says either starts this broker or stops it, and it is never quietly traded for something else" cannot make an exception for a value that means one thing to the parser and nothing to the person, and the person is the one who has to audit it. Allowing the one script this file already treats as the number and refusing every other keeps every readable value working, `-1` included, and turns the rest into the refusal a letter in the value has always earned. A list of refused scripts was the other shape and fails the way deny-lists fail — the next script is one it does not name — where an allow-list of ten digits and a sign is complete by construction. A refusal sentence of its own was rejected for a smaller reason: it would be a second thing a startup refusal can say about a number, and an operator reading it would learn the value's script rather than the range the setting takes.

## The temporary file a durable write goes through is created, never opened over

**Decision.** `DurableFile.replace` deletes whatever holds the name `<target>.tmp` and then creates its own with `CREATE_NEW`, `WRITE`, and `NOFOLLOW_LINKS`, where it used to open that name with `CREATE`, `WRITE`, and `TRUNCATE_EXISTING`. The order is the whole argument. `Files.deleteIfExists` unlinks a name and never the file behind it, so a symbolic link planted at `<target>.tmp` is what goes and the file it pointed at keeps every byte it had. `CREATE_NEW` then covers the instant between that delete and the open: a name anything has taken back in the meantime — a file, a link, a link pointing nowhere — is a name the create fails on rather than one it writes through, which the JDK reports as a `FileAlreadyExistsException` and this class reports as the `ShrikeIOException` every other failure of this sequence arrives as. `NOFOLLOW_LINKS` is the same door locked a second time and costs one option. A stale temporary file left by a crash is therefore deleted on purpose, rather than emptied as a side effect of writing over whatever was found there.

**Alternative rejected.** Leaving `CREATE` and `TRUNCATE_EXISTING` as they were, on the ground that every file this build replaces lives inside a data directory one broker holds an exclusive lock on. Also rejected: deleting the temporary file and then opening it with plain `CREATE`, which is this fix with the window left open. And, from the other end, refusing to write at all when something already holds `<target>.tmp`.

**Why.** The lock argument is true of the topic registry and of every group's offsets, and false of the one file this build writes for another process to read. The ready file is a handshake — it exists so that whoever started a broker can learn the port it bound — so it is written where that process can read it, and a shared temporary directory is the ordinary place for that. Anybody who can write there can create `shrike.ready.tmp` before the broker does, and under the old options that name was opened for writing and truncated: the file at the far end of a planted link would have been emptied, filled with `port=` and `pid=`, and then unlinked by the move, all inside a broker doing exactly what it was told. It takes an attacker with write access to a directory the operator chose, which is why this is hardening and not an incident; it costs one deleted name and one changed option, which is why it was not left as a note.

Deleting without `CREATE_NEW` fixes the case where somebody planted a link and walked away, and not the case where somebody is watching. Between the unlink and the open there is a window another process can put the name back in, and a `CREATE` would then open precisely what was put there — the same defect with a smaller target to hit. `CREATE_NEW` turns that window into a failed create, which is the honest end of it: a broker that could not create its own temporary file has written nothing, and the target still holds what it held. Refusing outright when the name is taken closes the same window and is the worse trade, because of which of the two events is likelier. A crash between creating the temporary file and moving it leaves a temporary file behind, and a refusal would turn that one bad shutdown into a broker that can neither write its registry nor take another commit until somebody deletes a file by hand — an outage manufactured by the guard, on the ordinary event rather than the hostile one.

The outcome this still leaves an attacker who can take `<target>.tmp` in a directory the broker does not own — writing the name, planting a link, or, on a sticky `/tmp`, pre-owning it so the delete fails with `AccessDeniedException` — is a durable write that fails, and with the ready file a broker that will not start; it is never a write that goes through their file. That residual is accepted as a boundary of the no-authentication, loopback-default posture this build states elsewhere rather than a defect this fix leaves open: an attacker holding that directory can deny the write by other means already, so the denial is that posture showing through, not a hole in the door this entry just locked.

`DurableFileTest#deletesASymbolicLinkPlantedAtItsTemporaryFileRatherThanWritingThroughIt` and `ReadyFileTest#deletesASymbolicLinkPlantedAtItsTemporaryFileInASharedDirectoryRatherThanWritingThroughIt` are the regression, one on the mechanism and one on the file that made it worth fixing; both fail before this change by finding somebody else's file emptied. `DurableFileTest#deletesAStaleTemporaryFileLeftBehindByACrashRatherThanBeingBlockedByIt` is the other half, and it is what says the refusal above is not what got built. Where a filesystem will not create a symbolic link at all, the two link tests abort rather than fail: what they are about is what becomes of one, and a filesystem that has none has nothing to say about it.

## What a failed create rolls back is decided by the move, the same as a commit

**Decision.** Memory never disagrees with the device about which topics exist, or with how many partitions. `TopicRegistry` now writes its file through the same `DurableFile.StepObserver` wrapper `GroupOffsetStore` uses — a `StepsTaken` recording each step before passing it on — and the third step is what it watches, for the reason "What a failed commit rolls back is decided by the move, and by nothing else" gives above: before the move the new list of topics is in `topics.tmp`, which no start reads, and at it `topics` is the file every later reader of the directory finds. A create that failed before the move leaves the broker as it found it, holding no topic and spending none of the partition budget. A create that failed after it keeps the topic — at the partition count the file lists, and whether what failed afterwards was forcing the directory or opening the logs — and still fails to the client, because nothing confirmed the write was durable. The entry this pairs with says the same thing about groups; the registry deliberately said nothing about topics until now, and that silence is what #35 asked to be turned into a sentence.

A topic kept this way has no log open behind it, so `Topic` grew a partition count of its own rather than deriving one from the size of its list. The count is what the file says, because the file is what the next start opens and what every later rewrite of that file is built from; the list is what this broker can serve, which is nothing until that start. A produce or a fetch naming one of its partitions is answered `unknown topic or partition` — the existing refusal, no new code — and a create naming it again is `TOPIC_ALREADY_EXISTS`, which is the whole point.

**Alternative rejected.** Rewriting the registry file to take the topic back out after a post-move failure, so that "nothing durable landed" becomes true again and memory can stay as it was. Also rejected: leaving the map alone and reconciling at the next create by reading the file back and merging it with what the broker holds. And, for the log-opening half of it, retrying the open or deleting the partition directories the failed one left.

**Why.** Rewriting the file to undo a move is the unlink argument in different clothes, and it fails the same way: it needs the two operations the create has just failed at — replacing a small file and forcing the directory — on a device that has already refused one, and a rewrite that fails halfway leaves the file naming a topic memory has forgotten, which is the divergence again with a wasted attempt in front of it. Keeping the entry needs no I/O at all and is right whichever way the device would have gone.

Reading the file back at the next create is the fix #12 suggested and it is a worse shape than it looks. It makes two answers to "which topics exist" and consults them in a fixed order, so every question that is not a create — a describe, the partition budget, a produce's lookup — goes on being answered from the map alone and goes on being wrong. It also turns every create into a read of a file this broker is the only writer of, which is a durability claim traded for a filesystem round trip. One answer that is kept right is cheaper and easier to state.

The last two are about the log-opening half, and what stopped both is that the on-disk state after that failure is already correct. A create writes the registry file before it opens a log, deliberately — the class says why — so a create that failed while opening partition 2 of 3 leaves a file listing three partitions and directories for the two that opened, and the next start opens all three, creating the one that is not there. Nothing is orphaned and nothing needs deleting; what was broken was only that the broker had forgotten the topic and would let the next create of that name rewrite the file with a smaller count, which is what left directories above it listed by nobody. Retrying the open inside the failure would be recovery machinery for a device that is failing, at the one moment it is least likely to work, and it would have to decide what to do when the retry failed too — which is the question this entry already answers.

What it costs is stated plainly. A topic can exist that this broker serves no partition of until it is restarted: the client was told its create failed, and every produce and fetch naming it is refused as an unknown partition, so nothing is silently accepted into a topic that is not open. It holds its partitions under the budget, because they are partitions the next start will open. And a WARN names it, the count, and the restart, because an operator meeting `TOPIC_ALREADY_EXISTS` for a topic no partition of which answers has a right to read why in the log. `TopicRegistryTest#forgetsATopicWhoseCreateFailedBeforeItsRegistryFileWasMovedIntoPlace` and `#keepsATopicWhoseCreateMovedItsRegistryFileIntoPlaceAndThenFailed` inject a failure after each of the four steps and assert both halves every time — what the directory holds, and what the broker believes — and `#refusesALaterCreateOfATopicWhoseRegistryFileLandedButWhoseLogsWouldNotOpen` is the log-opening half, made to fail by putting a regular file where a partition directory has to go.

## A refusal the framework has already named keeps that name, and a 5xx a caller can drive keeps its cause without its stack

**Decision.** Two changes to `ErrorResponses`, both of them about who is on the other end of a failure. The first: before the `Exception` catch-all answers 500, a failure that implements Spring's `ErrorResponse` and carries a 4xx is answered with the status it carries and this facade's own sentence for it. The one a caller can raise here is `HttpMediaTypeNotAcceptableException` — an `Accept` header naming nothing this facade produces — and it is now 406 `request refused` rather than 500 `internal error`. The second: the 503 for a broker that cannot be reached is logged through `answerWithoutTheStack`, which writes one ERROR line carrying the failure's own sentence and the class and message of what caused it, and does not hand the throwable to the logger. A framework refusal carrying a 5xx is left where it was, at 500 with its whole stack, because nothing says a caller drove it. Alongside them, `logging.level.org.springframework.web.servlet.PageNotFound=ERROR` is pinned in `application.properties`: the dispatcher writes one WARN naming the path for every request nobody serves, before this facade is asked anything.

**Alternative rejected.** For the mapping: an `@ExceptionHandler` per Spring exception this facade might meet. It cannot be written as one handler for the interface — `@ExceptionHandler` takes throwable types and `ErrorResponse` is not one — so it would be a list, and a list is a thing to keep in step with a framework this build patches by hand. Also rejected: extending `ResponseEntityExceptionHandler`, which brings RFC 9457 `ProblemDetail` bodies and a second answer shape with them. For the 503: keeping the stack and rate-limiting it, which needs state — a counter, a window, and a decision about when the window resets — for a line that is the same line every time. And, at the other end, dropping the 503 to DEBUG the way a 4xx is dropped.

**Why.** A request asking for a representation this facade does not produce is a request the caller can fix, so 500 was both the wrong story and the expensive one: the catch-all logs a 5xx with its throwable, so one header per request bought a stack trace per request, which is exactly the caller-driven disk fill the 4xx paths were already fixed for. Reading the status off `ErrorResponse` is one branch and it is the framework's own answer to "what is this failure worth" — it covers the siblings of that exception without naming them, and a Spring release that adds another gets it right for free. The `ProblemDetail` route was refused for a plainer reason than either: this facade publishes one error shape, and the README's claim that every failure is one shape is a claim a second shape ends.

The 503 is the case the 4xx rule did not cover and should have. A broker that is down is a state, not an event: every request that arrives while it holds meets the same failure, so the digit at the front of the status is the wrong thing to split on and "who can cause this again" is the right one. Rate limiting was the obvious shape and it buys nothing here — the second stack is identical to the first, so what a window would preserve is a repetition nobody reads, at the cost of mutable state on an error path. Dropping to DEBUG goes too far the other way: a broker this facade cannot reach is a condition an operator has to be told about, and told once per request is still told. So the level stays ERROR and the cause stays in the sentence, which is where an operator's eye goes first; the fifty frames underneath it named the same three classes every time. `AdminFacadeIT#writesOneLineAndNoStackForEachOfABurstOfRequestsToABrokerThatIsNotListening` asserts the count, the level, and the address in the line, and `#answersNotAcceptableWithoutAStackWhenACallerWillTakeNoMediaTypeThisFacadeProduces` asserts the 406 and the one quiet line behind it; both read the records this facade's own `System.Logger` makes, through `CapturedLog`, so that what a failure costs is asserted rather than reviewed.

The `PageNotFound` pin is the same argument about a line this facade does not write. Its own answer to an unmapped path is a quiet DEBUG line and a 404 in the one shape, but the dispatcher had already written a WARN naming the path by then, so log volume stayed proportional to request volume and a stranger with a list of paths decided how much of the disk was spent. Nothing is lost by pinning it: the request is still answered, still logged by the code that answers it, and `AdminFacadeIT#answersAPathNobodyServesWithoutTheFrameworkWritingAWarningPerRequest` asserts the pin through `isWarnEnabled()`, which is the predicate the dispatcher itself consults before writing that line.
